### 0.1 外部情報の採用基準

本プロジェクトは公開仕様書のない機器を対象とするため、外部から寄せられる情報が本書に混入しやすい。以下のいずれかを満たすもののみ採用する。

1. **実測データ** — 実機で確認した結果。取得条件を併記する
2. **一次情報** — メーカー公開資料、動作するソースコード、当事者の記述
3. **明確な新パターン** — 既知の情報と矛盾せず、かつ検証手順が示せるもの

**採用しない典型:**

- 「界隈で語り継がれている」等、出典を辿れない伝聞

## §1 プロジェクト概要

### 1.1 解決する問題

ALPS MD シリーズの公式 Windows ドライバは 32bit 版のみで、64bit Windows では動作しない。Windows のプリンタドライバはユーザーモードで動作するが、64bit の spooler プロセスは 32bit DLL をロードできないため、これは原理的な制約であり、パッチや設定では回避できない。

既存の回避策は 2 つ。32bit 仮想マシンの運用、またはコミュニティ製のスタンドアロンユーティリティ。前者は運用が重く、後者はアプリの印刷ダイアログから使えない。

Foilwright は、**任意のアプリケーションの印刷ダイアログから通常のプリンタとして選択でき、白・金銀を含む特色印刷が可能な** 64bit ネイティブの印刷経路を提供する。

### 1.2 前提となる利用者像

作者自身と、ALPS MD プリンタを所有する少数の知人。模型・フィギュア界隈でのウォータースライドデカール作成が主用途。想定台数は 10 台未満。

**エンタープライズ品質のサポートは提供しない。** 動作確認済みの構成以外は保証しない。この方針は README に明記する。

### 1.3 やらないこと

- 昇華モード(ダイサブ)への対応
- Windows 以外の OS
- v4 プリンタドライバ形式(§3.2 参照)
- 難読化・解析対策(§12.3 参照)

なお、MD-5500 の USB 直結対応は**やらないことではなく保留である**。§11.3 を参照。

## §2 用語定義

| 用語 | 定義 |
|---|---|
| **インク** | 物理カートリッジ 1 本に対応する色。CMYK 各色、特色白、メタリック金銀など |
| **プレーン** | 1 インク分の 1bit ラスタ。同サイズ・同解像度で複数枚が重なって 1 枚の成果物になる |
| **パス** | プリンタが用紙を 1 回通す動作。原則 1 パス = 1 インク |
| **マジックカラー** | 特定の RGB 値をインクに予約する方式。原稿中の該当画素がそのインクのプレーンに振り分けられる |
| **ページ分割方式** | 1 ページ = 1 インクプレーンとする代替方式。マジックカラーが機能しない場合の逃げ道 |
| **auto_undercoat** | インクが乗る全画素の和集合として自動生成されるプレーン。白の下地に使い、**最初に刷られる**。旧称 `auto_backing`(裏打ちと誤解されるため改名) |
| **golden** | ppmtomd が生成した既知正解のバイト列。実装の正しさを判定する基準 |
| **LF 補正値** | パス間の紙送り誤差を補正する値。機体固有・実測値 |
| **セッション 0** | Windows のサービス用セッション。spooler および変換器が動作する。ユーザーのデスクトップから隔離されており、**UI を表示できない** |

## §3 システム構成

### 3.1 四層構造

```
L0  transport   物理経路への書き込み
L1  emitter     MD コマンド生成 + 機種プロファイル
L2  raster      画像 → インク別 1bit プレーン
L3  interface   PPD / ポートモニタ連携 / トレイアプリ
```

**依存方向は L3 → L2 → L1 → L0 の一方向のみ。** 逆流を禁止する。特に L0 と L2 は機種を一切知らない。機種差は L1 のプロファイルに閉じる。

### 3.2 経路全体

```
アプリケーション(Photoshop / Illustrator / ペイント等)
  ↓ 印刷ダイアログでプリンタを選択
Microsoft PostScript Printer Driver V3 + 自作 PPD
  ↓ PostScript
Windows スプーラ
  ↓
mfilemon(ポートモニタ / 既製品・改造しない)
  ↓ パイプで標準入力へ
Foilwright 変換器(セッション 0 / UI を持たない)
  ↓ ジョブをキューフォルダに積んで即終了
Foilwright トレイアプリ(ユーザーセッション / UI を持つ)
  ↓ WritePrinter (RAW)
Generic / Text Only プリンタ → USB001 → USB-パラレル変換ケーブル
  ↓
MD-5000 / MD-5500
```

### 3.3 なぜプリンタドライバを自作しないか

3 つの理由による。

1. **署名**。ドライバパッケージには署名が必要。自己署名で回避可能だが手間が増える
2. **Microsoft の方針**。サードパーティ製プリンタドライバは段階的に廃止されつつある。Microsoft 純正ドライバを使う本構成はこの影響を受けにくい
3. **不要**。PPD を差し替えれば、純正 PostScript ドライバのまま独自プリンタとして振る舞う

### 3.4 なぜ v3 形式か

v4 プリンタドライバは Microsoft 製以外のポートモニタを使用できない。本構成はポートモニタに依存するため、**v3 形式一択**である。選択の余地はない。

### 3.5 なぜ二段構成(変換器 + トレイアプリ)か

ポートモニタから起動されるプロセスはセッション 0 で動作する。セッション 0 はユーザーのデスクトップから隔離されているため、**そこからダイアログを表示しても誰にも見えない**。

特色印刷はカートリッジ交換を伴うため、人間への指示 UI が必須である。よって UI を持つプロセスをユーザーセッション側に分離する。

副次的な利点として、印刷ダイアログを押した時点でアプリケーションが解放される、複数ジョブを溜めて同一インクのパスをまとめられる、という点がある。

## §4 不変条件

**以下は絶対保証である。破る変更は本書の更新を伴わなければならない。**

### 4.1 座標と単位

内部座標は **常にドット単位**。mm は L3 の入口(PPD 解釈)でのみ扱い、それ以降ドットに変換して持ち回る。

**根拠:** 解像度が機種・設定で変わるため、mm を持ち回ると変換が散らばり丸め誤差が蓄積する。

### 4.2 プレーンは 1bit

各インクプレーンは 1bit ラスタとする。ハーフトーン処理はソフトウェア側の責務。

**初版は閾値二値化のみを実装する。** ディザリングは実装しない。

**根拠(一次情報):**

- 公式マニュアルは、**複数の特色を同時に使用する場合、中間階調は表現できない**と明記している。単一特色のみの場合はグレースケール表現が可能(§13.3)
- 可変ドットによる階調表現は VPhoto 系モードの機能であり、走査解像度とは別系統(§11.1)
- 本プロジェクトの主用途は白 + 色の複数特色印刷であり、上記制約に該当する

**注意:** 「マイクロドライは階調をまったく持たない」というのは**誤りである**。単一特色時のグレースケールと VPhoto の可変ドットが存在する。1bit を採る根拠は機構の限界ではなく、**複数特色使用時の制約と、本用途がそれに該当すること**にある。

**用途上の妥当性:** アイデカールはベタ塗りと線で構成され、階調表現をほぼ必要としない。ディザを先に入れると、コマンド生成の正しさを検証する段階で変数が増える。

### 4.3 パスとカートリッジの関係

**初版は 1 パス = 1 カートリッジで実装する。ただしこれは実装方針であり、機器の制約ではない。**

公式マニュアルによれば、機器はメタリック系と CMYK を同時に印刷する機能を持つ(§13.2)。したがって「複数インクを 1 パスで刷れない」は**誤りである**。

確定している制約:

- **白インクは、メタリック & CMYK 同時印刷に使用できない。** 白は単独パスとなる(一次情報。§13.2)

初版で同時印刷を実装しない理由は、コマンド生成の検証を単純に保つためである。単独パスの積み重ねで所望の結果が得られる以上、同時印刷は最適化であって要件ではない。

**パスの実行順序**はパレット定義の `order` の昇順とする。**`order` が同値の場合は、パレット定義ファイル内の記述順とする。**

同値を許す理由は、メタリック系のように**同格であることが設計情報として意味を持つ**インク群が存在するためである。同格なものに異なる `order` を振ると、その差に意味があるように見えてしまう。順序の決定性は実装規則(§4.9)で担保する。

**tie-break に `name` を使ってはならない。** インクを改名すると印刷順が変わり、また利用者が同格インク間の順序を制御する手段が改名しかなくなる。記述順であれば、行を入れ替えるだけで制御できる。

**順序の意味:先に刷ったものが下の層になる。** ウォータースライドデカールは刷った面を表として使うため、**表から見て奥にあるものを先に刷る**。したがって白の下地が最初、その上に色が乗る。

**根拠(実測 + 一次情報の一致):**

- 作者が 32bit 環境の公式ドライバで実作業していた際、**白を先に刷り、その上に色を重ねていた**(§10.5)
- 公式ドライバの Print Using における白の項目名は **White (Undercoat)** である(§13.3)。Undercoat は下塗りを意味し、その上に別の層が乗ることを前提とした語である。VPhoto Primer (Undercoat) も同様

**注意:** Back Print Film(裏面印刷フィルム)は透かして見る前提の媒体であり、順序が反転する。**ウォータースライドデカールとは別物であり、混同しないこと。**

**重ね刷り:** 白は隠蔽力を上げるため同一プレーンを複数回刷ることがある。パレット定義の `passes` で回数を指定する(§6.1)。


### 4.4 機種差はプロファイルに隔離

機種による分岐を L1 のプロファイル外に書かない。`if model == "MD-5500"` のような条件分岐がプロファイル定義の外に現れたら、それは設計違反である。

### 4.5 インク一覧をコードに埋めない

インクの定義は必ず外部ファイル(§6)から読む。列挙型やハードコードされた配列としてインク名をソースに書かない。

**根拠:** 将来サードパーティ製スポットカラーインクを追加する可能性がある。その際に設定行の追加のみで済む形を維持する。

### 4.6 生成バイト列は常にダンプ可能

変換器は、プリンタへ送出するバイト列をファイルに保存する機能を**常に持つ**。これは後付けできない要件である。

**根拠:** 遠隔地の利用者から「印刷できない」と報告された際、バイト列があれば原因の大半が特定できる。ログのない不具合報告は解析不能。

### 4.7 `ref/` と `src/` は異なる言語で維持する

参照実装(Python)と本番実装(C#)を同一言語に統一しない。

**根拠:** MD のコマンド言語には公開仕様書がなく、実装は推測に基づく。同一言語では同じ誤解を両方で踏む。型の扱いが異なる言語で二度書くことで、仕様理解の曖昧な箇所が挙動の差として顕在化する。

### 4.8 L0 を送信専用に固定しない

L0 のインターフェースは、将来 **read が生えうる前提**で設計する。

- ポート名、プリンタキュー名、接続方式を L1 以上に漏らさない
- L0 を「バイト列を送る関数」として型に固めない。送出方式を差し替え可能な抽象として扱う
- 現時点で read を実装しないが、追加時に L1 以上の変更を要する形にしない

**根拠:** §11.2(タイミング)、§11.3(USB 直結)、§11.4(エラー状態の読み出し)は**いずれも L0 の再実装に着地する**。現在の L0 は Windows の印刷スタックに処理を委ねる方式であり、委ねた時点で制御と応答を手放している。これら 3 件は手放した部分を握り直す話であるため、同一箇所に帰着する。

送信専用の型で固めると、3 件のいずれか 1 件が顕在化しただけで L1 以上まで改修が波及する。

### 4.9 パス順序の決定に安定ソートを使う

`order` によるパスの並べ替えには、**安定ソート(同値要素の元の順序を保つソート)を使う。**

§4.3 の tie-break は「パレット定義ファイル内の記述順」であり、これは安定ソートによってのみ成立する。

**言語ごとの落とし穴:**

| 言語 | 関数 | 安定性 |
|---|---|---|
| Python | `sorted()` / `list.sort()` | **安定**(仕様で保証) |
| C# | `List<T>.Sort()` / `Array.Sort()` | **不安定**。使用禁止 |
| C# | LINQ の `OrderBy()` | **安定** |

**この差は §4.7 が想定した種類の事故そのものである。** 両実装を素直に書くと、`ref/`(Python)と `src/`(C#)で**メタリックを複数使ったときだけ、非決定的に**パス順序が食い違う。プレーン同士が重ならないため刷り上がりは変わらないが、**golden とのバイト列比較が不定になり、三段検証(§9.2)の前提が崩れる。**

**実装時の必須確認:** C# 側で `List<T>.Sort()` を使っていないこと。レビュー時に必ず見る。

## §5 機種プロファイル

### 5.1 スキーマ

```yaml
model: MD-5500
paper_table: 5000-series   # papers/{値}.yaml を読む。§5.5 参照
resolutions:
  - { dpi_x: 600,  dpi_y: 600,  default: true }
  - { dpi_x: 1200, dpi_y: 600 }
lf_correction: null      # 実測で埋める。§10 参照
max_width_dots: null     # 未確定
supports_opaque_white: true
```

### 5.2 未確定事項

`lf_correction` および `max_width_dots` は実測待ち。**推測値で埋めない。** 未確定のまま `null` を維持し、参照時は明示的にエラーとする。

### 5.3 接続方式

**Phase 3 が成立するまで、両機種とも USB-パラレル変換ケーブル経由で統一する。**

MD-5500 は本体に USB ポートを持つが、既存の実装で使用された実績がない。経路を 1 本に固定することで、Phase 1 の関門(§11.2)における原因の切り分けを容易にする。

USB 直結対応は保留であり、却下ではない。§11.3 を参照。

### 5.4 双方向通信

ALPS プリンタは仮想 LPT ポート経由で双方向通信を行う設計である。変換ケーブルが双方向に対応していない場合、単方向設定が必要になる。

**一次情報による確定事項(§13.3):** 公式ドライバは双方向通信で**装填済みカートリッジを検出**し、使用可能なものだけを選択肢に表示していた。双方向通信ができない場合は、**使用可能な全カートリッジを表示するフォールバックが用意されていた。**

**これは重要な朗報である。** 単方向でも印刷そのものは成立する設計になっていた。双方向はカートリッジ検出と状態取得のための機能であり、印刷の必須条件ではない。

**残る未確定:** エラー状態の読み出し(§11.4)は双方向を要する。カートリッジ自動検出も同様。

### 5.5 ppmtomd 由来の参考値(実機未確認)

ppmtomd 1.6 のソースに定義された 5000 系(MD-5000 / MD-5500 / DP-5000 共通)の論理ページ幅。600dpi 基準、1200dpi 時は倍、300dpi 時は半分(ppmtomd.c:70-81, 1903-1912)。

| 用紙 | 幅(600dpi 基準ドット) |
|---|---|
| A4 | 4800 |
| Letter / Legal | 4940 |

**全 8 種類の用紙(custom / executive / letter / legal / a4 / b5 / postcard / dyesublabel)の寸法・余白・用紙サイズコードは `papers/5000-series.yaml` に記録した。** 本節はその要点のみを示す。

**用紙表を機種プロファイルから分離する理由。** ppmtomd は用紙寸法テーブルを**機種系列ごとに 2 つ**持つ(5000 系と pre5000 系)。MD-5000 と MD-5500 は同一の表を共有するため、機種プロファイルに直接書くと同じ内容が 2 ファイルに重複し、片方だけ更新する事故が起きうる。`profiles/*.yaml` の `paper_table` が `papers/{値}.yaml` を参照する形にしている(D-014)。

**系列間の差の実例:** letter / legal の幅は 5000 系が 4940、pre5000 系が 4800。postcard / dyesublabel は上余白も異なる(71 対 284)。

#### 5.5.1 余白と位置合わせの罠(実測 2026-07-28)

用紙表の `left_margin` / `top_margin` は**印刷できない領域**であり、位置合わせでは指定シフトからこの値を引く(ppmtomd の `-autoshift` 相当、ppmtomd.c:1914-1928)。

**引いた結果が負になると、画像データ側を削る経路に入る。** ppmtomd はこのときコマンドを出さず、ラスタの先頭を捨てる(ppmtomd.c:2659)。**画像がその分の行数を持たないとエラーで停止する。** A4 の上余白は 284 ドットなので、120 行の画像に `-autoshift` を単独指定すると `Unexpected EOF reading row of PPM image` で落ちる(実測)。

**実装上の扱い:** `ref/` は負のシフトを未実装とし、渡されたら明示的に停止する。黙って誤った位置に刷るより落ちるほうが安全である(§4.6 の精神と同じ)。負の経路が必要になるのは、用紙の印刷可能領域より外側へ画像を寄せたい場合に限られる。

**シフト量の単位は 1/600 インチで、解像度設定に依存しない。** 内部で出力解像度に換算され、300dpi は半分、1200dpi は x 方向のみ 2 倍になる(ppmtomd.c:1920-1921)。

実装上の上限マクロは `PCL_MAXWIDTH=6000` だが、コメントに「実際の最大は 4800。超過分はプリンタが捨てる」とある(ppmtomd.c:1083-1086)。

**この値をもって機種プロファイルの `max_width_dots` を埋めることはまだしない。** §5.2 の null 維持ルールどおり、Phase 1 以降の実機挙動確認を経て採用する。ppmtomd は両機種を同一扱いしており、機種別の値はこのソースからは得られない。

### 5.6 コマンド体系の系譜

**ベースは HP PCL 系であり、Epson ESC/P 系ではない。**

**根拠:**

- ppmtomd 1.6 の解像度指定コマンドは `\033*t{res}R`(ppmtomd.c:288-289, 2489)。`ESC * t # R` は **PCL のラスタ解像度指定コマンド**である。PCL データストリームを解析した実例でも、同形式が解像度指定として現れる
- ppmtomd の論理ページ幅の上限マクロは `PCL_MAXWIDTH` と命名されている(ppmtomd.c:1083-1086)。**実装者自身が PCL と認識している**

**ALPS 独自拡張が併存する。** 色選択コマンド `\033\032{code}...r`(§6.5)は標準 PCL に存在しない。**PCL を土台に、ALPS が特色・カートリッジ制御を拡張した構造**と理解するのが正確。

**実務上の意味:**

- ラスタ転送・解像度・カーソル移動など PCL 由来の部分は、**公開されている PCL リファレンスが読める**
- 特色・カートリッジ・重ね刷りなど独自拡張の部分は、**ppmtomd が唯一の手がかり**である

**注意:** 「Epson ESC/P ベース」とする外部情報が存在するが誤りである(§0.1 判定実例 2)。この誤りを採ると、独自拡張部分を ESC/P リファレンスで解こうとして作業が空転する。

## §6 パレット定義

### 6.1 スキーマ

`magic_rgb` は**公式マニュアル記載の値**である(§13.3)。推測値ではない。

```yaml
inks:
  - name: white
    label: ホワイト
    magic_rgb: [230, 230, 230]
    printer_code: 0x0B
    tolerance: 8
    order: 10
    auto_undercoat: true
    passes: 2

  - name: metallic_gold
    label: メタリックゴールド
    magic_rgb: [225, 160, 0]
    printer_code: 0x04
    tolerance: 12
    order: 50

  - name: metallic_silver
    label: メタリックシルバー
    magic_rgb: [189, 193, 197]
    printer_code: 0x07
    tolerance: 12
    order: 50

  - name: metallic_magenta
    label: メタリックマゼンタ
    magic_rgb: [163, 36, 115]
    printer_code: 0x05
    tolerance: 12
    order: 50

  - name: metallic_cyan
    label: メタリックシアン
    magic_rgb: [0, 176, 201]
    printer_code: 0x06
    tolerance: 12
    order: 50

  - name: black
    label: ブラック
    magic_rgb: [0, 0, 0]
    printer_code: 0x00
    tolerance: 8
    order: 90
```

**`order` は昇順に実行され、先に刷ったものが下の層になる(§4.3)。** 白の下地が最小値、最後に見せたいものが最大値。

**`passes` の既定値は 1。** 白の 2 は暫定値であり、必要な回数は媒体と隠蔽力の要求で変わる。実測で決める(§10.5)。

**注意:** 白の指定色は純白ではなく明るいグレー(230,230,230)である。純白 255,255,255 は「印刷しない領域」と区別する必要があるため、この設計は妥当。**実装時に 255 と 230 を混同しないこと。**

**銀(189,193,197)と白(230,230,230)は近い。** `tolerance` を大きく取ると誤判定する。両方を同時に使う場合は特に注意。


### 6.2 各フィールドの意味

| フィールド | 意味 |
|---|---|
| `name` | 内部識別子。ASCII 小文字とアンダースコアのみ |
| `label` | UI 表示名。交換指示に使う |
| `magic_rgb` | このインクに予約する RGB 値 |
| `tolerance` | 近傍マッチングの許容誤差。§6.3 参照 |
| `printer_code` | 色選択コマンド `\033\032{code}...r` に載せるコードバイト。§6.5 参照 |
| `order` | パス実行順。昇順。**小さいほど下の層**。§4.3 参照 |
| `passes` | 同一プレーンを刷る回数。既定 1。隠蔽力を上げる重ね刷りに使う |
| `auto_undercoat` | true の場合、他の全インクが乗る画素の和集合をプレーンとする。下地として最初に刷られる |

### 6.3 tolerance が必要な理由

PostScript ドライバがカラーマネジメントを適用すると、原稿で指定した RGB 値がそのまま届かない可能性がある。完全一致では取りこぼす。

**対策は二段構え。** PPD 側でカラーマネジメントを無効化し、かつ変換器側で許容誤差付きの近傍マッチングを行う。

`tolerance` の適切な値は実測で決める。**初期値は暫定であり、根拠がない。**

#### 6.3.1 方式の妥当性(一次情報による裏付け)

**マジックカラー方式は、公式ドライバが採用していた方式と一致する。**

公式マニュアルは、メタリック & CMYK 同時印刷において、**領域の色構成によって特色部分とフルカラー部分を判別する**と説明している。各領域に適切な色を割り当てる必要があり、色構成を正確に指定できるアプリケーションで使用する前提とされている(§13.2)。

これは §6 の設計と発想が同一である。**推測から一次情報の裏付けを得た段階に格上げされた。**

さらに公式ドライバの Image Settings タブには **Color Match の None(カラーマッチングを行わない)** が用意されていた(§13.2)。色を無変換で通す経路が機器の設計として想定されていたことを示す。§6.3 の「カラーマネジメント無効化」は妥当な方針である。

**関連する注意点:** 同タブの Darker Black は、黒を 4 色すべてで生成する設定である。マジックカラー方式では純黒が別のインクへ分解されうるため、**この種の設定は必ず無効側に倒す。**

### 6.4 ページ分割方式(逃げ道)

マジックカラー方式が実測で機能しない場合に切り替える代替方式。1 ページ = 1 インクプレーンとし、ページ番号とインクの対応を PPD オプションまたは設定ファイルで指定する。

**両方式は L2 の入口の解釈が異なるだけで、それ以降は共通。** 内部表現(インク名 → 1bit プレーン)は同一である。

### 6.5 プリンタ側の色識別とサードパーティインクへのバッファ

ppmtomd 1.6 の読解(`docs/research/ppmtomd-survey.md`)により、ホスト → プリンタのインク指定は 2 層あると判明した。

1. **色選択コマンドのコードバイト**(プレーン送出前の `\033\032{code}...r`)
2. **カートリッジバーコード値**(ジョブ冒頭で使用カートリッジ一覧として送出)

「インクが何か」はこの 2 値で決まる。したがって §6.1 のスキーマは、**プリンタへ送る値を外部定義するフィールド**を持つ必要がある。これが無いとコード内対応表への依存が残り、§4.5(ハードコード禁止)の趣旨が損なわれる。

**`printer_code` は確定した(2026-07-28)。** 値は golden のバイト列から直接読み取った実測値であり、推測ではない。

| インク | `printer_code` | 由来 |
|---|---|---|
| ブラック | 0x00 | g1 |
| シアン | 0x01 | g2 |
| マゼンタ | 0x02 | g2 |
| イエロー | 0x03 | g2 |
| メタリックゴールド | 0x04 | g7 |
| メタリックマゼンタ | 0x05 | g7 |
| メタリックシアン | 0x06 | g7 |
| メタリックシルバー | 0x07 | g7 |
| ホワイト | 0x0B | g3 |

`barcode` は**保留とする。** カートリッジバーコードはカセット系の転送モードでのみ送出され、本プロジェクトが使う転送モード(colourPlane)では使わない。必要になった時点で追加する。

**`magic_rgb` との役割の違いに注意。** `magic_rgb`(§6.1、公式マニュアル由来)は**アプリケーション側で置く色**であり、`printer_code` / `barcode` は**プリンタへ送る値**である。両者は独立した層に属し、混同してはならない。

**サードパーティ製特色インクへの方針:** 販売元との関わりは持たない前提とし、問い合わせに依存しない。設計側のバッファで吸収する。

- 純正いずれかの識別を流用したカートリッジ → 既存インク定義の別名(`name` / `label` と `magic_rgb` だけ違う行)で対応
- 独自識別のカートリッジ → `printer_code` / `barcode` を設定行に書くだけで対応(コード変更なし)

サードパーティ製インクは、`printer_code` に純正いずれかの値を書けば「そのインクのふり」で刷れる。独自の識別を持つ場合も、判明した値を設定行に書くだけで対応できる。

## §7 UI

### 7.1 印刷ダイアログ側

**自作しない。** PPD にオプションを宣言すると Windows が「詳細設定」内に描画する。

配置する項目:

- 解像度(600 / 1200x600)
- インク指定方式(マジックカラー / ページ分割)
- 白版モード(なし / 自動生成 / マジックカラー指定)
- カラーマネジメント無効化

### 7.2 トレイアプリ側

**唯一の自作 UI。** ユーザーセッションで常駐し、キューを監視する。

必須機能:

1. **インク割り当てプレビュー** — どの領域がどのインクに解釈されたかを刷る前に表示する
2. ジョブ内容の表示(パス数、使用インク、順序)
3. 印刷開始ボタン
4. パスごとの交換指示 — 次に必要なインクを `label` で明示する
5. 進捗表示
6. **プリンタ状態表示の枠** — 現時点では内容が空でよい。§11.4 が解決した際に流し込む。ユーザーセッション側で動作するため、エラー通知の表示先として構造上ここが唯一の候補となる

**プレビューは必須機能である。** マジックカラー方式は誤爆時にリボンと用紙を消費する。これらは代替入手が困難な消耗品であり、事前確認の欠如は許容できないコストを生む。

交換指示では、複数回の交換を伴う印刷で現在位置が分からなくなることを防ぐため、**全パス中の何番目かを常に表示する**。


### 8.1 `ref/` の位置づけ

**書き捨てではない。検証装置として恒久的に維持する。**

`ref/` が担当するのは L1 と L2 のコアのみ。画像を受け取り、インク別プレーンに分解し、MD コマンド列を出力する。ここまで。

`ref/` が担当しないもの:

- トレイアプリ
- PPD 解釈
- キュー管理
- ポートモニタ連携
- プリンタへの実送信

**したがって `ref/` は機能追加に追従しない。** 更新するのは MD コマンド言語の仕様理解が変わったときのみ。それは稀にしか起きず、起きたときは重要な発見である。

### 8.2 ppmtomd の扱い

ppmtomd 本体はリポジトリに含めない。他者の GPL コードであり、配布の責務を負わない。

**その出力である golden バイナリは含める。** これは事実の記録であり、検証の基準となる。

## §9 テスト戦略

### 9.1 三段構え

```
ppmtomd(C言語 / 20年の実績)
  └→ tests/golden/*.bin
        ├→ ref/  が一致するか
        └→ src/  が一致するか
```

### 9.2 判定と切り分け

| src/ | ref/ | 判定 |
|---|---|---|
| golden と一致 | 一致 | 正常 |
| 不一致 | 一致 | C# の移植バグ |
| 不一致 | 不一致 | 仕様理解の誤り |
| 一致 | 不一致 | Python 側のバグ。または golden の前提条件の取り違え |

### 9.3 golden の採取対象

最低限、以下の組み合わせを採取する。

- ベタ 1 色(黒)
- ベタ 2 色
- 白版を含む多層
- **メタリック複数色(`order` 同値のパスが 2 本以上生じるケース)** — §4.9 の検証に必須
- 解像度違い(600 / 1200x600)
- 機種違い(MD-5000 / MD-5500)

**メタリック複数色のケースは優先度が高い。** §4.9 の安定ソート問題は、この組み合わせでしか顕在化しない。これが golden に無いと、`ref/` と `src/` の不一致が Phase 3 まで発見されない。

**実機カートリッジの有無に依存しない。** golden は ppmtomd で生成するため、メタリックカートリッジを所持していなくても**バイト列の一致検証は完全に実施できる。** 実機での刷り上がり確認のみが Phase 3 以降に持ち越される(§9.5)。

**機種差の特定は golden 同士の差分で行う。** 同一画像を機種指定だけ変えて生成し、バイナリ差分を取る。仕様書を探すより確実で速い。

### 9.3.1 OEM 系統を情報源に含める

ALPS はマイクロドライ機構を他社へ OEM 供給しており、**同一プロトコル圏に複数のブランドが存在する。**

- Citizen Printiva 系(600C / 700C / 1700C など)
- Oki DP 系

ppmtomd がこれらを同一ドライバでサポートしていることが、プロトコル共通性の裏付けとなる。また Printiva 向けの旧ドライバのファイル名に `alps` の文字列が含まれることも、系譜を示す傍証である。

**活用方針:** 仕様の裏取りや golden の採取元として、ALPS 単体で探すより広い範囲を参照できる。ALPS 名義で見つからない資料が Printiva / Oki 名義で残っている可能性がある。

**棄却した情報(2026-07-27):** 「Citizen が Vista / Windows 7 向けの 64bit ドライバを公開しており、ALPS 機に転用できる」との情報を検討し、採用しなかった。

| 主張 | 判定 |
|---|---|
| 64bit の**カーネルモード**印刷ドライバとして動作し安定する | **成立しない。** Windows のプリンタドライバはユーザーモード。カーネルモード印刷ドライバは Vista で非推奨化され、以降はインストール自体が不可 |
| Citizen が 64bit ドライバを公開していた | **裏付けなし。** アーカイブに残るのは Windows 3.1/95/98/Me 版と NT4 版のみ。Citizen Systems の現行サポート対象に Printiva は含まれない。64bit 版を掲げるのは自動生成型のドライバ配布サイトのみ |
| INF の VID/PID 書き換えで転用可能 | **二重に不整合。** INF 改変はパッケージ署名を破壊し 64bit Windows では導入できない。また VID/PID は USB の識別子であり、パラレル接続の本機と対象が異なる |
| 界隈で語り継がれた既知の手法 | **反証。** 事実であればコミュニティ製ユーティリティを新規開発する動機が消える。当該ユーティリティは複数の技術者により開発され、ALPS 機の修理・インク販売を業とする事業者が協力している。より簡便な解が存在したとは考えにくい |

**なお仮に実在したとしても本プロジェクトの要件を満たさない。** 当該情報自身が「特色白・金・銀の制御は困難」としており、特色制御こそが本プロジェクトの目的である。

### 9.4 実機テストの段階

| 段階 | 内容 | 実機リスク |
|---|---|---|
| Phase 0 | 環境調査。ポート一覧と変換ケーブルのデバイス ID を取得するのみ | なし |
| Phase 1 | 5mm 角のベタ 1 色を 1 枚 | 最小 |
| Phase 2 | 仮想プリンタ経由でメモ帳から印刷 | 小 |
| Phase 3 | 白版を含むフルパス | 中 |
| Phase 4 | USB 直結対応(§11.3)。実施は Phase 3 成立後 | 未定 |

**Phase 1 の判定は二値でなければならない。** 「出た」か「出ない」か。曖昧な結果を最初に持ち込まない。

**Phase 1 はプロジェクトの成否を決める関門である。** §11.2 のタイミングリスクがここで判明する。Phase 1 が成立するまで、UI・トレイアプリ・PPD の作り込みに着手しない。

**外部の協力者への配布は、作者の環境で Phase 3 が成立した後に限る。** 基準線のない状態で配ると、原因の切り分けが不可能になる。

### 9.5 実機検証の到達範囲

**バイト列の検証と実機の刷り上がり確認は、到達範囲が異なる。** これを混同しないこと。

| 検証内容 | 手段 | 必要な物 |
|---|---|---|
| バイト列が正しいか | golden との比較 | ppmtomd のみ。**実機・カートリッジ不要** |
| 実際に刷れるか | Phase 1–3 | 実機 + 該当カートリッジ + 用紙 |

**保有していないカートリッジの機能も、バイト列レベルでは完全に検証できる。** メタリック 4 色、Finish、VPhoto Primer などがこれに当たる。

**現時点の未確保:** メタリック系カートリッジ。入手可能性は不明だが、確保できない場合でも以下の方針とする。

- golden による検証は実施する(§9.3)

### 11.1 2400dpi について【解決済み 2026-07-27】

**ppmtomd 1.6 のソース読解とマニュアルの記述が一致し、解決した。**

**ソース側の証拠:** 解像度指定コマンド `\033*t{res}R` の取りうる値は `res300=0x02 / res600=0x03 / res1200=0x04` の 3 値のみで、2400 に対応するコードは存在しない(ppmtomd.c:288-289, 2489)。man ページは VPhoto を「可変ドット、誤解を招く形で 2400dpi と呼ばれる」印字と明記している(ppmtomd.man:481-483)。

**マニュアル側の裏付け:** 公式マニュアルの Print Quality は、Super が 16 階調・2400dpi・可変ドット、Fine が 4 階調・2400dpi・可変ドット、Standard が 600dpi と記載する(§13.3)。2400dpi は**可変ドットを用いる VPhoto 系モードに紐付く表記**であり、走査解像度ではない。

**二つの独立した情報源が同じ結論を示している。** カタログの 2400dpi は俗称である。

**確定方針:** 1200x600 を上限として実装する。VPhoto(可変ドット)は写真・昇華用途の機能であり、1bit プレーン前提(§4.2)の本用途では対象外。詳細は `docs/research/ppmtomd-survey.md` を参照。

**用途上の妥当性:** 1/12 のアイデカールにおいて、白目の幅を 5mm とすると 600dpi で約 118 ドット、1200dpi で約 236 ドット。階調は §4.2 により 1bit であるため、解像度が寄与するのは輪郭の滑らかさのみ。1200x600 で実用上十分と判断する。

### 11.2 タイミングに関する既知のリスク

**これは本プロジェクトで最も重大な未確定リスクである。**

公式ドライバは ALPS 専用の仮想 LPT ポートを介して双方向通信を行う。専用ポートを実装しているという事実は、標準のポート経由では満たせない要件が存在した可能性を示唆する。

**懸念:** プロトコルが厳しいタイミング要求を持つ場合、スプーラを経由しバッファリングされる本構成では要求を満たせない可能性がある。これは実装の巧拙ではなく Windows 印刷スタックの構造的性質に起因するため、回避が困難である。

**判明時期:** Phase 1(5mm 角のベタ 1 色を 1 枚)で判明する。この試験には経路全体のタイミング検証が含まれる。

**設計上の位置づけ:** 本リスクが顕在化した場合、仮想プリンタ方式そのものが成立しない。したがって Phase 1 は単なる動作確認ではなく、**プロジェクトの成否を決める関門**として扱う。Phase 1 以前に UI やトレイアプリの作り込みを進めない。

**回避策の候補(顕在化した場合のみ検討):**

- トレイアプリ側でバイト列を一括保持し、送出のみ連続実行する(既に §3.5 の二段構成でこの性質を持つ)
- 送出をリアルタイム優先度のスレッドで行う
- それでも不足する場合、方式の再検討が必要になる

### 11.3 MD-5500 の USB 直結対応(Phase 4)

**対応する意思はある。実装時期を Phase 3 成立後に置く。**

#### 状況

MD-5500 は本体に USB ポートを持つが、既知の実装はいずれもこれを使用していない。コミュニティ製ユーティリティは MD-5500 を含む全機種で USB-パラレル変換ケーブル経由とし、USB 直結を明示的に非対応としている。

**この理由が判明していないため、難易度を見積もれない。** 理由の候補:

1. 技術的な壁。ベンダ独自プロトコルで、公式ドライバの解析を要する
2. 実利がない。全機種対応が目的なら経路を統一するほうが保守が容易
3. 単に不要だった。既存ユーザーは変換ケーブルを所持している

**2 が最も蓋然性が高いと推測するが、1 を排除する材料がない。**

#### 難易度の二分岐

| ケース | 条件 | 影響 |
|---|---|---|
| 楽 | USB Printer Class 準拠。`usbprint.sys` が掴み `USB001` として見える | L0 の送出方法は現行とほぼ同一。対応は軽微 |
| 重 | ベンダ独自インターフェース | WinUSB / libusb でエンドポイントに直接書き込む。**L0 に別実装が生える**。Generic / Text Only 経由の出口が使えない |

#### 判定方法

実機の USB ポートを PC に接続し、デバイスマネージャで以下を確認する。**所要時間は数分、実機リスクなし。**

- プリンタとして認識されるか、不明なデバイスになるか
- ハードウェア ID(`USB\VID_xxxx&PID_xxxx`)
- デバイスクラス(Printer / ベンダ固有)

#### 実装時期を Phase 3 以降とする理由

経路が 2 本ある状態で Phase 1 を実施すると、失敗時の原因候補が倍になる。§11.2 のタイミングリスクを検証する段階では、**経路は 1 本でなければならない。**

パラレル経路で確実に印刷できる基準線を確立してから、USB を第二の経路として追加する。この順序を崩さない。

#### 設計上の備え

L0 は将来 2 系統の送出方法を持ちうる。§4.8 に従い、現時点で分岐を実装しないが、インターフェースを送出方式に依存した形に固めない。

### 11.4 エラー状態の読み出し(Phase 4 以降)

**公式ドライバが実現していた機能であり、対応する意思はある。**

#### 状況

本体前面の警告ランプは異常の発生のみを示し、原因(用紙切れ / リボン切れ / カバー開放 等)を区別しない。公式ドライバが原因を提示できていたことは、**プリンタへ問い合わせて応答を受け取っていたこと**を意味する。

#### 成立に必要な条件

| 条件 | 状態 |
|---|---|
| 双方向対応の変換ケーブル | 未確認(§5.4 / §10.1) |
| 双方向でポートを開く経路 | 現行 L0 では不可(§11.0) |
| エラーコードの解読 | 手がかりあり。下記参照 |

**単方向ケーブルの場合、機能は物理的に成立しない。** ケーブルの実測(§10.1)が前提条件となる。

#### 解読の手がかり

ppmtomd の作者が双方向でのステータス監視に取り組んでおり、監視用スクリプトを公開している。ドキュメントは付属しないが、プロトコルを扱う箇所は読解可能であると本人が記している。**エラーコードの意味を特定する第一の情報源はここ。**

#### 現時点で行うこと

1. **L0 を送信専用に固めない**(§4.8)
2. **トレイアプリに状態表示の枠を確保する**(§7.2-6)。内容は空でよい
3. **代替手段を機能させておく**

#### 代替手段(双方向が使えない場合)

§4.6 のバイト列ダンプにより、**どのジョブのどのパスまで送出したかは特定できる。** 異常の原因は判明しないが、発生位置は分かる。

完全な代替にはならないが、**何も分からない状態は回避できる。** 双方向が最後まで確保できない場合でも、この水準は維持する。

### 12.1 ライセンス

GPL-3.0。

**選定理由:**

- 参照する ppmtomd / gdevmd2k が GPL 系であり、「参照」と「移植」の境界が曖昧になりうる。最初から GPL とすることでこの論点が消滅する

- 著作権表示の保持義務が、リブランドに対する法的根拠となる
- クローズド化を構造的に禁止できる

### 12.2 同梱しないもの

以下は同梱せず、インストール手順で案内するのみとする。**他者の GPL / AGPL コードを配布する責務を負わない。**

- Microsoft PostScript Printer Driver V3(Windows 同梱品。OS 内のファイルを参照する)
- ppmtomd(GPL)

**特に Ghostscript のバンドルは行わない。** AGPL の解釈上、同梱・統合は商用ライセンスの要求対象となりうる。

### 12.3 解析対策

**行わない。**

Python は PyInstaller で実行ファイル化しても `.pyc` の抽出と逆コンパイルで元のソースに近いものが復元される。C# の IL も同様に読める。これは既知の性質であり、難読化なしには回避できない。

一方で、本プロジェクトに隠すべき非公開情報は存在しない。MD のコマンド言語は 20 年前から GPL で公開され、仮想プリンタの構成も既存プロジェクトが公開している。パレット定義は平文で置く前提の設定ファイルである。

全体を GPL で公開する以上、解析対策には意味がない。むしろ `ref/` の存在により第三者が実装の正しさを検証できることは、**代替入手困難な機材を扱うソフトウェアにおける信頼性そのもの**である。

難読化は自身のデバッグを著しく困難にするため、導入しない。

### 12.4 公開と配布の順序

**公開が先、配布が後。**

GitHub での公開により、第三者が管理する改竄不能なタイムスタンプと開発履歴が残る。非公開のまま少数に配布する期間は、先行を証明する手段が自己申告のみとなるため設けない。

### 12.5 由来の明示

以下の箇所に作者とリポジトリを明示する。GPL の表記保持義務が及ぶ範囲を明確にするため。

- 全ソースファイル先頭の著作権行
- `--version` の出力
- ダンプしたバイト列のログヘッダ
- README

**厳密一致は要求されていない。** マニュアルは「刷りたい特色に似た色を選べ」と説明し、色数の少ないアプリでは近い色で代用できるとしている。ただしその場合はテスト印刷で確認するよう求めている。**§6.3 の許容誤差付きマッチングは、公式の運用と整合する。**

**制約:**

- 同時に使用できる特色は最大 6 色(または 5 特色 + 黒)
- Multiple Inks 印刷では、装填できるカートリッジは**最大 4 本**
- **複数特色を同時に使う場合、中間階調は表現できない。** 単一特色のみならグレースケール表現が可能
- カートリッジホルダーへの**装填順序は問わない**
- 色を指定しても、対応するカートリッジをドライバ側で選択していなければ印刷されない
- White ink cartridge の部品番号: 106050-00

**双方向通信について:** 双方向が使えない場合、ドライバは使用可能な全カートリッジを表示する。→ §5.4
