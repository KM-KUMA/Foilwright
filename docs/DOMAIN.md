## §1 プロジェクト概要

### 1.1 解決する問題

ALPS MD シリーズの公式 Windows ドライバは 32bit 版のみで、64bit Windows では動作しない。Windows のプリンタドライバはユーザーモードで動作するが、64bit の spooler プロセスは 32bit DLL をロードできないため、これは原理的な制約であり、パッチや設定では回避できない。

既存の回避策は 2 つ。32bit 仮想マシンの運用、またはコミュニティ製のスタンドアロンユーティリティ。前者は運用が重く、後者はアプリの印刷ダイアログから使えない。

Foilwright は、**任意のアプリケーションの印刷ダイアログから通常のプリンタとして選択でき、白・金銀を含む特色印刷が可能な** 64bit ネイティブの印刷経路を提供する。

#### 公式ドライバでも解決できなかった問題

64bit 対応とは別に、**公式ドライバの構造上どうしても解決できない制約が 1 つある。**

特色ホワイトはメタリック & CMYK 同時印刷に使用できない(§13.3)。したがって白を使う多色刷りは、**白のパスを別ジョブとして送らざるを得ない。** ジョブが終わればプリンタは用紙を排出し、一度ローラーから離れた用紙は見当を再現できない。

実測でも確認されている(§10.6)。B5 では用紙が長く後端がローラーに残ったため続行できたが、**はがき大では完全に排出され、続きが刷れなかった。**

**全パスを 1 ジョブとして構成できれば、この制約は消える。** 用紙長にも依存しなくなる。これは 64bit 対応の副産物ではなく、**32bit 環境でも達成できなかった機能である。**(§11.5 / §14.1)

### 1.2 前提となる利用者像

作者自身と、ALPS MD プリンタを所有する少数の知人。模型・フィギュア界隈でのウォータースライドデカール作成が主用途。想定台数は 10 台未満。

**エンタープライズ品質のサポートは提供しない。** 動作確認済みの構成以外は保証しない。この方針は README に明記する。

### 1.3 やらないこと

- 昇華モード(ダイサブ)への対応
- Windows 以外の OS
- v4 プリンタドライバ形式(§3.2 参照)
- 難読化・解析対策(§12.3 参照)

なお、MD-5500 の USB 直結対応は**やらないことではなく保留である**。§11.3 を参照。

## §2 用語定義

| 用語 | 定義 |
|---|---|
| **インク** | 物理カートリッジ 1 本に対応する色。CMYK 各色、特色白、メタリック金銀など |
| **プレーン** | 1 インク分の 1bit ラスタ。同サイズ・同解像度で複数枚が重なって 1 枚の成果物になる |
| **パス** | プリンタが用紙を 1 回通す動作。原則 1 パス = 1 インク |
| **マジックカラー** | 特定の RGB 値をインクに予約する方式。原稿中の該当画素がそのインクのプレーンに振り分けられる |
| **ページ分割方式** | 1 ページ = 1 インクプレーンとする代替方式。マジックカラーが機能しない場合の逃げ道 |
| **auto_undercoat** | インクが乗る全画素の和集合として自動生成されるプレーン。白の下地に使い、**最初に刷られる**。旧称 `auto_backing`(裏打ちと誤解されるため改名) |
| **golden** | ppmtomd が生成した既知正解のバイト列。実装の正しさを判定する基準 |
| **LF 補正値** | パス間の紙送り誤差を補正する値。機体固有・実測値 |
| **セッション 0** | Windows のサービス用セッション。spooler および変換器が動作する。ユーザーのデスクトップから隔離されており、**UI を表示できない** |

## §3 システム構成

### 3.1 四層構造

```
L0  transport   物理経路への書き込み
L1  emitter     MD コマンド生成 + 機種プロファイル
L2  raster      画像 → インク別 1bit プレーン
L3  interface   PPD / ポートモニタ連携 / トレイアプリ
```

**依存方向は L3 → L2 → L1 → L0 の一方向のみ。** 逆流を禁止する。特に L0 と L2 は機種を一切知らない。機種差は L1 のプロファイルに閉じる。

### 3.2 経路全体

```
アプリケーション(Photoshop / Illustrator / ペイント等)
  ↓ 印刷ダイアログでプリンタを選択
Microsoft PostScript Printer Driver V3(in-box。自作 PPD は使えない。D-022)
  ↓ PostScript
Windows スプーラ
  ↓ Local Port(in-box)がポート名の名前付きパイプへ書き込む(D-023)
Foilwright トレイアプリ(ユーザーセッション / UI を持つ。D-024)
  ↓ \\.\pipe\foilwright で受信
  ↓ Ghostscript で PPM へラスタライズ(§3.6 / D-021)
  ↓ L2: インク別 1bit プレーンへ分解
  ↓ L1: MD コマンドのバイト列を生成
  ↓ L0: usbprint.sys のデバイスインターフェースへ直接
  ↓     CreateFile + WriteFile / ReadFile(D-020 / §15)
MD-5500(USB 直結)
```

**この経路は 2026-08-04 に 3 度書き換わった。** いずれも実測で前提が崩れたことによる。

1. 最終段の「Generic / Text Only プリンタ → WritePrinter(RAW) → USB-パラレル変換ケーブル」を破棄した。MD-5500 の USB リンクには ALPS 独自のパケット層があり、スプーラ経由で RAW を流す方式では原理的にその層を挟めない(§15 / D-018)。現在の L0 はデバイスインターフェースを直接開く方式で、実機印刷まで確認済み(D-020 / §15.6)
2. **自作 PPD を外した。** 現行 Windows は第三者製プリンタドライバパッケージの導入を拒否する(§3.5.1 / D-022)。設定項目はトレイアプリへ移設した(§7)
3. **ポートモニタ mfilemon を外した。** 標準の Local Port がポート名として名前付きパイプを受け付けるため、第三者製の印刷コンポーネントを一切使わずにジョブを受け取れる(D-023)。**セッション 0 の制約も同時に消えたため、変換器とトレイアプリを分ける理由が無くなり単体構成にした**(D-024)

**先行機は MD-5000(パラレル + 変換ケーブル)へ戻した(D-025)。** MD-5500 に給紙機構の異常が発生し、
復旧の見込みが立たなくなったため(§11.4)。L1 は両機種で golden がバイト完全一致するため、
プロファイルの差し替えだけで済む(§11 #3 / §4.4)。

**ただし L0 は分かれる。** USB リンクのパケット層(§15.2)は MD-5500 の USB ポート固有のものであり、
**パラレル経路には存在しないとみられる**【推測。実機で確認する】。根拠は ppmtomd がパラレル向けに
生の RGL をそのまま出力していることで、パケット層があるならその出力は成立しない。

| 経路 | 送出方式 | デバイスの VID |
|---|---|---|
| MD-5500 USB 直結 | パケット層あり(`05 ff` → `06` → `02 01 {len-1} {data}`) | `044E`(ALPS 自身) |
| MD-5000 + 変換ケーブル | **RGL を包まずそのまま送る** | `056E`(ケーブル側) |

**共通部分は再利用する** — デバイス探索・タイムアウト・ドレイン・応答の中身検査は方式に依存しない。

**7 月に MD-5000 で Phase 1 が成立しなかった件(§11.1.1)は再検証の対象である。** 当時は
「読み残しが滞留して会話がずれる」問題を知らなかった(§11.4 の訂正)。現在はドレインと
タイムアウトを実装済みのため、同じ構成でも結果が変わりうる。

### 3.3 なぜプリンタドライバを自作しないか

3 つの理由による。

1. **署名**。ドライバパッケージには署名が必要。自己署名で回避可能だが手間が増える
2. **Microsoft の方針**。サードパーティ製プリンタドライバは段階的に廃止されつつある。Microsoft 純正ドライバを使う本構成はこの影響を受けにくい
3. **不要**。PPD を差し替えれば、純正 PostScript ドライバのまま独自プリンタとして振る舞う

### 3.4 なぜ v3 形式か

v4 プリンタドライバは Microsoft 製以外のポートモニタを使用できない。当初は第三者製ポートモニタ(mfilemon)に依存する構成だったため v3 一択だった。

**D-023 で第三者製ポートモニタを使わなくなったため、この理由は失効した。**ただし結論は変わらない — 現行 Windows では、そもそも第三者製のプリンタドライバパッケージを v3 / v4 のいずれの形式でも導入できない(§3.5.1)。in-box の PostScript ドライバ(v3)を間借りする以外の選択肢が無い。

### 3.5 ~~なぜ二段構成(変換器 + トレイアプリ)か~~ → 単体構成へ変更(D-024)

**本節の理由は失効した。** 当初は「ポートモニタから起動されるプロセスはセッション 0 で
動作し、そこからダイアログを表示しても誰にも見えない」ため、UI を持つプロセスを
ユーザーセッション側へ分離する必要があった。

**D-023 で名前付きパイプ方式にしたことで、この制約が消えた。** パイプサーバは自分の
プロセスであり、最初からユーザーセッションで動かせる(スプーラは SYSTEM として動くが、
ユーザーセッションのプロセスが作ったパイプへ問題なく接続してくることを実測で確認)。

したがって変換器とトレイアプリを分ける理由が無くなり、**トレイアプリ単体構成へ変更した**
(D-024)。当初挙げていた副次的利点のうち「複数ジョブを溜めて同一インクのパスをまとめる」
は失われるが、キューフォルダの形式は同じであるため、必要になれば常駐サービスを後から
追加できる。

なお「印刷ダイアログを押した時点でアプリケーションが解放される」という利点は、
パイプがジョブを読み切った時点で成立するため維持される。

### 3.5.1 【重要】Windows 11 は第三者製プリンタドライバの導入を拒否する(2026-08-04 実測)

**§3.3 の前提が現行 Windows で崩れている。** 「PPD を差し替えれば純正 PostScript ドライバのまま独自プリンタとして振る舞う」は仕組みとしては正しいが、**その組み合わせを OS に登録する行為が『第三者製プリンタドライバパッケージの追加』とみなされ、拒否される。**

実測(Windows 11 25H2 / build 10.0.26200):

| 試したこと | 結果 |
|---|---|
| 未署名の INF + PPD を `pnputil` で追加 | **失敗**。`0xE000022F` — カタログが無く Code Integrity が強制されている |
| 自己署名(証明書を Root / TrustedPublisher に導入)して再試行 | **署名検証は通過**。`pnputil` はドライバストアへの登録に成功 |
| 登録済みパッケージを `Add-PrinterDriver` でプリンタドライバとして有効化 | **失敗**。**`0x80070BC6` = ERROR_PRINTER_DRIVER_BLOCKED** |
| in-box の PostScript ドライバ(`MS Publisher Color Printer`)を同じ手順で有効化 | **成功** |

**切り分けの結論:** 拒否されているのは署名でもパッケージの中身でもなく、**第三者製であること自体**。in-box ドライバは同じ v3 PostScript の仕組みで問題なく入る。`WindowsProtectedPrintMode` などの明示的なポリシー値は設定されておらず、**OS 既定の挙動**とみられる。解除できる設定は見つからなかった。

**含意:** 独自 PPD を配布物として同梱する構成(D-001 の実装経路)は、現行 Windows では成立しない。残る道は 2 つ。

1. **in-box の汎用 PostScript ドライバを間借りする。** 署名も登録も不要で今日確認済み。ただし独自 PPD を持てないため、§7.1 が印刷ダイアログへ載せる予定だった項目(インク指定方式・メディア種別・ハーフトーン・白版モード)は**トレイアプリ側の UI へ移す**必要がある
2. **Microsoft の認証署名(Partner Center 経由の attestation signing)を取得する。** 独自 PPD を維持できるが、EV 証明書と開発者アカウントの取得を伴う

**§3.3 の 3 番目の理由「不要。PPD を差し替えれば足りる」は、現行 OS では成立しない。** 本節が §3.3 に優先する。

### 3.5.2 経路の実証(2026-08-04 / D-022 の構成で成立)

**アプリケーションからインク別プレーンまでが実機環境で一気通貫した。**

```text
System.Drawing で厳密な RGB を描画
  → 仮想プリンタ "Foilwright MD-5500"(in-box の MS Publisher Color Printer)
  → PostScript(14.4KB)
  → Ghostscript -sDEVICE=ppmraw
  → PPM
  → ref/ の to_planes_magic
  → インク別 1bit プレーン
```

**マジックカラーは 1 ビットも変質しなかった。** パレットの 6 色(白 / 金 / 銀 / メタリックレッド / メタリックブルー / 黒)を厳密な RGB で描いて印刷し、出力を画素単位で数えた結果、**出現色は背景の白と期待した 6 色ちょうどで、中間色が 1 つも無かった**。

| 検証項目 | 結果 |
|---|---|
| Windows PostScript ドライバによる色変換 | **起きない**(6 色すべて完全一致) |
| アンチエイリアスによる混色 | **起きない**(描画側で平滑化を無効化) |
| L2 のプレーン分離 | 各パッチ 5184〜5256 ドット = 72dpi の 1 インチ角と一致 |
| `auto_undercoat`(白下地の自動生成) | **動作**。白 31176 ドット = 自分のパッチ + 他インク全画素の和集合 |

**これで D-021 が Phase 2 に持ち越した懸念(手前のドライバがカラーマネジメントを適用する可能性)は解消した。** §6.3 の対策のうち「PPD 側での無効化」は、独自 PPD を持たない D-022 の構成では実施できないが、**そもそも変質が起きないため不要**であることが実測で分かった。

**残る未実装:** 変換器(Ghostscript の呼び出しとプレーン生成を自動化する常駐処理)と、ポートモニタ(現在は固定ファイルへ書き出す開発用の代用)。トレイアプリからの送出は §15 で成立済み。

### 3.6 PostScript のラスタライズ(D-021)

**変換器は Ghostscript を子プロセスとして呼び、PostScript を PPM(P6)へ変換する。** Ghostscript は同梱せず、利用者が別途インストールする(§12.2)。L2 の入口が既に PPM であるため、golden による三段検証(§9.2)の資産がそのまま生きる。

**色の忠実性は実測で確認済み(2026-08-04 / Ghostscript 9.53.3)。** マジックカラー 6 色を PostScript に埋めて `-sDEVICE=ppmraw` でラスタライズしたところ、**72dpi / 600dpi のいずれでも全色がバイト単位で一致した**。マジックカラー方式は 1 の差でも誤爆するため、この確認は D-021 採否の急所だった。

```text
gswin64c -q -dNOPAUSE -dBATCH -dSAFER -sDEVICE=ppmraw -r600 -sOutputFile=out.ppm in.ps
```

**ただし色の変質リスクは手前に残る。** Ghostscript は値を変えないが、**その前段の Windows PostScript ドライバがカラーマネジメントを適用する可能性**は未検証である(§6.3 の懸念)。PPD 側での無効化と実測は Phase 2 で行う。

**実測値(A4 / 600dpi):** 出力は 4958 × 7017 画素・約 99.5MB、変換に約 2.2 秒。**変換器を「全体をメモリに載せる」前提で書くとジョブあたり 100MB 級を消費する**ため、行単位の処理を検討する。

#### 3.6.1 用紙全面から印字可能領域への切り出し(2026-08-04 確定)

**Ghostscript は用紙全面を描くが、プリンタが刷れるのは印字可能領域だけである。** この対応付けは L3 の責務であり、換算を L2 以降へ持ち込まない(§4.1)。

実測で数値が揃った(600dpi / A4):

| | 値 |
|---|---|
| Ghostscript の出力(用紙全面) | 4958 × 7017 ドット |
| 印字可能領域(`papers/5000-series.yaml` の a4) | width 4800 / length 6372 |
| 左余白 `left_margin` | 80(右余白は 78 になる) |
| 上余白 `top_margin` | 284(下余白は 361) |

**左右の余白がほぼ対称(80 と 78)であることが、この解釈の裏付けになる。**

**変換規則:** 全面ラスタから **左上 `(left_margin, top_margin)`、大きさ `(width, length)`** の矩形を切り出す。ラスタの原点は印字可能領域の原点に対応する(`make_golden.sh` の `-autoshift` が余白を引く挙動と整合)。

**切り出さないと 2 つの不具合が同時に起きる。** 横方向に 158 ドットはみ出し、かつ全体が右へ 3.4mm・下へ 12mm ずれる。

**実装上の注意:** A4 / 600dpi の PPM は約 99.5MB ある。**行単位で切り出すこと** — 全体を複製すると倍のメモリを消費する。
**位置確認ページで切り出しが裏付けられた(2026-08-19)。** MD-5000 に位置確認ページ(`tools/print-position-test.ps1` の出力を RGL 化したもの、黒 1 パス・10845 バイト)を送出し、印刷された。

**四隅の L 字マークの位置が期待値とおおむね一致した。** 左上の L 字は紙の左端から約 32.8mm・上端から約 31.8mm に出る計算で、実測もその通りだった。**§3.6.1 の換算規則(全面 4958x7017 から `(left_margin, top_margin)` = (80, 284) を起点に 4800x6372 を切り出す)が実機で成立している。**

**切り出しが効いていなければ右下へ約 3.4mm / 12mm ずれ、横方向は 158 ドットはみ出すはずだった。** そのいずれも起きていない。

### 3.7 ジョブを溜めてから送る構成がタイミングリスクを吸収する

**§11.2 のタイミング懸念は、当初の想定より小さい。** 当初の経路は「スプーラが RAW バイト列をプリンタへ流し続ける」形で、途中で途切れるとパスが破綻する懸念があった(§11 #7 / PROJECT.md の最重要リスク)。

現在の構成では、**トレイアプリがジョブを最後まで受け取って完成させてから、プリンタへ一括で送出する**(D-024 の単体構成 + D-020 の直接送出)。スプーラの都合とプリンタへの送出タイミングが**完全に分離される**。この性質は構成が単体か二段かに依存しない — 効いているのは「受信と送出を同時に行わない」ことである。

実測でも、1488 バイトのジョブは 0.01 秒、6515 バイトでも 0.02 秒で送出が完了しており(§15.4 / §15.5)、送出そのものが律速になる兆候はない。**「スプーラがジョブを欠落なく渡すか」は §3.5.2 で確認済み** — 名前付きパイプ経由で受け取った PostScript は、ファイルへ書き出した場合とバイト単位で同一の結果を与えた。**§11.2 のタイミング懸念はこれで解消したとみなす。**

## §4 不変条件

**以下は絶対保証である。破る変更は本書の更新を伴わなければならない。**

### 4.1 座標と単位

内部座標は **常にドット単位**。mm は L3 の入口(PPD 解釈)でのみ扱い、それ以降ドットに変換して持ち回る。

**根拠:** 解像度が機種・設定で変わるため、mm を持ち回ると変換が散らばり丸め誤差が蓄積する。

### 4.2 プレーンは 1bit

各インクプレーンは 1bit ラスタとする。ハーフトーン処理はソフトウェア側の責務。

**ハーフトーン方式は選択可能とする。** 既定は閾値二値化だが、ディザリングも実装対象である(§4.2.1)。

**根拠(一次情報):**

- 公式マニュアルは、**複数の特色を同時に使用する場合、中間階調は表現できない**と明記している。単一特色のみの場合はグレースケール表現が可能(§13.3)
- 可変ドットによる階調表現は VPhoto 系モードの機能であり、走査解像度とは別系統(§11.1)
- 本プロジェクトの主用途は白 + 色の複数特色印刷であり、上記制約に該当する

**注意:** 「マイクロドライは階調をまったく持たない」というのは**誤りである**。単一特色時のグレースケールと VPhoto の可変ドットが存在する。1bit を採る根拠は機構の限界ではなく、**複数特色使用時の制約と、本用途がそれに該当すること**にある。

**用途上の妥当性:** アイデカールはベタ塗りと線で構成され、階調表現をほぼ必要としない。ただし**階調が必要になる場面は確実に来る**という判断により、ディザリングを実装対象に含める(2026-07-28 方針変更)。当初「コマンド生成の検証段階で変数が増える」ことを理由に見送っていたが、その懸念は golden 12 種でコマンド生成の正しさが確定したことにより解消した。

#### 4.2.1 ハーフトーン方式の選択

ppmtomd が持つ 5 方式のうち、**実装対象は 3 つ**である。

| 方式 | ppmtomd 名 | 採否 | 理由 |
|---|---|---|---|
| 閾値二値化 | `None` | **採用**(既定) | 現行実装。ベタ塗り用途に最適 |
| ハーフトーン | `Halftone` | **採用** | man が「一般用途に推奨」と明記。クラスタードットの順序ディザ + スクリーン角度 |
| 粗いハーフトーン | `CoarseHalftone` | **採用** | 同方式のドットスクリーン版。通常の印刷物に近い見え方 |
| 誤差拡散 | `FloydSteinberg` | **不採用** | **ppmtomd 1.6 がクラッシュする**(下記) |
| 実験的セル | `Square` | **不採用** | RasterColour データモード専用。本プロジェクトは colourPlane を使う。man 自身が非推奨 |

**FloydSteinberg を採用しない理由(実測 2026-07-28):** ppmtomd 1.6 に `-dither FloydSteinberg` を指定すると `malloc(): corrupted top size` でメモリ破壊を起こし異常終了する(exit 134 / core dumped)。**golden を採取できないため、実装しても正しさを検証する手段がない**(§9)。man 自身も「原理的にマイクロドライ方式には向かない」と記しており、追う価値が薄い。

#### ディザ指定は色補正を巻き込む(重要)

**ppmtomd は `-dither` を `None` 以外にすると、色補正を機種に関係なく `Photo` に切り替える**(ppmtomd.c:1437-1441)。既定の `Plain` から勝手に変わる。

**これは写真用の色補正パイプライン全体を有効にする。** `photocolcor.c` に埋め込まれた 16×16×16×4 の較正テーブル(約 16,000 エントリの実測データ)を 64³×4 に補間展開し、`pow()` によるガンマテーブルを併用する。**ディザのパターンとは無関係の、別のサブシステムである。**

**Foilwright はこれに追従しない。** §6.3 / §6.3.1 のとおり色は無変換で通す方針であり、写真用の色再現は目的ではない。

**したがって golden は `-colourcorrection Plain` を明示して採取する。** 指定しないとディザの検証に色補正という別の変数が混入し、何を検証しているのか分からなくなる。実際、明示せずに採取した golden は `ref/` と一致せず、原因の特定に時間を要した(2026-07-28)。

**ディザ適用時は出力量が増える。** 中間調がドットパターンに展開されるため圧縮が効きにくくなる。実測では同一画像・同一色補正(`Plain`)で `None` 4919 バイトに対し `Halftone` 5879 バイト、`CoarseHalftone` 9417 バイト。品質の問題ではなく、送出データ量の話である。

### 4.3 パスとカートリッジの関係

**初版は 1 パス = 1 カートリッジで実装する。ただしこれは実装方針であり、機器の制約ではない。**

公式マニュアルによれば、機器はメタリック系と CMYK を同時に印刷する機能を持つ(§13.2)。したがって「複数インクを 1 パスで刷れない」は**誤りである**。

確定している制約:

- **白インクは、メタリック & CMYK 同時印刷に使用できない。** 白は単独パスとなる(一次情報。§13.2)

初版で同時印刷を実装しない理由は、コマンド生成の検証を単純に保つためである。単独パスの積み重ねで所望の結果が得られる以上、同時印刷は最適化であって要件ではない。

**パスの実行順序**はパレット定義の `order` の昇順とする。**`order` が同値の場合は、パレット定義ファイル内の記述順とする。**

同値を許す理由は、メタリック系のように**同格であることが設計情報として意味を持つ**インク群が存在するためである。同格なものに異なる `order` を振ると、その差に意味があるように見えてしまう。順序の決定性は実装規則(§4.9)で担保する。

**tie-break に `name` を使ってはならない。** インクを改名すると印刷順が変わり、また利用者が同格インク間の順序を制御する手段が改名しかなくなる。記述順であれば、行を入れ替えるだけで制御できる。

**順序の意味:先に刷ったものが下の層になる。** ウォータースライドデカールは刷った面を表として使うため、**表から見て奥にあるものを先に刷る**。したがって白の下地が最初、その上に色が乗る。

**根拠(実測 + 一次情報の一致):**

- 作者が 32bit 環境の公式ドライバで実作業していた際、**白を先に刷り、その上に色を重ねていた**(§10.5)
- 公式ドライバの Print Using における白の項目名は **White (Undercoat)** である(§13.3)。Undercoat は下塗りを意味し、その上に別の層が乗ることを前提とした語である。VPhoto Primer (Undercoat) も同様

**注意:** Back Print Film(裏面印刷フィルム)は透かして見る前提の媒体であり、順序が反転する。**ウォータースライドデカールとは別物であり、混同しないこと。**

**重ね刷り:** 白は隠蔽力を上げるため同一プレーンを複数回刷ることがある。パレット定義の `passes` で回数を指定する(§6.1)。


### 4.4 機種差はプロファイルに隔離

機種による分岐を L1 のプロファイル外に書かない。`if model == "MD-5500"` のような条件分岐がプロファイル定義の外に現れたら、それは設計違反である。

### 4.5 インク一覧をコードに埋めない

インクの定義は必ず外部ファイル(§6)から読む。列挙型やハードコードされた配列としてインク名をソースに書かない。

**根拠:** 将来サードパーティ製スポットカラーインクを追加する可能性がある。その際に設定行の追加のみで済む形を維持する。

### 4.6 生成バイト列は常にダンプ可能

変換器は、プリンタへ送出するバイト列をファイルに保存する機能を**常に持つ**。これは後付けできない要件である。

**根拠:** 遠隔地の利用者から「印刷できない」と報告された際、バイト列があれば原因の大半が特定できる。ログのない不具合報告は解析不能。

### 4.7 `ref/` と `src/` は異なる言語で維持する

参照実装(Python)と本番実装(C#)を同一言語に統一しない。

**根拠:** MD のコマンド言語には公開仕様書がなく、実装は推測に基づく。同一言語では同じ誤解を両方で踏む。型の扱いが異なる言語で二度書くことで、仕様理解の曖昧な箇所が挙動の差として顕在化する。

### 4.8 L0 を送信専用に固定しない

L0 のインターフェースは、将来 **read が生えうる前提**で設計する。

- ポート名、プリンタキュー名、接続方式を L1 以上に漏らさない
- L0 を「バイト列を送る関数」として型に固めない。送出方式を差し替え可能な抽象として扱う
- 現時点で read を実装しないが、追加時に L1 以上の変更を要する形にしない

**根拠:** §11.2(タイミング)、§11.3(USB 直結)、§11.4(エラー状態の読み出し)は**いずれも L0 の再実装に着地する**。現在の L0 は Windows の印刷スタックに処理を委ねる方式であり、委ねた時点で制御と応答を手放している。これら 3 件は手放した部分を握り直す話であるため、同一箇所に帰着する。

送信専用の型で固めると、3 件のいずれか 1 件が顕在化しただけで L1 以上まで改修が波及する。

### 4.9 パス順序の決定に安定ソートを使う

`order` によるパスの並べ替えには、**安定ソート(同値要素の元の順序を保つソート)を使う。**

§4.3 の tie-break は「パレット定義ファイル内の記述順」であり、これは安定ソートによってのみ成立する。

**言語ごとの落とし穴:**

| 言語 | 関数 | 安定性 |
|---|---|---|
| Python | `sorted()` / `list.sort()` | **安定**(仕様で保証) |
| C# | `List<T>.Sort()` / `Array.Sort()` | **不安定**。使用禁止 |
| C# | LINQ の `OrderBy()` | **安定** |

**この差は §4.7 が想定した種類の事故そのものである。** 両実装を素直に書くと、`ref/`(Python)と `src/`(C#)で**メタリックを複数使ったときだけ、非決定的に**パス順序が食い違う。プレーン同士が重ならないため刷り上がりは変わらないが、**golden とのバイト列比較が不定になり、三段検証(§9.2)の前提が崩れる。**

**実装時の必須確認:** C# 側で `List<T>.Sort()` を使っていないこと。レビュー時に必ず見る。

### 4.10 排出は最終パスの後に 1 回だけ

**用紙の排出コマンドは、ジョブ内の全パスが完了した後に 1 回だけ発行する。** パスごとに排出してはならない。

**根拠(実測。§10.6):** MD シリーズはローラーで用紙を保持したまま前後させ、同一の用紙にヘッドを複数回通すことで見当を合わせる。**排出して用紙がローラーから離れると、見当の再現は不可能になる。** 手で入れ直しても 0.1mm 級の精度は出ない。

**この不変条件は L1 のジョブ構成に対する制約である。** カートリッジ交換のためにパス間で待機する場合も、ジョブは終了させない。待機は §3.5 のトレイアプリが担い、L0 への送出はジョブ単位で連続させる。

**給紙モードが揃っていないと、同一ジョブ内でも排出される(§10.10.3)。** 用紙種別に応じて自動給紙と手差しが自動で切り替わる挙動があり、直前のパスと一致しない場合はページ合成を指定していても排紙されると報告されている。**ジョブ内の全パスで給紙モードを統一すること。**

**検証時の落とし穴(実測 2026-07-28):** 排出コマンドは単独の `0x0C` だが、**バイト列を単純に数えてはならない。ラスタデータ部に `0x0C` が画素バイトとして現れる。** ベタ画像では偶然含まれず正しく見えるが、ディザを掛けると破綻する(実測でディザ画像の素朴なカウントは 129、実際は 1)。コマンド列を構文解析してデータ部を読み飛ばす必要がある。`ref/tests/test_golden.py` の `_count_ejects` が参照実装。

**成立可否は §11.5 で検証中。** 成立しない場合、代替として見当合わせマーク(トンボ)方式へ退避する(§14.2)。

### 4.11 白の上に色を刷るときはコーティングを挟む

**白のパスの直後に色のパスを置いてはならない。間にコーティング(Finish)のパスを挟む。**

**根拠(実測。§10.7):** 作者が 32bit 環境で実作業していた際、**コーティングを挟まないと色が白の上に乗らなかった**。これは仕上がりの好みではなく、定着しないという物理的な制約である。

**コーティングを刷る範囲は白と同じ領域とする。** 紙の全面ではない。

**したがって白を使う多色刷りの最小構成は 3 段階になる。**

```text
白(必要回数の重ね刷り) → コーティング(白と同じ領域) → 色
```

**ただし 3 段階で足りない組み合わせがある。** MD-5500 の実運用者は、黒の上にホワイトを重ねる際に**光沢仕上げ 1 層では剥離を防げず**、アンダーコートを前後に挟む 5 層構成が必要だったと報告している(§10.8.1)。**中間層の構成は重ねる色の組み合わせに依存する。** パレット定義でコーティング系のインクを複数回・異なる位置に置けるようにしておくこと。`order` と `passes` の組み合わせで表現できる。

パレット定義ではコーティングも 1 つのインクとして扱い、`order` を白と色の間に置くことでこの順序を表現する。コーティングの `printer_code` は 0x0E(ppmtomd の `Finish` = Finish II カートリッジ)。

**この制約は §4.10 と組み合わさる。** 3 段階すべてが 1 ジョブに収まっていなければならない。途中で排出されると見当が失われ、白と色がずれる。golden g11 で 1 ジョブ構成が可能であることは確認済み。

### 5.2 未確定事項

`lf_correction` および `max_width_dots` は実測待ち。**推測値で埋めない。** 未確定のまま `null` を維持し、参照時は明示的にエラーとする。

### 5.3 接続方式

**先行機は MD-5500 の USB 直結に変更した(2026-08-01 / D-017)。**

MD-5000 + USB-パラレル変換ケーブルでは Phase 1 が成立しなかった(§11.1.1)。セルフテストは成功して機械は正常、送出側も 5 パターン × 2 経路で検証済み、公式ドライバ(32bit)でも「通信エラー(デバイスを識別できません)」で失敗。**残る変数が変換ケーブルの経路そのものに絞られたため、その変数を除去する。**

**経路を 1 本に固定する原則は維持する。** MD-5500 の USB 直結に固定し、変換ケーブルとの併用はしない。

以下は変更前の記述(D-012 / D-009 当時)。

> **Phase 3 が成立するまで、両機種とも USB-パラレル変換ケーブル経由で統一する。**

MD-5500 は本体に USB ポートを持つが、既存の実装で使用された実績がない。経路を 1 本に固定することで、Phase 1 の関門(§11.2)における原因の切り分けを容易にする。

USB 直結対応は保留であり、却下ではない。§11.3 を参照。

### 5.4 双方向通信

ALPS プリンタは仮想 LPT ポート経由で双方向通信を行う設計である。変換ケーブルが双方向に対応していない場合、単方向設定が必要になる。

**一次情報による確定事項(§13.3):** 公式ドライバは双方向通信で**装填済みカートリッジを検出**し、使用可能なものだけを選択肢に表示していた。双方向通信ができない場合は、**使用可能な全カートリッジを表示するフォールバックが用意されていた。**

**これは重要な朗報である。** 単方向でも印刷そのものは成立する設計になっていた。双方向はカートリッジ検出と状態取得のための機能であり、印刷の必須条件ではない。

**実測で裏付けた(2026-07-28)。** ELECOM UC-PGT + MD-5000 の組み合わせで、ホストがプリンタのデバイス ID(`ALPS    MD-5000/T-04`)を読み取れることを確認した(§10.1.1)。**双方向通信は物理的に成立している。**

**残る未確定:** エラー状態の読み出し(§11.4)は、双方向でポートを開く L0 の実装が必要。カートリッジ自動検出も同様。

### 5.5 ppmtomd 由来の参考値(実機未確認)

ppmtomd 1.6 のソースに定義された 5000 系(MD-5000 / MD-5500 / DP-5000 共通)の論理ページ幅。600dpi 基準、1200dpi 時は倍、300dpi 時は半分(ppmtomd.c:70-81, 1903-1912)。

| 用紙 | 幅(600dpi 基準ドット) |
|---|---|
| A4 | 4800 |
| Letter / Legal | 4940 |

**全 8 種類の用紙(custom / executive / letter / legal / a4 / b5 / postcard / dyesublabel)の寸法・余白・用紙サイズコードは `papers/5000-series.yaml` に記録した。** 本節はその要点のみを示す。

**用紙表を機種プロファイルから分離する理由。** ppmtomd は用紙寸法テーブルを**機種系列ごとに 2 つ**持つ(5000 系と pre5000 系)。MD-5000 と MD-5500 は同一の表を共有するため、機種プロファイルに直接書くと同じ内容が 2 ファイルに重複し、片方だけ更新する事故が起きうる。`profiles/*.yaml` の `paper_table` が `papers/{値}.yaml` を参照する形にしている(D-014)。

**系列間の差の実例:** letter / legal の幅は 5000 系が 4940、pre5000 系が 4800。postcard / dyesublabel は上余白も異なる(71 対 284)。

#### 5.5.1 余白と位置合わせの罠(実測 2026-07-28)

用紙表の `left_margin` / `top_margin` は**印刷できない領域**であり、位置合わせでは指定シフトからこの値を引く(ppmtomd の `-autoshift` 相当、ppmtomd.c:1914-1928)。

**引いた結果が負になると、画像データ側を削る経路に入る。** ppmtomd はこのときコマンドを出さず、ラスタの先頭を捨てる(ppmtomd.c:2659)。**画像がその分の行数を持たないとエラーで停止する。** A4 の上余白は 284 ドットなので、120 行の画像に `-autoshift` を単独指定すると `Unexpected EOF reading row of PPM image` で落ちる(実測)。

**実装上の扱い:** `ref/` は負のシフトを未実装とし、渡されたら明示的に停止する。黙って誤った位置に刷るより落ちるほうが安全である(§4.6 の精神と同じ)。負の経路が必要になるのは、用紙の印刷可能領域より外側へ画像を寄せたい場合に限られる。

**シフト量の単位は 1/600 インチで、解像度設定に依存しない。** 内部で出力解像度に換算され、300dpi は半分、1200dpi は x 方向のみ 2 倍になる(ppmtomd.c:1920-1921)。

実装上の上限マクロは `PCL_MAXWIDTH=6000` だが、コメントに「実際の最大は 4800。超過分はプリンタが捨てる」とある(ppmtomd.c:1083-1086)。

**この値をもって機種プロファイルの `max_width_dots` を埋めることはまだしない。** §5.2 の null 維持ルールどおり、Phase 1 以降の実機挙動確認を経て採用する。ppmtomd は両機種を同一扱いしており、機種別の値はこのソースからは得られない。

### 5.5.2 メディア種別(実測 2026-07-28)

用紙サイズ(§5.5)とは**別の概念**である。用紙サイズが寸法を決めるのに対し、メディア種別は**紙質を伝えてヘッドの加熱条件を変える**。コマンドは `ESC & l {byte1} {byte2} M`。

主要な値(golden のバイト列から読み取った実測値):

| メディア | byte1 | byte2 | 備考 |
|---|---|---|---|
| PlainPaper(普通紙) | 0x00 | 0x00 | ppmtomd の既定。現在の実装値 |
| FinePlainPaper | 0x00 | 0x02 | **すべてを 2 回印刷する**(ALPS 文書の Enhanced Quality) |
| **Cardboard(厚紙)** | **0x05** | **0x00** | §10.8.2 のリボン切れ対策 |
| PostCard | 0x06 | 0x00 | |
| LaserPaper | 0x07 | 0x00 | |

全 24 種類が `mddata.c` の `media_byte1[]` / `media_byte2[]` に定義されている(OHP・アイロン転写・裏面印刷・昇華・光沢・VPhoto など)。**機種による分岐はない**(共通の配列)。

**`Fine` 接頭辞は「すべてを 2 回印刷する」を意味する**(mddata.h:106-110 のコメント)。`passes` による重ね刷り(§6.2)とは別の機構で、**プレーン単位ではなくジョブ全体に掛かる**。混同しないこと。

**厚紙指定は消耗品の破損を防ぐ。** §10.8.2 の実践報告によれば、アンダーコート使用時のインクリボン切れが厚紙設定で解消する(ヘッド温度が上がるためと推測されている)。**品質設定ではなく安全設定として扱う。**

### 5.6 コマンド体系の系譜

**ベースは HP PCL 系であり、Epson ESC/P 系ではない。**

**根拠:**

- ppmtomd 1.6 の解像度指定コマンドは `\033*t{res}R`(ppmtomd.c:288-289, 2489)。`ESC * t # R` は **PCL のラスタ解像度指定コマンド**である。PCL データストリームを解析した実例でも、同形式が解像度指定として現れる
- ppmtomd の論理ページ幅の上限マクロは `PCL_MAXWIDTH` と命名されている(ppmtomd.c:1083-1086)。**実装者自身が PCL と認識している**

**ALPS 独自拡張が併存する。** 色選択コマンド `\033\032{code}...r`(§6.5)は標準 PCL に存在しない。**PCL を土台に、ALPS が特色・カートリッジ制御を拡張した構造**と理解するのが正確。

**実務上の意味:**

- ラスタ転送・解像度・カーソル移動など PCL 由来の部分は、**公開されている PCL リファレンスが読める**
- 特色・カートリッジ・重ね刷りなど独自拡張の部分は、**ppmtomd が唯一の手がかり**である

**注意:** 「Epson ESC/P ベース」とする外部情報が存在するが誤りである(§0.1 判定実例 2)。この誤りを採ると、独自拡張部分を ESC/P リファレンスで解こうとして作業が空転する。

## §6 パレット定義

### 6.1 スキーマ

`magic_rgb` は**公式マニュアル記載の値**である(§13.3)。推測値ではない。

```yaml
inks:
  - name: white
    label: ホワイト
    magic_rgb: [230, 230, 230]
    printer_code: 0x0B
    tolerance: 8
    order: 10
    auto_undercoat: true
    passes: 2

  - name: metallic_gold
    label: メタリックゴールド
    magic_rgb: [225, 160, 0]
    printer_code: 0x04
    tolerance: 12
    order: 50

  - name: metallic_silver
    label: メタリックシルバー
    magic_rgb: [189, 193, 197]
    printer_code: 0x07
    tolerance: 12
    order: 50

  - name: metallic_magenta
    label: メタリックマゼンタ
    magic_rgb: [163, 36, 115]
    printer_code: 0x05
    tolerance: 12
    order: 50

  - name: metallic_cyan
    label: メタリックシアン
    magic_rgb: [0, 176, 201]
    printer_code: 0x06
    tolerance: 12
    order: 50

  - name: cyan
    label: 紙用シアン
    printer_code: 0x01
    channel: C
    order: 60

  - name: magenta
    label: 紙用マゼンタ
    printer_code: 0x02
    channel: M
    order: 70

  - name: yellow
    label: 紙用イエロー
    printer_code: 0x03
    channel: Y
    order: 80

  - name: black
    label: ブラック
    magic_rgb: [0, 0, 0]
    printer_code: 0x00
    tolerance: 8
    channel: K
    order: 90
```

**`order` は昇順に実行され、先に刷ったものが下の層になる(§4.3)。** 白の下地が最小値、最後に見せたいものが最大値。

**インクには `magic_rgb`(特色。マジックカラーのマッチング対象)と `channel`(プロセスインク。CMYK 分解の受け皿)の 2 系統があり、判別は専用フラグではなくフィールドの有無で行う(D-019)。**

- `channel` を持つインク = プロセスインク。値は `C` / `M` / `Y` / `K` のいずれかで、パレット内で一意(2 つのインクが同じチャンネルを主張すると分解先が曖昧になる)
- `magic_rgb` を持つインク = 特色インク。`magic_rgb` を持つ場合は `tolerance` も必須で、逆に `magic_rgb` を持たなければ `tolerance` も省略する(片方だけは不可)
- **両方を持つことを許す**(黒がこれに該当する。純黒画素にマッチする特色であると同時に、CMYK 分解の K の受け皿でもある)
- **どちらも持たないインクはエラー**(選択される経路が存在しないため)

**`passes` の既定値は 1。** 白の 2 は暫定値であり、必要な回数は媒体と隠蔽力の要求で変わる。実測で決める(§10.5)。

**注意:** 白の指定色は純白ではなく明るいグレー(230,230,230)である。純白 255,255,255 は「印刷しない領域」と区別する必要があるため、この設計は妥当。**実装時に 255 と 230 を混同しないこと。**

**銀(189,193,197)と白(230,230,230)は近い。** `tolerance` を大きく取ると誤判定する。両方を同時に使う場合は特に注意。


### 6.2 各フィールドの意味

| フィールド | 意味 |
|---|---|
| `name` | 内部識別子。ASCII 小文字とアンダースコアのみ |
| `label` | UI 表示名。交換指示に使う |
| `magic_rgb` | このインクに予約する RGB 値。特色インクのみ(D-019) |
| `tolerance` | 近傍マッチングの許容誤差。§6.3 参照。`magic_rgb` と対で必須 |
| `channel` | プロセスインク(CMYK 分解の受け皿)であることを示す。値は `C`/`M`/`Y`/`K`。パレット内で一意(D-019) |
| `printer_code` | 色選択コマンド `\033\032{code}...r` に載せるコードバイト。§6.5 参照 |
| `order` | パス実行順。昇順。**小さいほど下の層**。§4.3 参照 |
| `passes` | 同一プレーンを刷る回数。既定 1。隠蔽力を上げる重ね刷りに使う |
| `auto_undercoat` | true の場合、他の全インクが乗る画素の和集合をプレーンとする。下地として最初に刷られる |

### 6.3 tolerance が必要な理由

PostScript ドライバがカラーマネジメントを適用すると、原稿で指定した RGB 値がそのまま届かない可能性がある。完全一致では取りこぼす。

**対策は二段構え。** PPD 側でカラーマネジメントを無効化し、かつ変換器側で許容誤差付きの近傍マッチングを行う。

`tolerance` の適切な値は実測で決める。**初期値は暫定であり、根拠がない。**

#### 6.3.2 マッチングの判定規則(D-015)

**各チャンネル独立で判定する。** R・G・B のずれが**すべて** `tolerance` 以内であればマッチとする。

```text
|r - magic_r| <= tolerance  かつ
|g - magic_g| <= tolerance  かつ
|b - magic_b| <= tolerance
```

**整数演算のみで完結させること。** ユークリッド距離(平方根)を使ってはならない。`ref/`(Python)と `src/`(C#)で浮動小数点の丸めが分かれると、**境界付近の色だけ判定が食い違い、プレーンの内容が変わってバイト列が一致しなくなる**。§4.9 の安定ソート問題と同種の罠であり、§9.2 の三段検証の前提が崩れる。

**複数のインクにマッチした場合は、最も近いものを選ぶ。** 距離は各チャンネルのずれの最大値とする。同点の場合は `order` が小さいほう(パレット定義で先に書かれたほう)を採る。§4.3 の tie-break と同じ原則で、`name` は使わない。

**どのインクにもマッチしない画素は、どのプレーンにも乗せない。** 純白 255,255,255 が「印刷しない領域」であること(§6.1)と整合する。

**`auto_undercoat` のインクは、和集合に加えて自身の `magic_rgb` マッチも含む。** 下地として他インクの下に敷かれるだけでなく、そのインク単独で描きたい領域も指定できる。和集合の計算は他インクの振り分けが確定した後に行う。**`auto_undercoat` を複数のインクに指定してはならない**(和集合の対象が定義できないため。実装は拒否する)。

**この規則は白と銀の近さに耐える。** 両者のずれは R=41 / G=37 / B=33 であり、暫定値の `tolerance` 8〜12 では衝突しない。ただし `tolerance` を 33 以上に上げると銀が白に吸われ始める(§6.1 の注意)。

#### 6.3.1 方式の妥当性(一次情報による裏付け)

**マジックカラー方式は、公式ドライバが採用していた方式と一致する。**

公式マニュアルは、メタリック & CMYK 同時印刷において、**領域の色構成によって特色部分とフルカラー部分を判別する**と説明している。各領域に適切な色を割り当てる必要があり、色構成を正確に指定できるアプリケーションで使用する前提とされている(§13.2)。

これは §6 の設計と発想が同一である。**推測から一次情報の裏付けを得た段階に格上げされた。**

さらに公式ドライバの Image Settings タブには **Color Match の None(カラーマッチングを行わない)** が用意されていた(§13.2)。色を無変換で通す経路が機器の設計として想定されていたことを示す。§6.3 の「カラーマネジメント無効化」は妥当な方針である。

**関連する注意点:** 同タブの Darker Black は、黒を 4 色すべてで生成する設定である。マジックカラー方式では純黒が別のインクへ分解されうるため、**この種の設定は必ず無効側に倒す。**

### 6.4 ページ分割方式

1 ページ = 1 インクプレーンとし、ページ番号とインクの対応を PPD オプションまたは設定ファイルで指定する。

**位置づけは §6.6 に移した。** 当初は「マジックカラーが機能しない場合の逃げ道」としていたが、**原稿の側でレイヤーが分離されている用途では第一の選択肢になる**(誤爆が原理的に起こらないため)。利用者が印刷ダイアログで選ぶ 3 方式のひとつとして扱う。

**全方式は L2 の入口の解釈が異なるだけで、それ以降は共通。** 内部表現(インク名 → 1bit プレーン)は同一である。

#### 6.4.1 仕様

**入力は複数ページ、出力は 1 ジョブ。** N ページの原稿から N 枚のプレーンを作り、それらをまとめて 1 つのジョブとして送出する(§4.10)。ページごとに別のジョブへ分けてはならない。用紙が排出されて見当が失われる。

**各ページは黒成分(K)で二値化する。** ページ全体が 1 つのインクに対応するため、色を判別する必要がない。原稿の黒い部分がそのインクで刷られる。

**この規則は実際の運用と一致する。** 公式ドライバでも「白で刷りたい図柄は黒ベタの原稿で用意する」という手順が使われている(§10.9.3)。原稿の作り方を変えずにそのまま持ち込める。

**ページとインクの対応は設定で指定する。** PPD オプションまたは設定ファイルで「1 ページ目 = ホワイト、2 ページ目 = ブラック」のように与える。対応が定義されていないページはエラーとする(黙って捨てない)。

**パスの実行順はページ順ではなく `order` に従う**(§4.3)。ページの並びと刷る順序は別の概念である。利用者がページ順で意図を表したい場合は、パレット定義の `order` をそれに合わせる。

### 6.6 インク指定方式は 3 種類あり、利用者が選ぶ

**単一の方式に固定しない。** 原稿の作り方によって最適な方式が異なるためである。

| 内部識別子 | 日本語表示 | PPD キーワード | 内容 |
|---|---|---|---|
| `auto` | 絵柄から自動判別 | `Auto` | 1 枚の原稿から、特色に一致した画素は特色へ、残りを CMYK 分解へ回す。**既定** |
| `per_page` | ページごとに指定 | `PerPage` | 1 ページ = 1 インク。ページ番号とインクの対応を設定で指定する(旧 §6.4) |
| `spot_only` | 特色のみ | `SpotOnly` | マジックカラーのみを使い、一致しない画素は刷らない。§6.3.2 の規則そのまま |

**`auto` を既定とする理由:** §1.1 が「任意のアプリケーションの印刷ダイアログから通常のプリンタとして選択でき」ることを目標に掲げている。何も設定せずに刷った利用者が期待どおりの結果を得られる方式を既定にすべきである。特色を意図的に使う用途は「選んで使う」性質のものであり、切り替えの手間が許容されやすい。

**`per_page` は逃げ道ではなく対等な選択肢である。** 原稿の側で既にレイヤーが分離されている場合(白目のレイヤーとそれ以外、など実際の制作手順がこれにあたる)、ソフトウェアが色を見て推測する必要がない。**誤爆が原理的に起こらない**ため、確実性が要る用途ではこちらが優れる。§6.4 の「マジックカラーが機能しない場合の代替」という位置づけは、この節で上書きする。

**`auto` の振り分け規則:**

1. 各画素について、まず §6.3.2 の規則で特色とのマッチングを試みる
2. いずれかの特色に一致したら、その画素は**特色のプレーンにのみ**属する(§4.3: 1 パス = 1 カートリッジ)
3. どの特色にも一致しなかった画素だけを CMYK 分解に回す
4. `auto_undercoat` の和集合は、特色・CMYK 両方の全プレーンが確定した後に計算する

**誤爆のリスクと対策:** 原稿中の色がたまたま特色の予約色に近いと、意図せず特色として拾われる。`tolerance` を小さく保つことで抑えるほか、**§7.2 のインク割り当てプレビューで刷る前に発見できる**。リボンと用紙を消費する前に気づける設計になっていることが、この方式を既定にできる前提である。

### 6.5 プリンタ側の色識別とサードパーティインクへのバッファ

ppmtomd 1.6 の読解(`docs/research/ppmtomd-survey.md`)により、ホスト → プリンタのインク指定は 2 層あると判明した。

1. **色選択コマンドのコードバイト**(プレーン送出前の `\033\032{code}...r`)
2. **カートリッジバーコード値**(ジョブ冒頭で使用カートリッジ一覧として送出)

「インクが何か」はこの 2 値で決まる。したがって §6.1 のスキーマは、**プリンタへ送る値を外部定義するフィールド**を持つ必要がある。これが無いとコード内対応表への依存が残り、§4.5(ハードコード禁止)の趣旨が損なわれる。

**`printer_code` は確定した(2026-07-28)。** 値は golden のバイト列から直接読み取った実測値であり、推測ではない。

| インク | `printer_code` | 由来 |
|---|---|---|
| ブラック | 0x00 | g1 |
| シアン | 0x01 | g2 |
| マゼンタ | 0x02 | g2 |
| イエロー | 0x03 | g2 |
| メタリックゴールド | 0x04 | g7 |
| メタリックマゼンタ | 0x05 | g7 |
| メタリックシアン | 0x06 | g7 |
| メタリックシルバー | 0x07 | g7 |
| ホワイト | 0x0B | g3 |

`barcode` は**保留とする。** カートリッジバーコードはカセット系の転送モードでのみ送出され、本プロジェクトが使う転送モード(colourPlane)では使わない。必要になった時点で追加する。

**2 層構造は実測で確認済み(2026-07-28)。** 外部の実践者の記録にある「特色ホワイトは番号 16、黒は番号 0」が ppmtomd の `barWhite = 16` / `barBlack = 0` と一致した(§10.9.2)。同じ白でも色選択コード(0x0B = 11)とバーコード番号(16)は別の値である。

**バーコード番号の一覧**(`mddata.h`。ホスト側が送出しないため参考値):

| 番号 | 対象 | 番号 | 対象 |
|---|---|---|---|
| 0 | ブラック | 13–15 | **OHP 用**イエロー / マゼンタ / シアン |
| 1–3 | イエロー / マゼンタ / シアン(紙用) | 16 | ホワイト |
| 4 | マルチカラー | 17 | Finish |
| 5–6 | ゴールドフォイル / シルバーフォイル | 18 | VPhoto Primer |
| 8–11 | メタリック 金 / マゼンタ / シアン / 銀 | 19 | **Finish II**(ppmtomd の `Finish` はこちら) |
| 20–22 | Labeca 黒 / 青 / 赤 | 23 | EconoBlack |
| 25–28 | 昇華用 Y / M / C / オーバーコート | 7, 12, 24, 29 | 予約(未使用) |

**紙用と OHP 用でカートリッジが分かれている。** 同じシアンでも番号が異なる(3 と 15)。**Finish も 2 種類ある**(17 と 19)。

**この表は ppmtomd 由来(海外名)である。純正ドライバから抽出した国内名の対応表は §13.7.5 にあり、一見食い違って見えるが同じカセットを指す。**

| 番号 | 本表(海外名) | §13.7.5(国内名) | 関係 |
|---|---|---|---|
| 9 | メタリック マゼンタ | メタリックレッド | **同一**(§6.1 の名称対応) |
| 10 | メタリック シアン | メタリックブルー | **同一**(§6.1 の名称対応) |
| 21 / 22 | Labeca 青 / 赤 | ラベカレッド / ラベカブルー | **順序が逆。ppmtomd 側が誤っている可能性がある(§13.7.5)** |

**利用者に見せる名前は国内名を使う**(§6.1 の `label` の方針と同じ)。番号との対応で迷ったら §13.7.5 を優先する — 純正ドライバの文字列リソースから直接得た一次情報であるため。

**カートリッジの識別変更は利用者の物理作業である。** バーコードのラベルを貼り替えることで、あるインクを別の色として認識させる運用が実際に行われている(§10.9.3 / §10.8.4)。ホスト側は色選択コードを指定するだけでよく、**Foilwright の実装は関与しない**。

**`magic_rgb` との役割の違いに注意。** `magic_rgb`(§6.1、公式マニュアル由来)は**アプリケーション側で置く色**であり、`printer_code` / `barcode` は**プリンタへ送る値**である。両者は独立した層に属し、混同してはならない。

**サードパーティ製特色インクへの方針:** 販売元との関わりは持たない前提とし、問い合わせに依存しない。設計側のバッファで吸収する。

- 純正いずれかの識別を流用したカートリッジ → 既存インク定義の別名(`name` / `label` と `magic_rgb` だけ違う行)で対応
- 独自識別のカートリッジ → `printer_code` / `barcode` を設定行に書くだけで対応(コード変更なし)

サードパーティ製インクは、`printer_code` に純正いずれかの値を書けば「そのインクのふり」で刷れる。独自の識別を持つ場合も、判明した値を設定行に書くだけで対応できる。

## §7 UI

**構成は D-024 による。トレイアプリ単体で、パイプサーバ・変換・UI・送出のすべてを担う。**

§7.1 が扱っていた「印刷ダイアログ側の UI」は失効した。現行 Windows では独自 PPD を
同梱できず(§3.5.1 / D-022)、印刷ダイアログに項目を出す手段が無い。設定はすべて
本節のトレイアプリが持つ。

### 7.1 設定は既定値とジョブごとの上書きの二層

**既定値**はトレイアプリの設定画面で決め、以後のすべてのジョブに適用される。
**ジョブごとの上書き**はプレビュー画面で行い、そのジョブにのみ効く。Windows の
印刷設定(既定 + ジョブごと)と同じ構造であり、利用者はこの挙動に慣れている。

設定項目(旧 §7.1 から移設):

- 解像度(600 / 1200x600)
- **インク指定方式**(絵柄から自動判別 / ページごとに指定 / 特色のみ。§6.6)
- **メディア種別**(普通紙 / 厚紙 など。§5.5.2。厚紙はリボン切れ対策であり品質設定ではない)
- **ハーフトーン**(なし / ハーフトーン / 粗いハーフトーン。§4.2.1)
- 白版モード(なし / 自動生成 / マジックカラー指定)

**カラーマネジメント無効化の項目は不要。** §3.5.2 の実測により、経路上で RGB 値は
変質しないことが確認されている。

**プレビュー上で方式を切り替えられることは、PPD より優れている。** PPD では
「自動判別でこの原稿がうまく分離されるか」は刷るまで分からなかったが、プレビューで
切り替えれば結果がその場で見える。

### 7.2 トレイアプリ

**唯一の自作 UI。** ユーザーセッションで常駐し、名前付きパイプ `\\.\pipe\foilwright`
でスプーラからのジョブを受ける(D-023)。

必須機能:

1. **インク割り当てプレビュー** — どの領域がどのインクに解釈されたかを刷る前に表示する
2. ジョブ内容の表示(パス数、使用インク、順序)
3. 設定の変更(§7.1 の項目。変更するとプレビューが再描画される)
4. 印刷開始ボタン
5. **カセットの過不足表示と交換指示**(§7.3)
6. 進捗表示
7. **プリンタ状態表示** — `05 01` で読める(§11.4 / §15.2)

**プレビューは必須機能である。** マジックカラー方式は誤爆時にリボンと用紙を消費する。
これらは代替入手が困難な消耗品であり、事前確認の欠如は許容できないコストを生む。

**トレイアプリが起動していないと印刷は失敗する。** パイプが存在しないため、スプーラの
書き込みがエラーになる。プレビューが必須である以上どのみち刷れないため、これは
許容する(D-024)。

### 7.3 カセットの過不足は機械が判定する

**§7.2 の旧版は「パスごとに交換指示を出す」前提だったが、これは実機の挙動と異なる。**
MD-5500 はカセットホルダを自動で回転させ、装填済みのインクから必要なものを選ぶ
(§15.5 で C→M→Y→K の自動選択を実測)。**装填済みのインクで足りるなら交換は起きない。**

さらに **`05 01` で現在の装填状況を読める**(§11.4)。応答の 11 レコードのうち 8 つが
上下段のホルダ、9 番目がヘッドに装着中のカセットを表し、各レコードの先頭バイトが
バーコード番号(§13.7.5)である。したがってトレイアプリは次のように動ける。

1. ジョブに必要なインクを算出する
2. `05 01` で装填状況を読む
3. **足りていれば全パスを一括送出する**(交換は発生しない)
4. **足りなければ、送れるパスまで送って停止する。** 不足しているインクを `label`(品番付き)
   で表示し、交換を待つ
5. 交換後に **再度 `05 01` を読んで正しいカセットが入ったことを検証してから**続きを送る

**利用者が誤ったカセットを入れたまま先へ進むことができない。** これは公式ドライバにも
無い挙動であり、状態を読めるようになった副産物である。

**待機中もジョブを終了させてはならない(§4.10)。** 排出は最終パスの後に 1 回だけであり、
用紙がローラーから離れると見当を再現できない。L0 はパケット単位で送出するため、
途中まで送って停止し、交換後に続きを送ることができる。

#### 実装済みの範囲(2026-08-07)

**上記 1〜3 と「不足の名指し」までを実装した。** 4〜5(途中停止して交換を待ち、検証して続きを送る)は未実装である。

| 手順 | 状態 |
|---|---|
| 1. 必要インクの算出 | **実装済み**(`JobAssembly.BuildJobPlanes` が返すインク一覧) |
| 2. 装填状況の読み取り | **実装済み**(`05 01` → `StatusDecoder`) |
| 3. 充足していれば一括送出 | **実装済み** |
| 4. 不足時に送れるパスまで送って停止 | **未実装** |
| 5. 交換後に再検証して続きを送る | **未実装** |

判定は `CassetteCheck.Evaluate` が行い、結果は 3 値(充足 / 不足 / **判定不能**)。**エラー中は必ず判定不能を返す** — §11.4 の実測どおりカセット情報が更新されないため、「不足」と誤って表示すると現物と食い違う指示になる。`barcode` 未設定のインクも「不足」と混同せず判定不能として分離する。

**突き合わせには `barcode` を使う(D-026)。** `printer_code`(ホストが送る色選択バイト)とは別体系であり、混同してはならない。

#### 4〜5 を実装しない理由

**プリンタがジョブ途中の待機にどこまで耐えるかが未測定だからである。** タイムアウトで用紙が排出されれば §4.10(排出は最終パスの後に 1 回だけ)が破れ、見当が再現できなくなる。**測らずに実装すると、動くように見えて用紙とリボンを浪費する仕組みができあがる。**

**実機が復帰したら、まず待機可能時間を測る。** 短い場合は、交換を伴う多パスの構成そのものを見直すことになる(§14.1 と同じ論点)。

**判定と表示だけでも実用価値はある** — 刷る前に「白が足りない」と分かるため、誤って開始して消耗品を失う事故を防げる。

交換指示では、複数回の交換を伴う印刷で現在位置が分からなくなることを防ぐため、
**全パス中の何番目かを常に表示する**。

### 8.1 `ref/` の位置づけ

**書き捨てではない。検証装置として恒久的に維持する。**

`ref/` が担当するのは L1 と L2 のコアのみ。画像を受け取り、インク別プレーンに分解し、MD コマンド列を出力する。ここまで。

`ref/` が担当しないもの:

- トレイアプリ
- PPD 解釈
- キュー管理
- ポートモニタ連携
- プリンタへの実送信

**したがって `ref/` は機能追加に追従しない。** 更新するのは MD コマンド言語の仕様理解が変わったときのみ。それは稀にしか起きず、起きたときは重要な発見である。

### 8.2 ppmtomd の扱い

ppmtomd 本体はリポジトリに含めない。他者の GPL コードであり、配布の責務を負わない。

**その出力である golden バイナリは含める。** これは事実の記録であり、検証の基準となる。

## §9 テスト戦略

### 9.1 三段構え

```
ppmtomd(C言語 / 20年の実績)
  └→ tests/golden/*.bin
        ├→ ref/  が一致するか
        └→ src/  が一致するか
```

### 9.2 判定と切り分け

| src/ | ref/ | 判定 |
|---|---|---|
| golden と一致 | 一致 | 正常 |
| 不一致 | 一致 | C# の移植バグ |
| 不一致 | 不一致 | 仕様理解の誤り |
| 一致 | 不一致 | Python 側のバグ。または golden の前提条件の取り違え |

### 9.3 golden の採取対象

最低限、以下の組み合わせを採取する。

- ベタ 1 色(黒)
- ベタ 2 色
- **白版を含む多層** — §11.5 の検証に必須。**排出コマンドの出現回数を数えることが第一の目的**(下記)。**採取済み: g10(白・金・銀・黒の 4 層。排出 1 回を確認)**
- **メタリック複数色(`order` 同値のパスが 2 本以上生じるケース)** — §4.9 の検証に必須
- 解像度違い(600 / 1200x600)
- 機種違い(MD-5000 / MD-5500)

**メタリック複数色のケースは優先度が高い。** §4.9 の安定ソート問題は、この組み合わせでしか顕在化しない。これが golden に無いと、`ref/` と `src/` の不一致が Phase 3 まで発見されない。

**実機カートリッジの有無に依存しない。** golden は ppmtomd で生成するため、メタリックカートリッジを所持していなくても**バイト列の一致検証は完全に実施できる。** 実機での刷り上がり確認のみが Phase 3 以降に持ち越される(§9.5)。

**白版を含む多層ケースは、採取した時点で §11.5 の答えが出る。** 生成されたバイト列に含まれる排出コマンドが 1 回なら、ppmtomd は 1 ジョブ内で複数パスを構成している。そのバイト列をそのまま流せばよい。複数回なら、パス間の用紙の扱いをソースで追う必要がある。**いずれにせよ実機に触れる前に確定できる。**

**機種差の特定は golden 同士の差分で行う。** 同一画像を機種指定だけ変えて生成し、バイナリ差分を取る。仕様書を探すより確実で速い。

### 9.3.1 OEM 系統を情報源に含める

ALPS はマイクロドライ機構を他社へ OEM 供給しており、**同一プロトコル圏に複数のブランドが存在する。**

- Citizen Printiva 系(600C / 700C / 1700C など)
- Oki DP 系

ppmtomd がこれらを同一ドライバでサポートしていることが、プロトコル共通性の裏付けとなる。また Printiva 向けの旧ドライバのファイル名に `alps` の文字列が含まれることも、系譜を示す傍証である。

**活用方針:** 仕様の裏取りや golden の採取元として、ALPS 単体で探すより広い範囲を参照できる。ALPS 名義で見つからない資料が Printiva / Oki 名義で残っている可能性がある。

**棄却した情報(2026-07-27):** 「Citizen が Vista / Windows 7 向けの 64bit ドライバを公開しており、ALPS 機に転用できる」との情報を検討し、採用しなかった。

| 主張 | 判定 |
|---|---|
| 64bit の**カーネルモード**印刷ドライバとして動作し安定する | **成立しない。** Windows のプリンタドライバはユーザーモード。カーネルモード印刷ドライバは Vista で非推奨化され、以降はインストール自体が不可 |
| Citizen が 64bit ドライバを公開していた | **裏付けなし。** アーカイブに残るのは Windows 3.1/95/98/Me 版と NT4 版のみ。Citizen Systems の現行サポート対象に Printiva は含まれない。64bit 版を掲げるのは自動生成型のドライバ配布サイトのみ |
| INF の VID/PID 書き換えで転用可能 | **二重に不整合。** INF 改変はパッケージ署名を破壊し 64bit Windows では導入できない。また VID/PID は USB の識別子であり、パラレル接続の本機と対象が異なる |
| 界隈で語り継がれた既知の手法 | **反証。** 事実であればコミュニティ製ユーティリティを新規開発する動機が消える。当該ユーティリティは複数の技術者により開発され、ALPS 機の修理・インク販売を業とする事業者が協力している。より簡便な解が存在したとは考えにくい |

**なお仮に実在したとしても本プロジェクトの要件を満たさない。** 当該情報自身が「特色白・金・銀の制御は困難」としており、特色制御こそが本プロジェクトの目的である。

### 9.4 実機テストの段階

| 段階 | 内容 | 実機リスク |
|---|---|---|
| Phase 0 | 環境調査。ポート一覧と変換ケーブルのデバイス ID を取得するのみ | なし |
| Phase 1 | 5mm 角のベタ 1 色を 1 枚 | 最小 |
| Phase 2 | 仮想プリンタ経由でメモ帳から印刷 | 小 |
| Phase 3 | 白版を含むフルパス | 中 |
| Phase 4 | USB 直結対応(§11.3)。実施は Phase 3 成立後 | 未定 |

**Phase 1 の判定は二値でなければならない。** 「出た」か「出ない」か。曖昧な結果を最初に持ち込まない。

**Phase 1 はプロジェクトの成否を決める関門である。** §11.2 のタイミングリスクがここで判明する。Phase 1 が成立するまで、UI・トレイアプリ・PPD の作り込みに着手しない。

**外部の協力者への配布は、作者の環境で Phase 3 が成立した後に限る。** 基準線のない状態で配ると、原因の切り分けが不可能になる。

### 9.5 実機検証の到達範囲

**バイト列の検証と実機の刷り上がり確認は、到達範囲が異なる。** これを混同しないこと。

| 検証内容 | 手段 | 必要な物 |
|---|---|---|
| バイト列が正しいか | golden との比較 | ppmtomd のみ。**実機・カートリッジ不要** |
| 実際に刷れるか | Phase 1–3 | 実機 + 該当カートリッジ + 用紙 |

**保有していないカートリッジの機能も、バイト列レベルでは完全に検証できる。** メタリック 4 色、Finish、VPhoto Primer などがこれに当たる。

**現時点の未確保:** メタリック系カートリッジ。入手可能性は不明だが、確保できない場合でも以下の方針とする。

- golden による検証は実施する(§9.3)
- 実機での刷り上がり確認は**未検証範囲として README に明記する**
- 協力者が該当カートリッジを保有していれば、Phase 3 で検証を依頼する(§9.4)

**未検証であることを隠さない。** 動作確認済み構成のみを保証するという方針(§1.2)と一貫させる。

- **Windows 標準の `usbprint.sys` がそのまま掴む。** ベンダ固有ドライバもフィルタドライバも不要
- **通常の USB プリンタポートとして見える。** L0 の実装は MD-5000 + 変換ケーブルの場合と同一でよい

**機種名の表記は `MD-5500_T-03`。** MD-5000 の `MD-5000/T-04` とは区切り文字が異なる(アンダースコア対スラッシュ)。**デバイス ID の書式は機種で統一されていない。** 文字列の解析に依存する実装を書かないこと。

**変換ケーブル経由との比較。** MD-5000 + ELECOM UC-PGT では VID が変換ケーブル側(056E)になり、機種名は取れるものの**印刷データが到達しなかった**(§11.1.1)。直結では VID が ALPS 自身(044E)になる。

### 10.6 用紙保持と排出の実測(32bit 環境 / 公式ドライバ)

作者が 32bit 環境の公式ドライバで実作業していた際の記録。**§4.10 および §11.5 の根拠となる一次実測データ。**

| 条件 | 用紙 | 結果 |
|---|---|---|
| 白以外の複数色を同時指定(1 ジョブ) | — | **成功。** 排出は最後の 1 回のみ |
| 特色ホワイトを使用(白が別ジョブになる) | B5 | **成功。** 排出動作の途中でぴたりと停止し、後端がローラーに残ったため続行できた |
| 特色ホワイトを使用(白が別ジョブになる) | はがき大 | **失敗。** 完全に排出され、続きが刷れなかった |

**確定した事実:**

1. **保持機構は正常に機能する。** B5 で停止し、その後のパスも正常に刷れている
2. **多パス動作も正常に機能する。** 白以外の複数色同時指定は問題なく成功していた
3. **排出はパスの区切りではなくジョブの区切りで起きる**
4. **失敗の原因は用紙長ではない。** 用紙長は「後端が残るかどうか」を左右しただけで、根本原因は白が別ジョブになること(§1.1)

**この 3 件目が最も重要である。** ジョブを分けなければ排出は起きない。したがって §11.5 の課題は「用紙を保持できるか」ではなく、**「全パスを 1 ジョブとして送れるか」**に絞られる。

**使用機種:** MD-5500(2026-07-28 確認)。

### 10.7 アイデカール制作の実手順(32bit 環境 / 公式ドライバ)

| 段階 | 内容 | 範囲 |
|---|---|---|
| 1 | 白目のレイヤーを**白で 4 回程度**重ね刷り | 白目部分のみ |

### 10.8 外部の実践知見(MD-5500 実運用者)

出典: 塗装工房 PaintKobo のコラム「MD5500のページ合成」(`http://www.paintkobo.net/MD5500.html`、2026-07-28 参照)。**MD-5500 を業務で長期運用している当事者の実測記録**であり、§0.1 の一次情報に該当する。以下は要点の記録であり、原文の転載ではない。

#### 10.8.1 剥離を防ぐ層構成

**特色を重ねると剥がれる。** 黒の上に特色ホワイトを直接重ねると、ホワイトが所々剥がれる。**光沢仕上げを 1 層挟むだけでは不十分**で、完全には防げなかったと報告されている。

安定した層構成として報告されているのは次の 5 層。

```text
紙用ブラック → アンダーコート → 仕上げ(光沢) → アンダーコート → 紙用特色ホワイト
```

**§4.11 の制約はより厳しい形で裏付けられた。** 当プロジェクトの実測(§10.7)では「白 → コーティング → 色」の 3 段階だったが、この報告では**中間層が 3 層**になっている。用途と重ねる色の組み合わせによって必要な中間層が変わるとみられる。

**「アンダーコート」は光沢仕上げとは別のインクである。**【推測】公式ドライバの VPhoto Primer に相当する可能性が高いが、断定できない。ppmtomd では `Primer`(`printer_code` = 0x10)。

**アンダーコートは印刷対象の領域にのみ乗る。** 普通紙・厚紙では、黒で印刷する部分にのみ乗ると報告されている。全面塗布ではない。§4.11 に記録した「コーティングの範囲は白と同じ」と同じ性質。

#### 10.8.2 用紙設定でリボン切れを防ぐ

**アンダーコート使用時にインクリボンが切れることがある。** 用紙の種類を「厚紙」に設定すると発生しなくなったと報告されている(ヘッド温度が上がるためではないかと推測されている)。

**実装への含意:** メディア種別の指定(`ESC & l {b1} {b2} M`)は品質だけでなく**消耗品の破損防止**に効く。現在の実装は `media_byte1` / `media_byte2` を 0 固定にしており、厚紙指定のバイト値は未調査。Phase 3(白版を含むフルパス)の前に確認する必要がある。

#### 10.8.3 ホワイトの隠蔽力と「銀下」

**MD のホワイトは隠蔽力が高くない。** 貼付時に下地が透ける経験が報告されている。対策として**メタリックシルバーを下地に使う「銀下」**という手法が紹介されている。報告されている構成は、メタリックシルバーの上にホワイト 1 回、その上に CMY を各 2 回。

**§10.5 の「白 4 回」とは別の解法である。** 白を重ねて隠蔽力を稼ぐか、銀を下地にして白を減らすかの選択肢がある。`passes` と `order` の組み合わせでどちらも表現できる。

#### 10.8.4 サードパーティインクの実例

**OKI(沖電気)のインクに、シアン・マゼンタ・イエローのバーコードを貼って使用**していると報告されている。特色のブルー・レッド・グリーンをこの方法で使っている。

**§6.5 の「純正いずれかの識別を流用する」の実例である。** ただし識別の流用が**物理的なバーコードの貼り替え**で行われている点が重要。ホスト側は純正インクとして扱えばよく、`printer_code` の変更すら不要になる。§6.5 の設計バッファはこのケースを吸収できる。

#### 10.8.5 中間調のストライプ

**淡色・中間色をそのまま印刷すると、CMY が細かいストライプ状に出る。** 離れて見れば指定色に見えるが、近付くと縞模様が目立つと報告されている。

**§4.2.1 のディザ方式選択に直結する。** ppmtomd の `Halftone` は man 自身が「ラインスクリーン」と説明しており、この縞模様の正体である可能性が高い。**ドットスクリーンを使う `CoarseHalftone` のほうが、この用途では良い結果になりうる。** 実機で比較する価値がある(Phase 3)。

なお当該報告者は、この縞模様を避けるために**単色ごとに重ねる「ページ合成」方式を採っている**。これは中間調を階調で表現せず、特色の重ねで色を作る手法であり、本プロジェクトのマジックカラー方式(§6)と発想が一致する。

### 10.9 外部の実践知見(模型用デカール制作者)

出典: ZAKU MODELS「MDプリンター使用におけるメモランダム」(2018-11-20、2026-07-28 参照)。**MD-5500 でウォータースライドデカールを制作している当事者の記録**であり、§0.1 の一次情報に該当する。要点の記録であり原文の転載ではない。

#### 10.9.1 ホワイトは 2 種類あり、性質が逆である

| 種類 | 性質 | リボン巻き量 |
|---|---|---|
| **ベースドホワイト** | 他のインクの**上に乗りやすい**。ただし**この上には他のインクが乗りにくい** | 特色ホワイトの 2 倍 |
| **特色ホワイト** | **この上には他のインクが乗りやすい**。ただし他のインクの上には乗りにくい | — |

**下地に向くのは特色ホワイト**と結論づけられている。

**当面は特色ホワイトのみを対象とする。** ベースドホワイトの色選択コードは実物がなければ確定できず(§11 #11)、入手は自力調達か知人からの借用に依存する。§9.5 の方針どおり、**保有していないカートリッジの機能もバイト列レベルでは検証できる**ため、コードさえ判明すればパレット定義に 1 行足すだけで対応できる。実装を待たせる必要はない。

**インクの重なりやすさには方向性がある。** 「A の上に B」と「B の上に A」で結果が違う。同記事は「A 色に B 色が乗りにくい場合は順序を逆にすると乗りやすい」とも述べている。

**§4.11 との関係は未確定。** 本プロジェクトの実測(§10.7)では白の上に色を乗せるのにコーティングが必要だったが、この記事は特色ホワイトなら色が乗りやすいとしている。**使用したホワイトの種類が §10.7 の記録に残っていない。** 条件の違いか、それとも媒体(フィルム対紙)の違いかは判明していない。

#### 10.9.2 バーコード番号は色選択コードとは別系統(実証)

同記事は**特色ホワイトのバーコードを「番号 16」、黒を「番号 0」**と記している。ppmtomd の定義(`mddata.h`)は `barWhite = 16` / `barBlack = 0` であり**完全に一致した**。

**§6.5 が予測した 2 層構造が実証された。** 同じ白でも、プリンタへ送る色選択コード(`printer_code` = 0x0B = 11)とカートリッジのバーコード番号(16)は別の値である。

**紙用と OHP 用でカートリッジが別系統である。** バーコード定義には `barOHPYellow = 13` / `barOHPMagenta = 14` / `barOHPCyan = 15` が存在し、紙用の 1 / 2 / 3 とは別番号が割り当てられている。§10.8 の「紙用ブラック」「紙用特色ホワイト」という表記はこの区別を指している。

**Finish も 2 種類ある。** `barFinish = 17` と `barFinishII = 19` が別番号で、ppmtomd の `colGlossyFinish` は後者に対応する。

#### 10.9.3 「白を黒として刷る」回避策と、その不要化

公式ドライバでは**原稿の白い部分が「印刷しない領域」と解釈される**ため、白を刷りたい図柄は**黒ベタの原稿として用意し、白カートリッジのバーコードを黒に貼り替える**という回避策が使われている。

**§6.1 の設計はこの制約を回避する。** マジックカラー方式では白を `magic_rgb: [230, 230, 230]`(純白ではない明るいグレー)で指定するため、原稿を黒で作り直す必要も、バーコードを貼り替える必要もない。**公式ドライバでは不可能だった使い方であり、§1.1 の位置づけを補強する。**

#### 10.9.4 サードパーティ特色インクと解像度の関係

象のロケット社が 19 種の特色インクを供給している(2019 年開発)。同記事によれば:

- バーコードが黒(番号 0)のままの場合、**1200dpi で印刷する必要がある**
- 600dpi で使うには、バーコードを特色ホワイト(16)・MF インク・メタリック系・紙用シアン/マゼンタなどに貼り替える
- 同色を重ねれば 2 回 3 回 4 回と濃度を上げられる
- 紙用 CMY と重ねる際は**特色インクを最後に印刷する**
- 1200dpi では特色 19 色同士が約 90% 重なる

**解像度とカートリッジ識別が結びついている理由は不明。**【推測】バーコード番号ごとにヘッドの駆動条件が変わる可能性があるが、裏付けはない。§11 の未確定事項として扱う。

#### 10.9.5 その他

- **公式ドライバは Windows 7 まで。** 専用に古い OS の PC を用意する運用が行われている(§1.1 の課題設定を裏付ける)
- 用紙は Wave「NEW クリアデカール」が供給の安定性から選ばれている
- しばらく印刷しないと掠れが出るが、数枚刷ると解消する(原因不明と明記)

### 10.10 サードパーティ特色インクの運用(象のロケット / paoon)

出典: paoon の製品ページ(`https://www.paoon.com/decal/traldcmvl.html`、2026-08-01 参照)。**供給元が公開している運用手順**であり、§0.1 の一次情報に該当する。要点の記録であり原文の転載ではない。

**§6.5 で設計したバッファが、実在する製品の運用と一致することを確認できた。**

#### 10.10.1 出荷時は紙用ブラックとして認識される

**インクカセット認識バーコードは紙用ブラック(0 番)と同じ状態で出荷される。** プリンタは紙用ブラックとして扱う。

**この状態では 1200dpi で印刷する。** 供給元は「紙用ブラックの 600dpi や 2400dpi の設定では綺麗に印刷することはできません」と明記しており、**グレイスケール + 1200dpi** を指定する運用としている。

**§11 #12 の実用的な答えが出た。** 「解像度とカートリッジ識別が結びつく理由」は、**バーコードが示すインク種別ごとに適正な解像度が異なる**ためだった。ただし**機構的な理由(なぜ紙用ブラック識別だと 600dpi で綺麗に出ないのか)は依然として不明。**【推測】識別ごとにヘッドの駆動条件(加熱時間・パルス幅)が変わる可能性があるが、裏付けはない。

#### 10.10.2 バーコードの貼り替え先(§6.5 の実例)

600dpi で使う場合は、目的に応じて次のいずれかのバーコードに貼り替える。

| 貼り替え先 | 品番 | 定着性 |
|---|---|---|
| 特色ホワイト | MDC-SCWH | 良好 |
| MF インク | MDC-PREP | 良好 |
| **ベースドホワイト** | **MDC-OPWH** | 良好 |
| メタリックシルバー / ゴールド | MDC-METS / METG | 良好 |
| メタリックレッド / ブルー | MDC-METR / METB(別品番 MLC-SMTR / MLC-SMTB あり) | 良好 |
| 紙用シアン | MDC-FLCC | 98% 程度 |
| 紙用マゼンタ | MDC-FLCM | 96% 程度 |

**ベースドホワイト `MDC-OPWH` が第三者の資料でも確認された**(§11 #11 / §13.5.3)。品番の裏付けが 2 系統になった。

**§6.5 の設計が現実の運用と一致している。** 「純正いずれかの識別を流用したカートリッジ → 既存インク定義の別名で対応」としていたが、実際にこの方式が製品として成立している。**ホスト側は流用先の `printer_code` を指定するだけでよく、Foilwright の実装は関与しない。**

**メタリック系のバーコードを使う場合の注意。** リボンの継ぎ目の重なりが大きく、境目が二度塗り状になってベタで濃いラインが目立つことがある。

#### 10.10.3 給紙モードの不一致でページ合成が破れる(重要)

**「用紙の種類によって自動給紙と手差しが自動で切り替わり、直前の印刷と一致しないと、ページ合成にチェックがあっても排紙される」**

**§4.10 の不変条件に対する新しい破れ方である。** これまで「ジョブを分けると排出される」ことは把握していたが(§10.6 / §11.5)、**同一のページ合成内であっても給紙モードが揃っていないと排出される**という条件は未把握だった。

**実装への含意:** ジョブ内の全パスで給紙モードを統一する必要がある。用紙種別に応じて自動で切り替わる挙動があるため、**パスごとに異なるメディア種別を指定すると意図せず排出されうる**(§5.5.2)。Phase 1 で給紙レバーが A では給紙されず M で給紙できた事象(§11.1.1)とも関連する可能性がある。

**未確定:** この自動切替がホスト側のコマンドで制御されるのか、プリンタ本体の判断なのか。ppmtomd のコマンド列に給紙モードの指定は存在しない(§11.1.1)。

#### 10.10.4 デカール用途では「裏面印刷」でカール矯正を止める

**デカールシートや MD 用ビューカルへの印刷時は「必ず裏面印刷にチェックを入れてカール矯正は止める」**とされている。

**実装への含意:** 現在の emitter はカール補正コマンド(`ESC SUB 0 0 C`)を常に固定値で出力している。**主用途であるデカール印刷ではこれを無効化する必要がある可能性が高い。** ppmtomd には `-nocurl` と `-forcecurlcorrection` のオプションが存在するため、バイト列の差分を golden で採取して確認できる。**未実施。**

#### 10.10.5 重ね刷りと併用順序

- **特色インク同士は 95% 程度重なる。** 2 回 3 回と重ねることで濃度を上げ、多彩な色を作れる。ページ合成機能を使う
- **紙用 CMYK と併用する場合、特色インクを最上面(最後)に印刷する。** §4.3 の `order` で表現でき、特色に大きい値を与えればよい
- 重ね合わせの実例: シアン + オレンジ = 濃いアーミー色 / マゼンタ + オレンジ = ワイン系の赤 / メタリックシルバー + オレンジ = メタリックオレンジ

**メタリックとの重ね合わせが成立している点に注目。** §13.5 の公式仕様ではメタリックは透過しないとされるが、**象のロケットの特色は透過性の顔料インク**であり、上に重ねることで色を作れる。

#### 10.10.6 その他

- 対応機種: MD-5500 / MD-5000 / MD-1500 / MD-1300 / MD-1000。**MD-1000 系も同じインク系統**
- 全 20 色の特色シリーズが供給されている(オレンジ ZK-MDC-ORMR 等)
- 紙用 CMYK に比べ印字エッジのシャープさはわずかに劣るが、**網点では得られない単色文字**を印刷できる
- 特色ホワイトの下地の上にも印刷可能
- デカール軟化剤・水性 / ラッカー / ウレタン系コーティングとの相性は良好

### 11.0 4 件が同一の壁を共有していることに注意

### 11.1 2400dpi について【解決済み 2026-07-27】

**ppmtomd 1.6 のソース読解とマニュアルの記述が一致し、解決した。**

**ソース側の証拠:** 解像度指定コマンド `\033*t{res}R` の取りうる値は `res300=0x02 / res600=0x03 / res1200=0x04` の 3 値のみで、2400 に対応するコードは存在しない(ppmtomd.c:288-289, 2489)。man ページは VPhoto を「可変ドット、誤解を招く形で 2400dpi と呼ばれる」印字と明記している(ppmtomd.man:481-483)。

**マニュアル側の裏付け:** 公式マニュアルの Print Quality は、Super が 16 階調・2400dpi・可変ドット、Fine が 4 階調・2400dpi・可変ドット、Standard が 600dpi と記載する(§13.3)。2400dpi は**可変ドットを用いる VPhoto 系モードに紐付く表記**であり、走査解像度ではない。

**二つの独立した情報源が同じ結論を示している。** カタログの 2400dpi は俗称である。

**確定方針:** 1200x600 を上限として実装する。VPhoto(可変ドット)は写真・昇華用途の機能であり、1bit プレーン前提(§4.2)の本用途では対象外。詳細は `docs/research/ppmtomd-survey.md` を参照。

**用途上の妥当性:** 1/12 のアイデカールにおいて、白目の幅を 5mm とすると 600dpi で約 118 ドット、1200dpi で約 236 ドット。階調は §4.2 により 1bit であるため、解像度が寄与するのは輪郭の滑らかさのみ。1200x600 で実用上十分と判断する。

#### 送出したデータと結果

| # | 内容 | サイズ | 結果 |

| 1 | 5mm 角ベタ黒(左 10.2mm / 上 36.0mm に配置) | 1493 B | 全量送出。無反応 |

| 3 | RGL に入り白紙 1 枚(描画なし) | 65 B | 全量送出。無反応 |

**いずれもエラーは発生していない。** ジョブは `Printing` のまま保持され、`DetectedErrorState` は 2(エラーなし)。紙もヘッドも動かず、異音もない。

#### 確定した事実

**送出側はシロである。**

- **自作ツール(RAW 直送)と Windows 標準経路(ドライバ経由)で症状が同一。** ツール固有の問題ではない
- **データ量・内容に関係なく同一の症状。** 1 バイトでも 64620 バイトでも変わらないため、コマンド列の解釈が原因とは考えにくい
- **スプーラは全量を送出済み**(`Size = 0` / `Status = OK`)
- **デバイスは正常**(`CM_PROB_NONE`)。機種名 `ALPS    MD-5000/T-04` を**現在も読み取れている**

#### 判明した運用上の事実

- **リボン未装着では即エラーになる。** 装着前は `DetectedErrorState = 1`(Other)。装着後に 2(エラーなし)へ変わった。**Windows は MD 固有のエラー原因を解釈できず Other に丸める**(§11.4 の裏付け)
- **給紙レバー A(自動)では給紙されなかった。** M(手差し)に切り替え、`ready / insert` ボタンを押して給紙できた。**A の条件は未解明**
- ppmtomd のコマンド列に**給紙モードの指定は存在しない**。給紙は本体のレバーで決まる

#### 残る原因の候補

1. **プリンタ本体側の実行条件が未達。** カートリッジの認識(§10.9.2 のバーコード)が済んでいない、あるいは何らかの操作待ちの可能性。エラーを出さずに待機する挙動と整合する
2. **USB の印刷データ経路が機能していない。** Phase 0 で確認したデバイス ID の読み取りは制御用の経路であり、**印刷データが流れる経路が生きている証拠にはならない**。制御側のみ生存している可能性

**§11.2 のタイミング問題は、まだ検証できていない。** データがプリンタに到達しているかが未確定であるため、タイミングの成否を論じる段階に達していない。

#### 追加試行と結論(同日)

**リボンを 4 本(CMYK 揃い)に増やしたところ、挙動が変わった。**

| 試行 | 結果 |
|---|---|
| リボン 1 本(黒のみ)で送出 | 完全に無反応。エラーも出ない |
| リボン 4 本にして同じデータを送出 | **赤ランプが点灯**(異常を表明した) |
| シアン 1 色に変えて送出(`printer_code` 0x01) | 無反応 |

**セルフテストを実行したところ、途中まで動作して停止した。** 給紙・ヘッド駆動・リボン送りは機能しており、印字も部分的に行われた。ただし**黒が印刷されていない**ことが判明。

#### 結論: 原因は機械または消耗品にある

**送出側はシロと確定した。** 5 パターン(黒 1493B / 排出のみ 1B / 白紙 65B / テキスト 64620B / シアン 1493B)を、自作ツール(RAW 直送)と Windows 標準経路(ドライバ経由)の双方で送出し、**内容・データ量・経路のいずれにも関係なく同一の症状**だった。

**決定打はセルフテストである。** ホストを一切介さない経路で実行しても途中停止する以上、**ホスト側の実装をどれだけ修正しても症状は変わらない**。

**§11.2 のタイミング問題は依然として未検証。** 機械が正常動作しない状態では判定できない。Phase 1 の再試行は、機械側の問題が解決してからとする。

#### 公式ドライバ側の失敗理由は判明した(2026-08-01)

**公式ドライバは専用ポート `MD_LPT1:` を使う設計だった**(§13.5.1)。日本語版マニュアルのすべての印刷ダイアログで確認できる。仮想 PC のポート一覧に `MD_LPT1:` は存在せず、`USB001` を指定したため「デバイスを識別できません」となったとみられる。

**したがって「公式ドライバでも印刷できない」は、経路の問題を示す証拠として弱い。** 公式ドライバが USB プリンタポートに対応していないだけの可能性がある。Foilwright は公式ドライバを使わないため、この制約は継承しない。

#### MD-5500 でも同一症状(2026-08-01 / 前提の見直し)

**D-017 により先行機を MD-5500 の USB 直結へ変更し、Phase 0 は成功した(§10.1.0)。しかし Phase 1 は MD-5000 とまったく同じ症状だった。**

| 条件 | MD-5000 | MD-5500 |
|---|---|---|
| 接続 | ELECOM UC-PGT(USB-パラレル変換) | 本体 USB 直結 |
| VID | 056E(ELECOM) | 044E(ALPS) |
| ポート | `USB002` | `USB003` |
| デバイス認識 | OK | OK |
| 送出結果 | 全量送出・無反応・エラーなし | **同左** |

**機体・ケーブル・接続方式のすべてが異なるのに挙動が同一である。** 共通するのは**送出しているバイト列と送出方法**のみ。

**§11.1.1 の「送出側はシロ」という判断は根拠が弱かった。** 当時の根拠は「データが欠落なく届いている」ことだったが、**届いていても実行されないなら意味がない**。またセルフテストの途中停止は黒リボンの不良が原因で、交換後は完走した — **その時点で「機械側の問題」という結論は崩れていた**。

**現在の最有力候補はバイト列そのもの。** golden との一致は「ppmtomd と同じバイト列である」ことの証明であって、**「そのバイト列で実機が動く」ことの証明ではない**。ppmtomd の既定オプションのまま採取しており、実運用で必須の指定が抜けている可能性がある(§10.10.4 のカール矯正停止など)。転送モード(`ESC * r 04 U` = colourPlane)が正しいかも未検証。

**次の一手は公式ドライバの出力の捕捉。** 推測を挟まずに差分を見られる唯一の方法。ただし現時点では実現していない(下記)。

#### 転送モードの検証(2026-08-03 / 未達)

**単色印刷には専用の転送モードがある**ことが判明したため検証した(§5.7)。私が送出していたのは `colourPlane`(0x04)で、黒 1 色でも CMY の空プレーンを伴う構造だった。`blackRaster`(0x00)は色選択コマンドもバックフィードも持たない最小構造である。

**`blackRaster` で送出しても症状は変わらなかった。** MD-5500 に 1488 バイトを送出し全量が受理されたが、機械は無反応でエラーも出ない。**転送モードは原因ではない。**

#### 送出方法はシロと確定(2026-08-03 / 決定的)

**Windows 標準のテストページと自作ツールの RAW 送出を同一条件で比較した。**

| | 自作ツール(RAW) | Windows テストページ |
|---|---|---|
| DataType | `RAW` | `NT EMF 1.008` |
| スプールサイズ | 0 | 52696 |
| ジョブ状態 | **Error** | **Error** |
| `DetectedErrorState` | **1 = Other** | **1 = Other** |
| `PrinterState` | **2(エラー)** | **2(エラー)** |

**両者ともまったく同じエラーになる。** 送出経路の違いは症状に影響しない。**自作ツールの `WritePrinter` 送出に問題はない。**

**「これまでエラーが出なかった」ことの説明もついた。** Windows はプリンタの状態を常時監視しておらず、**実際に印刷を試みたときだけ問い合わせる**。何も送っていない間は `DetectedErrorState = 2`(エラーなし)に見えるが、これは「確認していない」という意味でしかない。**送出直後の値だけが意味を持つ。**

**判定手順が確立した。** 送出後に `DetectedErrorState` を読めば、プリンタが受理したか拒否したかが分かる。**紙を消費せずに実行可否を判定できる。**

#### 障害箇所を特定: USB バルク転送が失敗している(2026-08-04 / 決定的)

**スプーラを完全に迂回し、`usbprint.sys` のデバイスインターフェースへ `WriteFile` で直接書き込んだ。**

```text
WRITE_FAILED  win32=31  written=0  elapsed=5006ms
```

- **win32=31 = ERROR_GEN_FAILURE**(接続されたデバイスが機能していません)
- **written=0** — 1 バイトも書けていない
- **elapsed=5006ms** — 5 秒でタイムアウト

**確定した事実:**

1. **ホスト側ソフトウェアは全層シロ。** 自作ツール・スプーラ・ポートモニタのどれでもなく、**OS 最下層のバルク OUT 転送がデバイスレベルで失敗**している
2. **制御転送とバルク転送で生死が分かれている。** デバイス ID の読み取り(制御転送)は成功、印刷データ(バルク転送)は全滅。「小さい通信は通るが大きい転送が通らない」
3. スプーラ経由の `Error, Printing, Retained` の正体はこれ。ポートモニタが書き込み失敗を受けてリトライし続けていた

**実施済みの切り分け(すべて同一結果):** カートリッジ 1 本 / 4 本、電源再投入(ランプ正常)、別 USB ポート(同一コントローラ内 Port 1 → 2)、テストページ(EMF)/ RAW、MD-5000(変換ケーブル)/ MD-5500(直結)。

#### 最有力仮説: xHCI ↔ USB 1.1 の相性(2026-08-04)

**MD-5500 は 1998 年設計の USB 1.1(Full Speed)機器で、Intel USB 3.0 xHCI コントローラのルートハブに直結されている**(`Port_#000x.Hub_#0001` = ROOT_HUB30)。

**xHCI ルートポートに USB 1.1 機器を直結すると、列挙は成功するのにバルク転送が失敗する相性問題が知られている。** 2 台の別々のプリンタ(MD-5000 + 変換ケーブル / MD-5500 直結)と 3 つの経路(自作 RAW / テストページ / 仮想 PC の公式ドライバ)がすべて同じ症状である事実は、「共通項 = ホスト PC の USB コントローラ」で最も自然に説明できる。仮想 PC の USB パススルーもホストの xHCI を経由する。

**検証方法: USB 2.0 ハブを間に挟む。** ハブの Transaction Translator が世代間の橋渡しをするため、xHCI からは High Speed のハブとしか通信しない。古い USB 機器の定番の回避策。**未実施(ハブの入手待ち)。**

#### 仮説の修正: Windows 11 の USB スタック退行(2026-08-04 / 最重要)

**決定的な証言が得られた。同じ PC で、OS が Windows 10 だった時代には MD-5500 で印刷できていた。**(2021 年ごろ。仮想 PC のイベントログにある 2021-01-28 のプリンタ構成記録とも整合する)

**これによりハードウェア相性説は棄却される。** USB コントローラ(Intel xHCI)は当時と同一で、その構成で印刷が成立していた。**変わったのは OS のみ(Windows 10 → 11)。**

**修正後の最有力仮説: Windows 11 の USB スタック(USBXHCI / usbprint)が、レガシー USB 1.1 プリンタへのバルク OUT 転送で退行している。** Windows 11 ではレガシー USB プリンタの印刷不能が既知の不具合として複数回報告されている(初期ビルドの USB 印刷問題は Microsoft が公式に認めていた)。現行環境は Windows 11 Home ビルド 10.0.26200。

**説明できる範囲が広がった:**

- ホスト側ソフト全層シロ・バルク OUT のみ失敗 → OS スタック内の退行と整合
- 2 台のプリンタ + 3 経路で全滅 → すべて同じ OS スタックを通る
- 電源管理無効化(EnhancedPowerManagementEnabled=0)が無効 → 電源管理より深い層の問題

#### Linux(usbipd + libusb)からの送出試行(2026-08-04)

**usbipd-win で MD-5500 を WSL2 へパススルーし、libusb(pyusb)でユーザー空間から直接バルク転送した。** カーネルの usblp は WSL2 標準カーネルに存在しないため、libusb 直叩き。なお物理層は Windows の xHCI ドライバを経由するため、**Windows の完全な迂回にはなっていない**(usbprint.sys は迂回している)。

**観測されたパターン(再現性あり):**

| 段階 | 結果 |
|---|---|
| 接続直後の制御転送(set_configuration / clear_halt) | **成功** |
| デバイス記述の読み取り | 成功(`Alps Electric Co., Ltd MD-5500 Printer`、Full Speed、双方向プリンタクラス、バルク OUT 0x01 / IN 0x82) |
| **バルク OUT 書き込み** | **即 STALL(EPIPE、0.0 秒)** — タイムアウトではなく能動的な拒否 |
| `clear_halt` で STALL 解除 → 再書き込み | 解除は成功するが、**書いた瞬間に再 STALL** |
| バルク失敗後の制御転送 | **ハングまたはエラー**(通信全体が崩壊し、物理再接続でのみ回復) |

**解釈:** プリンタは「一時的な詰まり」ではなく、**バルク OUT パケットを受けるたびに拒否する状態**にある。かつ最初の失敗後は USB インターフェース全体が応答不能になる。Windows で観測した「5 秒タイムアウト(win32=31)」はこの同じ現象の別の見え方とみられる。

**残る仮説(未決着):**

1. **Windows 11 xHCI ドライバの退行。** Full Speed バルク転送のスケジューリングが変わり、最初のパケットで転送異常 → デバイス側が混乱、というシナリオ。Win10 時代に同 PC で動いていた証言と整合。usbipd 経由でも物理層は同じドライバを通るため棄却できない
2. **プリンタ側が受信拒否状態。** ただし 2 台(MD-5000 / MD-5500)が同じ状態である必要があり、不自然さが残る
3. ~~**Alternate Interface の未選択。**~~ **検証の上で棄却(2026-08-04)。** 純正 USB ポートドライバの INF(`mdp_usb.inf`)に `DefaultAltInterface = 02` があり有力視したが、**実機の記述子には interface 0 / alternate setting 0 しか存在しない**(1 config・1 interface。pyusb で確認)。INF の値は alternate setting ではなく bInterfaceProtocol(02 = 双方向)の選択を指すとみられ、現 alt 0 が既に proto=02 で既定を満たす。明示的に `SET_INTERFACE(0,0)` を投げてもバルク OUT は 64 バイトすら即 STALL のままだった

#### 追加の切り分け(2026-08-04 第 2 回 usbipd 試行)

- **バルク IN も STALL する**(OUT だけではない)。両バルクエンドポイントが halt を張り続ける = **プリンタ FW がジョブ受け入れ不能状態を明示している**とみられる
- プリンタクラスの **SOFT_RESET(bRequest=2)もタイムアウト無応答**(前回の GET_PORT_STATUS ハングと同族。標準 control 要求のみ生きている)。SOFT_RESET → clear_halt(両 EP)→ OUT でも即 STALL
- `set_configuration` は Resource busy(カーネルが interface を claim 済み)
- IN の STALL を踏んだ直後は OUT の失敗モードが **EPIPE ではなく 5 秒タイムアウト(errno=110)に変わる** — Windows で観測した win32=31 / 5006ms と同じ顔。2 つの失敗モードは同一現象の遷移形
- 前回と異なり、今回はバルク失敗後も clear_halt が通り続けた(インターフェース崩壊は毎回ではない)

**決定打(残り):** ① **USB 2.0 ハブを挟む**(注文済み・到着待ち)。② **仮想 PC(VMware + 32bit 純正ドライバ)から MD-5500 直結で印刷を試み、ホスト側で USBPcap によりバス上のやり取りを採取する** — 成功すれば純正ドライバの初期化シーケンス(バルクが通るようになる手順)が丸ごと録れ、ベースドホワイトを含む全コマンドの実測にもなる。③ 別マシン(Windows 10 機・Raspberry Pi 等の素の Linux)から送出。

#### 決定的観測: バルク OUT は生きていた(2026-08-04 / USBPcap 採取)

**仮想 PC(VMware・Win8.1・32bit 純正ドライバ)から印刷を試み、ホスト側 USBPcap でバスを採取した(dumps/vm_print.pcap、348 パケット/MD-5500 分)。結論は上記 2 仮説をいずれも棄却する。**

- **ステータスモニタは 4 秒周期で `bulk OUT: 05 01`(2 バイト)を書き、`bulk IN` から 38 バイトのカセット状態を読んでいた — すべて成功。** つまり **Windows 11 の USB スタックはバルク OUT を通す**(退行説は棄却)。STALL は**データ内容依存**で、プリンタ FW が「解釈できない先頭バイト列」をエンドポイント halt で拒否していたと理解できる
- **純正ドライバは 5 分半のキャプチャ中、印刷データを 1 バイトも送っていない。** ジョブダイアログは出るがポーリングのみで、データ送出前の何かで待機していた(= 純正ドライバでも「印刷が始まらない」状態。機械側の受け入れ条件が満たされていない可能性)
- **`05 01` の再現に成功(usbipd + pyusb、2026-08-04)。** ただし単発 write のみでは IN がタイムアウト。**先に GET_DEVICE_ID(制御 `0xA1,0`)を打ってから `05 01` → IN** の順で完全再現(§11.4 参照)。**Windows 11 の xHCI 経由でバルク双方向が成立した瞬間** — これで「OS がバルクを壊す」説は完全に消える

**残る本命仮説(更新):** プリンタは**特定のオープニングシーケンス**(制御要求 → バルクの特定バイト列)を先に受けないと印刷ジョブのバルクストリームを受け付けない。ppmtomd 形式の生ジョブを何の前置きもなく投げていたのが STALL の原因。**次の解析対象は「純正ドライバが実際に印刷するときの先頭バイト列」** — 仮想 PC 側で印刷が始まる条件(おそらくカセット構成 or 用紙)を満たして再採取する。

#### 【この節の結論は下位節でさらに訂正される】内容依存プローブ第 1 報(2026-08-04)

**プリンタを仮想 PC からホストへ戻した直後に、書き込み内容を変えて総当たりした結果、これまでの理解が覆った。**

| 送ったバイト列 | 書き込み | 直後の IN 読み取り |
|---|---|---|
| `05 01`(ステータス問い合わせ) | **成功** | **成功(38 バイト)** |
| RGL 先頭 4 バイト(`1b 25 80 41`) | **成功** | EPIPE |
| `00 00`(無意味な 2 バイト) | **成功** | EPIPE |
| RGL 先頭 64 バイト | **成功** | EPIPE |

**バルク OUT は生の RGL バイト列を受け付ける。内容依存の拒否は存在しない。** フレーミング仮説も棄却(そもそもポートドライバはフレーミングを足していない — pcap 上で `05 01` が生の 2 バイトとして現れている)。

**EPIPE の正体は「応答が無いのに IN を読んだ」こと。** 印刷データは返事を返さないのが正常であり、そこで IN を読むと STALL する。**さらに悪いことに、この空読みを繰り返すとインターフェース全体がウェッジし、`clear_halt` も `reset()` も無応答になって物理再接続以外に回復手段がなくなる**(本節の観測 3 回すべてで再現)。

**過去の「バルク OUT が即 STALL」の観測はプリンタが既にウェッジ状態にあったための二次症状だったとみられる。** §11.1.1 冒頭の切り分け(2026-08-03〜04 前半)は、この状態で取られたもので、結論の前提が崩れている。

**運用規則(実装に反映すること):**

- **印刷データを書いた後に IN を読んではならない。** 読むのはステータス問い合わせ `05 01` の直後だけ
- ステータス問い合わせの前には **GET_DEVICE_ID(制御 `0xA1,0`)を打つ**(打たないと IN がタイムアウトする)
- ウェッジしたら**物理再接続**。ソフトからの復旧手段は現時点で無い

**ステータスの可変フィールドを 1 つ発見。** ヘッダ 5 バイト目が仮想 PC 稼働時の `00` から `10` に変化していた(`02 80 21 00 00` → `02 80 21 00 10`)。用紙・カバー・エラー等の状態ビットとみられる【推測】。状態を変えながら採取すれば意味を特定できる。

#### 確定: USB 経由では生の RGL を流せない。ポートレベルのコマンド層がある(2026-08-04 / モデル判別実験)

**上記「内容を選ばない」は誤りだった。書き込み API が成功を返すことと、プリンタがデータを受理することは別である。** 4 パターンの比較で決着した。

| 実験 | 結果 |
|---|---|
| A. `05 01` を 2 回、間に IN 読み取りあり(clear_halt なし) | **両方成功**(38 バイト応答 ×2) |
| B. `05 01` を 2 回、間に読み取りなし | **両方成功**(応答は後からまとめて読める) |
| C. RGL 先頭 64 バイトを書き、長めに読む | 書き込みは成功するが読み取りが **STALL** |
| D. C の直後にステータス問い合わせ | **リンク全死**(制御転送すら errno=110) |

**結論:** 正当なコマンド(`05 01`)は連続で何度でも通り、clear_halt も不要。**一方で生の RGL バイト列を書くとプリンタは直後にリンクごと落とす。** 「書き込み成功」はデータがプリンタのバッファに入っただけで、受理を意味しない — **halt は 1 転送遅れて現れる**ため、単発の書き込みだけを見ると成功に見えてしまう。

**含意(設計に直結):** MD-5500 の USB リンクは **RGL の生ストリームを受け付けない。** パラレル接続で通用する ppmtomd 形式のバイト列を、そのまま USB のバルクエンドポイントへ流す方式は成立しない。`05 01` と同じ体系の**ポートレベルのコマンド層**が存在し、印刷データもその中に載せる必要がある(あるいはデータ転送を開始させる前置きコマンドが要る)。これは §11.3 で「MD-5500 の USB 直結は標準 usbprint.sys が掴む楽なケース」と判断した前提を覆す — **掴めることと、素のデータが通ることは別だった。**

**回復手順(実測):** リンクが死んでも**物理再接続は不要**。`usbipd detach` → `attach` の往復でポートリセットがかかり、ステータス問い合わせが復活する(所要 10 秒程度)。実験の反復コストが大幅に下がった。

#### コマンド空間の総当たり結果(2026-08-04)

2 バイトコマンドを全数試し、バルク IN に応答を返すものを有効と判定した(リンクが死ぬたび `usbipd detach`/`attach` で自動回復させながら 32 + 48 通り)。

**先頭バイトは `05` のみが有効。** `00`〜`04` / `06`〜`0f` はすべて無応答かつリンク断。

| コマンド | 応答 | 内容 |
|---|---|---|
| `05 01` | 38 バイト | **カセット状態**(ヘッダ 5 + 11 スロット×3。§11.4) |
| `05 02` | 256 バイト | 機体情報。`02 80 00 10` に続き ASCII `27P40475I0,` — 製造番号・ファーム識別とみられる【推測】 |
| `05 03` | 256 バイト | `a9 00` の反復。用途不明 |
| `05 04` | 256 バイト | 数値表(`ae 01 c2 01 d6 01 ...`)。リボン残量またはキャリブレーション値か【推測】 |
| `05 00` および `05 05`〜`05 29` | 1 バイト `04` | **未サポート応答**とみられる |

**重要な帰結: このコマンド体系に印刷データを流す口が見当たらない。** 有効なのは 4 つの読み出しクエリのみで、書き込みチャネルが存在しない。**したがって印刷データの送出方法は、単純な 2 バイトコマンドの延長線上にはない** — 長さフィールドを伴うパケット形式か、あるいは別の前置きシーケンスが必要と考えられる。

**次の作業(優先順):** ①**純正ドライバに実際に印刷させて USBPcap で捕捉する**(最も確実。仮想 PC で印刷が始まらなかった原因は用紙未装填の可能性がある — ステータス 5 バイト目が仮想 PC 稼働時 `00`、用紙投入後とみられる現在 `10` に変化している)。②ポートモニタ(`mdp_usb.dll` / `mdp_pm9x.dll`)およびランゲージモニタ(`AL21LMON.DLL` / `ALLGM321.DLL`)の静的解析でパケット構築コードを特定する。

**検証手段(効果が見込める順):**

1. **usbipd-win + WSL2。** MD-5500 を Linux 側へパススルーし、Linux の USB スタックから送出する。**この PC だけで完結し、Windows 11 のスタックを完全に迂回できる。** 動けば OS 退行説が確定し、当面の印刷手段にもなる
2. **USB 2.0 ハブを挟む。** スタックが変わっても転送スケジューリングが変わるため、依然として効く可能性がある
3. Windows 10 機があればそこから送出(決定的だが機材依存)

**なお §11.1.1 で前回「機械側の実行条件」とした 3 候補(カートリッジ構成・認識・異音)は、カートリッジ関連が今回の切り分けで棄却された。** 異音は別個の問題として残る。

#### 残る原因は機械側の実行条件(2026-08-03 / 上記により更新)

**プリンタは通信に応答し、MD 固有のエラーを返して拒否している。** Windows は中身を解釈できず `Other` に丸めるが(§11.4)、**拒否そのものは明確に検知できる。**

黒リボン 1 本を装着した状態でも解消しなかった。候補は次の 3 つ。

1. **カートリッジ構成が不足している。** §13.5.6 のとおり公式ドライバは装着済みカートリッジを双方向で確認する。MD-5000 でも 1 本のときは無反応、4 本にすると挙動が変わった(§11.1.1)
2. **カートリッジの認識に失敗している。** バーコードが読めない・装着が不完全・リボン自体の不良(§10.9.2)
3. **異音の原因が未解消。** 機構的な問題が残っている可能性

**送出側で打てる手は尽きた。** 実装は golden と一致し、送出経路も Windows 標準と同一の結果を返す。**次は機械の実行条件を整える段階。**

#### 送出方法そのものが未検証(2026-08-03 / 上記により解決)

**これまでの全試行が同一の送出方法を使っていた。** `WritePrinter` による RAW 送出で、成功の根拠としてきた「N / N バイト送出完了」は**スプーラが受理したこと**しか示さない。**スプーラからプリンタへの最終区間は一度も検証していない。**

**傍証:** ジョブが常に `Printing, Retained` のまま残り、一度も消化された状態にならない。正常完了なら保持設定があっても状態は変わるはずである。

**次に検証すべきこと:** Windows 標準のテストページ印刷。自作ツールを一切通らない経路で紙が動くかを見れば、送出方法の問題か経路の問題かが切り分けられる。**未実施**(実機の異音により中断。下記)。

#### MD-5500 の異音(2026-08-03 / 実機停止)

**セルフテストを実行しようとしたところ異音が発生し、エラー状態になった。** 中止条件に該当するため電源を切り、実機の使用を停止した。

**§10.9.5 の外部事例と符合する可能性がある** — 紙押さえ用スプリングの曲がりによるヘッドとの干渉で異音が出た事例が報告されている。原因は未特定。

**実機での検証は当面できない。** MD-5000 も Phase 1 が通っていないため、**実機に依存しない調査へ切り替える。**

#### 公式ドライバの出力を捕捉する試み(未達 2026-08-01)

32bit 仮想 PC の公式ドライバでポートを `FILE:` に設定して印刷したところ、**保存先を尋ねるダイアログは表示されるが、生成されるファイルは 0 バイト**だった。

**ドライバは印刷処理を開始しているが、1 バイトも書かずに中断している。** §13.5.1 のとおり公式ドライバは専用ポート `MD_LPT1:` を前提としており、**出力先が `FILE:` であってもプリンタの存在確認に失敗して打ち切っているとみられる。**

**次に確認すること:** ALPS のポートモニタが導入されているか(プリンタのプロパティ → ポート → ポートの追加 の一覧)。導入されていれば `MD_LPT1:` を作成でき、ドライバが正常に動作する可能性がある。未導入ならドライバ一式の再インストールが必要。

#### MD-5500 で異音が発生(2026-08-03 / 中止)

**セルフテストを実行しようとしたところ異音が発生し、エラー状態になった。中止条件に該当するため電源を切って停止した。**

**それ以前に blackRaster モードでの送出も試したが無反応だった**(§11.1.1 の切り分け)。転送モードの違いは原因ではない。

**外部事例との符合。** §10.9.5 に記録した MD-5500 の故障事例では、紙押さえ用スプリングの曲がりとヘッドの干渉により異音が発生していた。同種の可能性がある。**機械の状態を確認するまで通電しない。**

**この時点で実機による検証は停止した。** 以降はエラー状態の読み出し(§11.4)を先に実装し、原因を機械から直接聞き出す方針へ切り替える。

#### 機械側の候補

- **黒カートリッジの不良・消耗・装着不良**(他の色は印字されているため、黒固有の問題の可能性が高い)
- ヘッドの部分的な劣化(§10.9.5 に 6 年使用でヘッド交換した外部事例あり)
- カートリッジのバーコード読み取り不良(§10.9.2)

#### エラー原因はホストから読み出せなかった(§11.4 の実証)

赤ランプ点灯時に Windows が報告した状態は `DetectedErrorState = 2`(エラーなし)であり、**実機の異常を検知できていない**。試行した 2 経路はいずれも失敗した。

| 経路 | 結果 |
|---|---|
| `ReadPrinter`(スプーラ経由の双方向読み出し) | Win32 error 6(無効なハンドル) |
| ポート `USB002` への直接オープン | 失敗。`usbprint.sys` が排他的に保持している |

**§11.4 が「現行 L0 では双方向でポートを開けない」と予測していたとおりの結果。** 読み出しには `usbprint.sys` を迂回して WinUSB 等でエンドポイントを直接開く必要があり、これは L0 の作り直しに相当する(§11.0 の 4 件が帰着する同一判断)。

**本節は §11.4 の課題が机上の懸念ではなく実際の障害であることの記録として扱う。**

**何も破損していない。** 異音・紙詰まりは発生していない。

### 11.2 タイミングに関する既知のリスク

**これは本プロジェクトで最も重大な未確定リスクである。**

公式ドライバは ALPS 専用の仮想 LPT ポートを介して双方向通信を行う。専用ポートを実装しているという事実は、標準のポート経由では満たせない要件が存在した可能性を示唆する。

**懸念:** プロトコルが厳しいタイミング要求を持つ場合、スプーラを経由しバッファリングされる本構成では要求を満たせない可能性がある。これは実装の巧拙ではなく Windows 印刷スタックの構造的性質に起因するため、回避が困難である。

**判明時期:** Phase 1(5mm 角のベタ 1 色を 1 枚)で判明する。この試験には経路全体のタイミング検証が含まれる。

**設計上の位置づけ:** 本リスクが顕在化した場合、仮想プリンタ方式そのものが成立しない。したがって Phase 1 は単なる動作確認ではなく、**プロジェクトの成否を決める関門**として扱う。Phase 1 以前に UI やトレイアプリの作り込みを進めない。

**回避策の候補(顕在化した場合のみ検討):**

- トレイアプリ側でバイト列を一括保持し、送出のみ連続実行する(既に §3.5 の二段構成でこの性質を持つ)
- 送出をリアルタイム優先度のスレッドで行う
- それでも不足する場合、方式の再検討が必要になる

### 11.3 MD-5500 の USB 直結対応(Phase 4)

**対応する意思はある。実装時期を Phase 3 成立後に置く。**

#### 状況

MD-5500 は本体に USB ポートを持つが、既知の実装はいずれもこれを使用していない。コミュニティ製ユーティリティは MD-5500 を含む全機種で USB-パラレル変換ケーブル経由とし、USB 直結を明示的に非対応としている。

**この理由が判明していないため、難易度を見積もれない。** 理由の候補:

1. 技術的な壁。ベンダ独自プロトコルで、公式ドライバの解析を要する
2. 実利がない。全機種対応が目的なら経路を統一するほうが保守が容易
3. 単に不要だった。既存ユーザーは変換ケーブルを所持している

**2 が最も蓋然性が高いと推測するが、1 を排除する材料がない。**

#### 難易度の二分岐

| ケース | 条件 | 影響 |
|---|---|---|
| 楽 | USB Printer Class 準拠。`usbprint.sys` が掴み `USB001` として見える | L0 の送出方法は現行とほぼ同一。対応は軽微 |
| 重 | ベンダ独自インターフェース | WinUSB / libusb でエンドポイントに直接書き込む。**L0 に別実装が生える**。Generic / Text Only 経由の出口が使えない |

#### 判定方法

実機の USB ポートを PC に接続し、デバイスマネージャで以下を確認する。**所要時間は数分、実機リスクなし。**

- プリンタとして認識されるか、不明なデバイスになるか
- ハードウェア ID(`USB\VID_xxxx&PID_xxxx`)
- デバイスクラス(Printer / ベンダ固有)

#### 実装時期を Phase 3 以降とする理由

経路が 2 本ある状態で Phase 1 を実施すると、失敗時の原因候補が倍になる。§11.2 のタイミングリスクを検証する段階では、**経路は 1 本でなければならない。**

パラレル経路で確実に印刷できる基準線を確立してから、USB を第二の経路として追加する。この順序を崩さない。

#### 設計上の備え

L0 は将来 2 系統の送出方法を持ちうる。§4.8 に従い、現時点で分岐を実装しないが、インターフェースを送出方式に依存した形に固めない。

### 11.4 エラー状態の読み出し(Phase 4 以降)

**公式ドライバが実現していた機能であり、対応する意思はある。**

#### 状況

本体前面の警告ランプは異常の発生のみを示し、原因(用紙切れ / リボン切れ / カバー開放 等)を区別しない。公式ドライバが原因を提示できていたことは、**プリンタへ問い合わせて応答を受け取っていたこと**を意味する。

#### ポートは開けたが、状態は取れていない(2026-08-03)

**前進 1 件、未達 1 件。** `usbprint.sys` を迂回せずにデバイスを開くことには成功したが、**返る値がプリンタの実状態を反映していない。**

**取得した値は常に `0x01` で固定。** 次の 4 条件すべてで同一だった。

| 条件 | STATUS |
|---|---|
| 異音の発生直後(エラー状態) | 0x01 |
| リボンを全て外した後(エラー解消) | 0x01 |
| USB 再接続の直後 | 0x01 |
| **カバーを開けた状態** | **0x01** |

**カバー開放でも変わらない時点で、状態を読めていないと判断した。** Windows 側も同時刻に `DetectedErrorState = 2`(エラーなし)を報告しており、**ホストは MD のエラーを一切検知していない。**

**`0x01` という値自体が不自然。** USB プリンタクラスの GET_PORT_STATUS ではビット 0 は予約で、意味を持つビット(用紙・オンライン・エラー)がすべて 0 なのに予約ビットだけ立っていることになる。

**もう一方の IOCTL も失敗している。** `IOCTL_USBPRINT_GET_1284_ID`(0x220050)は `win32=87`(引数不正)。**呼び出し方に問題がある可能性が高く**、状態取得のほうも「成功を返すが実際には何もしていない」状態とみられる。

**未解決の候補:** IOCTL コードの誤り / 入力バッファの要否 / `METHOD_BUFFERED` 以外の転送方式 / そもそも `usbprint.sys` が該当 IOCTL を実装していない。

**確実な代替は WinUSB への差し替え。** USB 制御転送で GET_PORT_STATUS を直接送れる。ただし**印刷経路が一時的に使えなくなる**ため、実施は慎重に判断する。

#### 収穫: L0 の作り直しは不要かもしれない

**`usbprint.sys` が掴んだままデバイスを開けた**(`CreateFile` が成功)。§11.0 は「双方向で開くには L0 をポート直叩き方式へ移行する必要がある」としていたが、**少なくとも「開く」ことに関してはドライバの差し替えを要さない。**

正しい命令さえ見つかれば、**現行の印刷経路を維持したまま状態を読める見込みがある。** §11.0 の 4 件が同一判断に帰着するという構造は、この点では緩む可能性がある。

**実装:** `tools/read-port-status.ps1`。レジストリの `DeviceClasses` からデバイスインターフェースのパスを取得し、`CreateFile` で開いて `DeviceIoControl` を発行する。

| IOCTL | 値 | 結果 |
|---|---|---|
| `IOCTL_USBPRINT_GET_LPT_STATUS` | 0x22004C | **成功** |
| `IOCTL_USBPRINT_GET_1284_ID` | 0x220050 | 失敗(win32=87 = 引数不正)。呼び出し方の調整が必要 |

**デバイスパスの組み立てに注意。** レジストリのキー名は `##?#USB#VID_...#serial#{guid}` 形式で、**先頭の `##?#` だけが `\\?\` に対応し、以降の `#` はそのまま残す。** すべての `#` をバックスラッシュに置換すると開けない(`win32=3`)。

**返る 1 バイトの構造**(USB プリンタクラス仕様の GET_PORT_STATUS):

| ビット | 意味 |
|---|---|
| 5 (0x20) | Paper Empty。1 = 用紙なし |
| 4 (0x10) | Select。1 = オンライン |
| 3 (0x08) | Not Error。**0 = エラー発生中** |

**§11.0 の想定を覆した。** 「双方向でポートを開くには L0 の作り直しが必要」としていたが、**`usbprint.sys` を迂回せずに読めた。** WinUSB へのドライバ差し替えは不要。エラー読み出しのために L0 の方式変更を迫られる、という前提は成立しない。

#### MD-5500 の実測値(2026-08-03)

異音の発生後、紙とリボンを抜いた状態で読み取った値。

```text
STATUS=0x01  paperEmpty=0  select=0  notError=0
```

**当初この値を「オフラインかつエラー発生中」と解釈したが、撤回する。** 同じ値がカバー開放時にも返るため(上記)、**ビットの意味を読み取れているとは言えない。**

**Phase 1 の原因究明には使えなかった。** 状態が変化しても値が動かない以上、この読み取りからは何も判断できない。

**副次的な事実:** Windows の標準 API(`DetectedErrorState`)も、カバー開放という明確なエラーを検知していない。**汎用ドライバ経由では MD のエラーは一切ホストに伝わらない**ことが確認できた(§11.4 の課題設定を裏付ける)。

#### 解決: 状態読み出しはバルクの独自プロトコルだった(2026-08-04 / USBPcap + 再現成功)

**IOCTL や GET_PORT_STATUS は全て的外れだった。** 純正ステータスモニタの通信を USBPcap で採取したところ(§11.1.1 の pcap)、**状態取得は USB プリンタクラスの標準機構ではなく、バルクエンドポイント上の ALPS 独自 2 バイトプロトコル**だった。

**手順(実測・再現成功):**

1. 制御転送 **GET_DEVICE_ID**(`bmRequestType=0xA1, bRequest=0, wLength=512`)で IEEE-1284 デバイス ID 文字列を取得(下記)。**これを先に打たないと次の IN がタイムアウトする**(順序依存)
2. **バルク OUT に `05 01`(2 バイト)を書く**
3. **バルク IN から 38 バイトのカセット状態を読む**

```text
GET_DEVICE_ID → "MANUFACTURER:ALPS   ;COMMAND SET:RGL;MODEL:MD-5500_T-03   ;
                 CLASS:PRINTER;COMMENT:TH,CC,S,240,600/I,0;ACTIVE COMMAND SET:..."
bulk OUT 05 01
bulk IN  02 80 21 00 00 | ff 00 00 | 03 00 00 | 01 00 00 | 00 00 00 | 00 00 ff |
         00 00 02 | 00 00 ff | 00 00 ff | 00 00 ff | 00 00 00 00 00 00 00 03
```

**応答 38 バイトの構造(判明分):**

- 先頭 5 バイト = ヘッダ(`02 80 21 00 00`)
- 続く 8 スロット × 3 バイト = **上段ホルダ 4 + 下段ホルダ 4**。各スロットの先頭バイトが**カセットのバーコード番号**(§13.7.5 の対応表そのもの)。`ff`=未装着
- 採取時の実機構成(上段: 未装着 / シアン=03 / イエロー=01 / ブラック=00、下段: 未装着 / マゼンタ=02 / 未装着 / 未装着)と**完全一致**。純正モニタの「リボン情報」タブの表示とも一致
- 末尾 9 バイトはリボン残量等とみられる(`[??%]` 表示 = 未取得。§13.7.3 の "Ribbon Remainder" に対応か)【推測】

#### 状態応答の構造を訂正 + エラー時の値(2026-08-04 / 給紙エラー中に採取)

**レコードの解釈が誤っていた。** 38 バイトの応答は「ヘッダ 5 + 3 バイト × 11」だが、**カセットは 9 個(ホルダ 8 + ヘッド 1)しか存在しない。** 給紙エラー中に採取した応答と正常時を突き合わせたところ、**rec[9] と rec[10] はカセットではなく状態フィールド**であることが判明した。

```text
正常   02 80 21 00 00 | ff 00 00 | 03 00 00 | 01 00 00 | 00 00 00 | ff 00 00 |
                        02 00 00 | ff 00 00 | ff 00 00 | ff 00 00 | 00 00 00 | 00 00 03
エラー 02 80 21 00 c9 | ff 00 00 | 03 31 00 | 01 8d 02 | 00 8d 02 | ff 00 00 |
                        02 3f 00 | ff 00 00 | ff 00 00 | ff 00 00 | 00 10 00 | 86 00 03
```

| 位置 | 正常 | エラー | 解釈 |
|---|---|---|---|
| ヘッダ 5 バイト目 | `00` | **`c9`** | 状態バイト |
| rec[0]〜rec[7] | — | — | 上段 4 + 下段 4 のホルダ |
| rec[8] | — | — | ヘッドに装着中のカセット |
| rec[9] の 2 バイト目 | `00` | **`10`** | 用途不明。エラー時にのみ値が入る |
| rec[10] の 1 バイト目 | `00` | **`86`** | **エラーコードの可能性が高い**【推測】 |

**カセットのレコードの 2〜3 バイト目の意味は未解明。** 当初「リボン残量」と解釈したが、**後の実測で否定された。**

印刷前(すべてゼロ)→ 印刷後(値が出現)まではリボン量と整合したが、**純正ドライバで 1 枚印刷した前後で値が非単調に変化した。**

| バーコード | 対象 | 純正で刷る前 | 純正で刷った後 |
|---|---|---|---|
| `0x03` | 紙用シアン | 49 | 49 |
| `0x02` | 紙用マゼンタ | 63 | 61 |
| `0x01` | 紙用イエロー | **653** | **79** |
| `0x00` | 紙用ブラック | **653** | **114** |

**累積使用量なら減ることはなく、残量なら 653 → 79 という急減を 1 枚の印刷で説明できない。** この間にカルーセルが回転してカセットの位置が変わっているため、**リボン量ではなくカセットの回転位置やリボンの繰り出し位置を表している可能性がある**【推測】。

§13.7.3 の純正ドライバに "Ribbon Remainder" の文字列は実在するが、**この 2 バイトがそれに当たるという裏付けは無い。** 純正ドライバの残量表示は `[??%]` のまま値が出ないことも観測されており(§13.7.3)、別の経路で取得している可能性がある。

**§7.2 の「リボン残量表示」は、この値の意味が確定するまで実装しないこと。** 誤った数値を利用者に見せると、消耗品の判断を誤らせる。

#### 状態バイトはビットフラグ + カセット消失の観測(2026-08-04)

**3 つの状況を突き合わせて、状態バイトの分解に裏付けが取れた。**

| 状況 | 状態バイト | rec[9] | rec[10] |
|---|---|---|---|
| 待機 | `0x00` | `00 00 00` | `00 00 03` |
| **給紙エラー**(印刷動作の途中で失敗) | **`0xc9`** | `00 10 00` | `86 00 03` |
| **カセット消失**(印刷を始める前に失敗) | **`0xc0`** | `80 00 00` | `00 10 03` |

**`0xc9` = `0xc0`(エラー)+ `0x09`(印刷実行中)** と読める。給紙エラーは印刷動作に入った後に発生し、カセット消失は印刷を始める前に発生したため印刷中ビットが立っていない。**状態バイトはビットフラグの集合である**という見立てに実測の裏付けが得られた。

**カセット消失の観測:** blackRaster(黒 1 色)のジョブを送出したところ、**送出直前まで存在していたブラック(バーコード `0x00`)がエラー時には `0xff`(未装着)に変わっていた。**

```text
印刷直前 rec[0]=03 rec[1]=02 rec[2]=01 rec[3]=00  ← ブラックあり
エラー時 rec[0]=03 rec[1]=02 rec[2]=01 rec[3]=ff  ← ブラックが消えた
```

**プリンタが使おうとしたインクが、その瞬間に検出されなくなっている。** カルーセルの回転中にカセットが浮いた、あるいはバーコードの読み取りに失敗した可能性がある【推測】。

**【訂正】`rec[9]` の先頭バイト `0x80` はエラー種別を識別しない(2026-08-08)。**

2026-08-04 に「`0x80` = ペーパーフィードメカニズム異常」と確定したと記録したが、**誤りだった。**

MD-5000 で純正ドライバが **「キャリッジメカニズムに異常が発生しました」** を表示している最中に採取したところ、**同じ機体で「ペーパーフィードメカニズムに異常」が出ていたときの応答と 1 バイトも違わなかった。**

```text
給紙エラー時    02 80 21 00 c0 ... 80 00 00 | 00 40 03
キャリッジエラー時 02 80 21 00 c0 ... 80 00 00 | 00 40 03   ← 完全一致
```

**当初の判断が誤った理由:** MD-5500 で 1 例だけ突き合わせて確定と結論した。**1 例では「その値がその意味である」ことは示せても「その意味だけを表す」ことは示せない。** 別種のエラーで同じ値が出るかを確かめていなかった。

**現時点で言えること:**

| 観測 | 解釈 |
|---|---|
| 状態バイト `0xc0` | **何らかのエラー**(種別は不明) |
| rec[9] 先頭 `0x80` | **機構系のエラーであること**までは示すとみられる【推測】 |
| rec[10] 2 バイト目 `0x10` / `0x40` | 機種で異なる。エラー種別ではない(同一機体で種別が変わっても不変) |

**§13.8.3 のとおり機構エラーは 8 種類あるが、`05 01` の応答はそれらを区別していない。** 純正ドライバは別の手段で種別を得ているはずで、**その経路は未解明**である。候補は「印刷中のデータチャネルの応答」「未知のクエリコマンド」など。**USBPcap で純正がエラーを表示する瞬間を採取すれば判明する。**

**実装への反映:** 状態表示は **「機構に異常が発生しました(種別は特定できません)」** のように、**分かっていないことを分かっていないと出す**。特定の機構名を出してはならない — 利用者が誤った箇所を点検することになる。

**この対応付けは、こちらのソフトが利用者へ日本語で正確な原因を提示するための土台になる**(§7.2 のプリンタ状態表示)。純正と同じ文言を出せる。

**この異常状態では状態応答が更新されない(2026-08-05 に確認)。** インクリボンを物理的に取り外した後に採取したところ、**取り外す前の応答と 1 バイトも違わなかった。**

```text
リボン装着時 02 80 21 00 c0 03 31 00 02 3d 00 01 4f 00 ff ... 80 00 00 00 10 03
リボン取外後 02 80 21 00 c0 03 31 00 02 3d 00 01 4f 00 ff ... 80 00 00 00 10 03  ← 完全一致
```

給紙機構の異常でプリンタが停止しているため、**カセットの再スキャンが行われず、最後に読んだ情報を返し続けている。**

**実装への含意(重要):**

- **エラー状態でのカセット情報を信用してはならない。** §7.3 のカセット過不足の判定は、**状態バイトが正常(エラービットが立っていない)ときの応答に限って有効**である
- エラー中に「必要なインクが無い」と表示すると、**現物と食い違う指示を利用者に出すことになる**。エラー時はまずエラー自体の解消を促す
- 先に「ブラックのカセットが消えた」と解釈したのも、この停止によるもの。**物理的な消失ではなかった**

**重要な含意:** 純正ドライバでも同じエラーが出る。**この異常はホスト側ソフトの問題ではなく、プリンタの給紙機構そのものの状態である。** 今日 1 本目のジョブが「全バイト受理されたのに給紙で失敗」した時点から継続していたとみられる。

**未解明のまま残る課題:** この状態から機構をホーム位置へ戻す手段。純正のステータスモニタには「中断」ボタンがあるため手段は存在するはずで、**その操作を USBPcap で採取するのが次の一手**(§15.2.2 の宿題と同じ)。取り消しコマンドが分かれば、エラー時にカセットをヘッドへ取り残さずに復帰できる。

**実装への含意:** §7.3 のカセット過不足の判定は、**ジョブの送出直前だけでなくエラー発生時にも読む**必要がある。「送出前には存在したインクが、実行時に消える」ことが実在するため。

#### MD-5000(パラレル + 変換ケーブル)での実測(2026-08-07)

**状態問い合わせはパラレル経路でも通る。** D-025 で「未検証」としていた項目が解決した。変換ケーブル(VID `056E`)経由で `05 01` を送ると 38 バイトの応答が返る。**プロトコルの読み出し側は経路に依存しない。**

```text
02 80 21 00 c0 | 00 72 00 | 03 32 00 | 02 3f 00 | 01 31 00 | ff 00 00 | ff 00 00
                 ff 00 00 | ff 00 00 | ff 00 00 | 80 00 00 | 00 40 03
```

**クエリの対応範囲に機種差がある。**

| コマンド | MD-5500 | MD-5000 |
|---|---|---|
| `05 01`(カセット状態) | 38 バイト | **38 バイト** |
| `05 02`(機体情報) | 256 バイト | **`04` = 未サポート** |
| `05 03` | 256 バイト | **`04` = 未サポート** |
| `05 04` | 256 バイト | **`04` = 未サポート** |

**したがって `05 02`〜`05 04` に依存する機能を作ってはならない。** MD-5000 では取得できない。

**エラーの表現は共通。** 状態バイト `0xc0`・rec[9] の先頭 `0x80` は MD-5500 でもMD-5000 でも同一の値が観測された。**ただしこの組み合わせは「機構のいずれかに異常」を示すだけで、種別は識別しない**(§11.4 の訂正)。同じ値がペーパーフィード異常でもキャリッジ異常でも出ることを実測で確認している。

**末尾のレコードには差がある** — MD-5000 は `00 40 03`、MD-5500 は `00 10 03`。rec[10] の 2 バイト目が `0x40` と `0x10` で異なる。意味は未解明。

**注意:** 2 台の別々のプリンタが同じ「ペーパーフィードメカニズム異常」を示している。**個別の故障が偶然重なったとは考えにくく、共通する条件を疑うべきである。** 現時点では未解明。

**潰した仮説(2026-08-07):**

| 仮説 | 結果 |
|---|---|
| 用紙が装填されていない | **否定**。装填しても変わらない |
| 給紙切換レバーの位置(A / M) | **否定**。M に切り替えて ready/insert を押しても給紙しない |
| 本体内部に用紙が残留している | **否定**。カバーを開けて確認、紙は無かった |
| こちらのソフトが原因 | **否定**。純正ドライバでも同じエラーが出る(MD-5500 で確認) |

**残る候補:** 機構そのものの故障(§13.8.3 のとおり機構エラーは 8 種類あり、状態バイトだけでは区別できない)、あるいは 2 台に共通する環境要因。**この手は既に試して決着した(2026-08-08)。** 純正ドライバで MD-5000 を動かし「キャリッジメカニズムに異常」を表示させた状態で採取したが、**ペーパーフィード異常時と応答が 1 バイトも違わなかった**(§11.4 の訂正)。**状態応答から機構エラーの種別は得られない。**

**2 台のエラー応答をバイト単位で比較した(2026-08-07)。** カセットの内容以外で異なるのは **rec[10] の 2 バイト目だけ**である。

| | MD-5500 | MD-5000 |
|---|---|---|
| 状態バイト | `0xc0` | `0xc0`(同一) |
| rec[9] 先頭(エラー種別) | `0x80` | `0x80`(同一) |
| **rec[10] の 2 バイト目** | **`0x10`** | **`0x40`** |

**エラー種別が同一で、ここだけ機種で違う。** 機種の識別子か、エラーの副次的な詳細を表す可能性がある【推測】。正常時は両機種とも `0x00` であり(§11.4 の採取一覧)、**エラー時にのみ値が入る**点は rec[9] と共通する。

**副次的な観測:** MD-5000 のカセットレコードの 2 バイト目に値が入っている(`0x72` / `0x32` / `0x3f` / `0x31`)。**7 月以来使っていない機体であるにもかかわらず値が残っている**ということは、**前回の使用時の情報がプリンタ側に保持されている**ことを意味する。§11.1.1 で「うんともすんとも言わない」と記録した当時、**既に給紙機構が異常だった可能性**を示唆する【推測】。当時は状態を読む手段が無かったため確認できていない。

**状態バイトの既知の値(すべて実測):**

| 値 | 観測された状況 |
|---|---|
| `0x00` | 待機 |
| `0x01` | ジョブ完了直後 |
| `0x09` | **印刷実行中** |
| `0x10` | 待機(別の場面) |
| `0xc0` | ジョブ送出の直前 |
| `0xc9` | **給紙エラー中**(用紙送りに失敗しエラーランプ点灯) |

`0xc9` は `0xc0` と `0x09` の重ね合わせに見え、ビットフラグの集合である可能性が高い【推測】。**採取は `tools/probe-status.ps1` で行い、`dumps/status-probe.log` へ追記される。** 物理状態を変えながら採取して突き合わせれば意味を確定できる。

**含意:** §11 #9(エラー状態の読み出し可否)は**可能と確定**。L0 の作り直しも WinUSB 差し替えも不要 — バルクエンドポイントに 2 バイト書いて 38 バイト読むだけ。§7.2 のプリンタ状態表示に流し込める。**ただし現状 usbprint.sys が interface を claim しているため、印刷経路と同時には開けない**(排他)。状態取得と印刷の両立は L0 設計時の課題(§11.5 と同じく「握り直し」の一部)。

#### 成立に必要な条件

| 条件 | 状態 |
|---|---|
| 双方向対応の変換ケーブル | **確保済み**(ELECOM UC-PGT。§10.1.1) |
| 双方向でポートを開く経路 | 現行 L0 では不可(§11.0) |
| エラーコードの解読 | 手がかりあり。下記参照 |

**物理層の前提はクリアした。** ケーブルは双方向対応であり、MD-5000 はデバイス ID を返す(§10.1.1)。単方向ケーブルなら機能が物理的に成立しないという懸念は解消した。**残る障害は L0 の実装方式のみ** — 現行は Windows の印刷スタックに送出を委ねており、その時点で応答を受け取る手段を手放している(§11.0)。

#### 解読の手がかり

ppmtomd の作者が双方向でのステータス監視に取り組んでおり、監視用スクリプトを公開している。ドキュメントは付属しないが、プロトコルを扱う箇所は読解可能であると本人が記している。**エラーコードの意味を特定する第一の情報源はここ。**

#### 現時点で行うこと

1. **L0 を送信専用に固めない**(§4.8)
2. **トレイアプリに状態表示の枠を確保する**(§7.2-6)。内容は空でよい
3. **代替手段を機能させておく**

#### 代替手段(双方向が使えない場合)

§4.6 のバイト列ダンプにより、**どのジョブのどのパスまで送出したかは特定できる。** 異常の原因は判明しないが、発生位置は分かる。

完全な代替にはならないが、**何も分からない状態は回避できる。** 双方向が最後まで確保できない場合でも、この水準は維持する。

### 11.5 全パスを 1 ジョブとして送れるか【最優先】

**本プロジェクトが公式ドライバを超えられるかどうかが、この一点にかかっている。**

#### 課題

§4.10 のとおり、排出は最終パスの後に 1 回だけでなければならない。しかし現在の L0 はスプーラにバイト列を委ねる方式であり、**ジョブの境界をスプーラが決める。** 白のパスと色のパスが別ジョブに分割されれば、その間で用紙が排出され、§10.6 と同じ失敗を再現する。

#### 既に確定していること(§10.6)

- 保持機構は正常に機能する
- 1 ジョブ内の多パス動作も正常に機能する
- **したがって未確定なのは機器側ではなく、ホスト側でジョブをどう構成するかだけである**

#### 判定手順

1. **golden(白版を含む多層)を採取し、排出コマンドの出現回数を数える**(§9.3)。実機不要。ppmtomd が 1 ジョブで多パスを構成しているかがここで分かる → **完了(下記)**
2. 1 回であれば、そのバイト列構造をそのまま L1 の出力仕様とする → **この段階に進んだ**
3. Phase 1 で、スプーラ経由で送出した際にその構造が保たれるかを実機確認する → 未実施

#### 手順 1 の結果(2026-07-28)

**プロトコル側は 1 ジョブ多パスで構成できる。排出は最終パスの後に 1 回だけだった。**

`tests/golden/g10_c5_white_multilayer_md5000_600.bin` を採取。ホワイト・メタリックゴールド・メタリックシルバー・ブラックの 4 プレーンを 1 回の実行で指定したもの。

| 項目 | 実測値 |
|---|---|
| プレーン数 | 4(`printer_code` = 0x0B / 0x04 / 0x07 / 0x00。最後のみ最終フラグ 0x80) |
| パス間のバックフィード(`ESC SUB 0 0 FF`) | 3 回 |
| **排出(単独のフォームフィード `0x0C`)** | **1 回。ジョブ末尾のみ** |

採取済みの golden 全 10 種で同じ構造を確認した。**白が他のインクと同じジョブに同居できる。** ppmtomd はエラーも警告も出さない。

**含意:** 公式ドライバが白を別ジョブに分けていたのは**ドライバ側の実装制約であり、プロトコルの制約ではない**(§1.1 / §13.3)。機器もプロトコルも 1 ジョブ多パスを許容しており、§10.6 の失敗はホスト側の構成に起因していたことになる。

**残る不確定は 1 点のみ。** このバイト列をスプーラ経由で流したとき、ジョブの境界が保たれるか(手順 3)。これは §11.2 のタイミング問題と同じ構造であり、Phase 1 で同時に判明する。

#### overlay モードは採用しない(調査記録 2026-07-28)

ppmtomd には `-overlay` オプションがあり、**印刷終了時に用紙を排出せず先頭位置へ戻す**。複数回の実行で 1 枚の紙に重ね刷りするための機能で、公式ドライバの「ページ合成」に相当するとみられる。

実測したバイト列の差(通常との比較):

- 先頭側に `ESC SUB 01 00 A` が 2 箇所追加される
- curl 補正コマンドの値が `00 00` から `01 00` に変わる
- **末尾の `ESC e`(プリンタリセット)が出力されない**
- **`0x0C` の意味が変わる。** 排出ではなく top of form(用紙先頭へ戻す)になる(ppmtomd.c:2519-2520)

**Foilwright はこの機能を使わない。** overlay は「1 ジョブでは全パスを送れない」という前提に対する回避策であり、本プロジェクトは §4.10 のとおり**最初から全パスを 1 ジョブに収める**方針を採る。§11.5 の手順 1 でその成立を確認済みである。

**ただし `0x0C` の意味が文脈で変わる事実は重要。** 排出回数を数える検証(§4.10)は overlay モードのバイト列に対しては成立しない。将来 L0 が複数ジョブを扱う判断をした場合、この区別が必要になる。

#### 成立した場合の意味

用紙長への依存が消える。**はがき大でも A4 でも、白を含む多色刷りが単一ジョブで完結する。** これは 64bit 対応の副産物ではなく、32bit の公式ドライバでも達成できなかった機能である(§1.1)。

#### 成立しなかった場合

L0 をポート直叩き方式へ移行する判断が生じる。§11.0 のとおり、この判断は §11.2 / §11.3 / §11.4 と同時に評価する。それでも成立しない場合は §14.2 のトンボ方式へ退避する。

- ppmtomd(GPL) — golden の生成元であり、実行時には不要
- ~~mfilemon(GPL-3.0)~~ — **D-023 で使用をやめたため、そもそも依存ではなくなった**

**実行時に利用者が導入する必要があるのは Ghostscript だけである。** ポートモニタ(D-023)も
プリンタドライバ(D-022)も Windows 同梱のものを使うため、追加導入は生じない。

### 12.3 解析対策

**行わない。**

Python は PyInstaller で実行ファイル化しても `.pyc` の抽出と逆コンパイルで元のソースに近いものが復元される。C# の IL も同様に読める。これは既知の性質であり、難読化なしには回避できない。

一方で、本プロジェクトに隠すべき非公開情報は存在しない。MD のコマンド言語は 20 年前から GPL で公開され、仮想プリンタの構成も既存プロジェクトが公開している。パレット定義は平文で置く前提の設定ファイルである。

全体を GPL で公開する以上、解析対策には意味がない。むしろ `ref/` の存在により第三者が実装の正しさを検証できることは、**代替入手困難な機材を扱うソフトウェアにおける信頼性そのもの**である。

難読化は自身のデバッグを著しく困難にするため、導入しない。

GitHub での公開により、第三者が管理する改竄不能なタイムスタンプと開発履歴が残る。非公開のまま少数に配布する期間は、先行を証明する手段が自己申告のみとなるため設けない。

**「ページ合成印刷モードで印刷すると、印刷が終了しても用紙が排出されません」**(p91 / p94)。機能の定義は「印刷文書の 1 ページ目と 2 ページ目を同じ紙に印刷します」(p104)。

**§4.10 の不変条件を公式資料が裏付けた。** また §11.5 の overlay モード調査(ppmtomd の `-overlay`)がこの機能に対応することも確認できた。

**ページ合成を使わない場合の手順も記載されている。** 「アンダーコート印刷をした後に用紙を用紙トレイにセットして、フルカラーで印刷してください。このときは手差しモードで印刷を行なってください。自動給紙で連続印刷を行うと、用紙が正しく送られないことがあります」(p91)。**手作業での再セットが前提**であり、§10.6 の失敗(はがき大で排出されて続行不能)と符合する。

#### 13.5.5 特色の誤爆を公式が認めている(D-016 の裏付け)

**「特色カラーの色成分は多少の許容範囲を持たせてあります。そのため、写真などの色数の多いデータと同じファイル上では、特色カラーの色成分と一致する部分が生じ、一部が特色カラーで印刷されることがあります」**(p41 / p57)。

**D-016 で `auto` 方式の弱点として挙げた誤爆は、公式ドライバでも起きる既知の現象だった。** 公式の対策は「写真などのデータと一緒に特色カラーを印刷するときは、ページ合成機能を使用してください」であり、**本プロジェクトの `per_page` 方式と同じ解**である。

**色成分を内部で調整するアプリでは特色印刷ができない**とも記されている(p41 / p57)。§6.3 が「PPD 側でカラーマネジメントを無効化する」としている理由がここでも裏付けられた。

#### 13.5.6 双方向通信でカートリッジを検出・残量を読む

**「プリンタの双方向通信ができない場合などには、使用できる全てのインクカセットが表示されます」**(p33 / p39 / p44 / p49 / p55 / p60 / p68 / p73)。**装着されているカートリッジを双方向で検出**し、選択肢を絞り込んでいる。

**残量も読める。** 詳細情報ダイアログに「上段のホルダ# / 下段のホルダ#」とインク名・残量(60% / 40% / 80% / 100% / 20%)が表示される(p103)。**ホルダは上下 4 本ずつの計 8 本。**

**§11.4 の到達目標が具体化した。** エラー原因だけでなく、カートリッジの種類と残量まで読めることが公式機能として実在する。

#### 13.5.7 ハーフトーンは 3 種類

「なし」「精細」「高精細」(p101)。定義は次のとおり。

- **なし** — 階調表現を行わない。50% 程度を境に白黒に分けられる
- **精細** — フルカラー印刷時、表面が粗い紙に適した階調表現
- **高精細** — 緻密な階調表現

**§4.2.1 で採用した 3 方式と対応する。**【推測】「なし」= `None`、「精細」= `CoarseHalftone`、「高精細」= `Halftone`。粗い紙向けという説明が粗いドットスクリーンと符合するが、バイト列での確認は未実施。

**印刷品質は別軸で 3 段階**(スタンダード / ファイン / スーパー、p101)。ハーフトーンとは独立した設定である。

#### 13.5.8 その他の実務情報

- **多色特色印刷は最大 6 色**(p29 / p34)。フルカラー + 特色では、CMYK に加えて**特色 3 色までがカートリッジ交換なし**(p42)
- **特色フラッシュカラーは下地処理が必須**。CMYK で下地を刷ってから重ねる(p45 / p56)
- **紙用光沢仕上げ2 は 5 回まで反転して再利用できる**(p20)。ただし印刷面に凹凸があるとインクが付着するため、再利用の条件が限定される
- **官製はがきは給紙レバーを必ず「M」に**(p15 / p23 / p31 等)。自動給紙で連続印刷する場合も M のまま
- 市販ラベルは**「熱転写プリンタ対応」のみ**。感熱・インクジェット用・ワイヤードット用は故障の原因(p74)

#### 13.6.1 ベースドホワイトの正体が確定(§11 #11 の解決)

**「MD-5500 からは、不透明度の高い『ベースドホワイトインク』もサポートされました」**(特色活用ガイド p43)。§13.5.3 の推測(MD-5000 発売後の追加インク)が公式記述で確定した。**品番 `MDC-OPWH` も公式マニュアルに記載**(オンラインマニュアル p68/74/80/90)。市場流通品・サードパーティ資料に続く 3 系統目、かつ初の公式一次資料。

**役割が特色ホワイトと正反対である。**

| | 特色ホワイト(MDC-SCWH) | ベースドホワイト(MDC-OPWH) |
|---|---|---|
| 刷る順序 | **先**(下地。この上にフルカラーを重ねる) | **後**(フルカラーの上に重ねる) |
| 主用途 | 色紙への下地印刷・白文字 | **転写系**(アイロンプリント・光沢転写フィルム・OHP) |
| 理由 | 紙の色の影響を消す | 転写後に**裏側から見る**ため、色の背面に白が要る |

**§10.9.1 の実践報告(「ベースドホワイトは他のインクの上にのりやすい」)と完全に整合する。** 逆順の重なり特性は、この用途のために設計されたものだった。

**ドライバでの指定方法は 2 通り**(オンラインマニュアル p70/76/83/90):

1. [特色設定] → [印刷方法] = 「ベースドホワイト」(ページ合成の 2 回目として。図形や文字の形に沿わせる場合はこちら)
2. [詳細設定] → [ベースドホワイトオプション] → チェック + [領域の抽出方法]。**[自動] では画像部分に矩形で刷り、文字部分には刷らない**。「濃い / 薄い」の選択もある

**色の濃い布地にはページ合成でベースドホワイトを 2 度刷る**ことが推奨されている(p92)。`passes` の設計(§6.2)がそのまま対応する。

**OHP の注意**: 「フルカラー印刷した上に特色ホワイトを印刷することはできません。フルカラー印刷をした後に白を印刷する場合は、ベースドホワイトを使用してください」(p80)。**上に乗せる白はベースドホワイト一択**。

**色選択コード(`printer_code`)は依然として不明。** ドライバ画面の資料からはバイト値まで分からない。ただし MD-5500 ドライバの [特色設定] または [詳細設定] で指定して FILE: 出力を捕捉すれば特定できる見込みが立った(§11 #11 の残作業)。

#### 13.6.2 公式ドライバの色マッチング許容幅の実測値(D-015 との対比)

特色活用ガイド p10 に、**フルカラー + 特色モードでの許容誤差の実測記録**がある(Photoshop 5.0 で 1/256 段階ずつ変えたテスト):

- **RGB 指定: R は -1〜+2、G は ±0〜+3、B は ±0〜+1** — 非対称かつ極めて狭い(「ピンポイント」と表現)
- CMYK 指定: -1% のみ
- 32 ポイント以下の文字は近似色でよい。**「Windows NT の場合は、文字のポイントに関係なく、近似色を指定」**(オンラインマニュアル p49) — 現行 Windows は NT 系であり、近似色マッチングが常用となる

**D-015(各チャンネル独立・対称 tolerance)との違い**: 公式は非対称・チャンネル別の許容幅を使っていた。Foilwright の対称 tolerance(白 8 / メタリック 12)は公式の「フルカラー + 特色」より大きく、「多色モード」(近似色で可)に近い挙動。**auto 方式の誤爆リスク評価では、公式のフルカラー + 特色より誤爆しやすい方向であることを認識しておく**(プレビュー §7.2 の重要性が増す)。

#### 13.6.3 インクの透明・不透明の 2 分類と重ね順の原則

**「特色ホワイト・ベースドホワイト・フラッシュカラー・メタリックカラーはすべて不透明なインク。CMYK インクは下地の色の影響を受ける透明インク」**(特色活用ガイド p43)。

**原則: 不透明インクで透明インクの印刷面を隠さないように順序を組む。** メタリックの上にフルカラーを重ねる場合は必ずメタリックが先(p13)。例外がベースドホワイト(意図的に最後に重ねて裏から見る)。

`order` の設計(§4.3)はこの原則を表現できるが、**パレット定義に「透明 / 不透明」の区分は現状ない**。誤った順序の警告(§7.2 のプレビュー拡張)を作る場合に必要になる。

#### 13.6.4 フラッシュカラーは下地処理が自動で入る

**「フラッシュカラー印刷ではインクの接着性を高め、光沢を与える目的で、フラッシュカラーの下にフルカラー 100% を先に印刷します」**(特色活用ガイド p14)。どのモードでもフラッシュ使用時に CMYK 4 色が必要なのはこのため。

- 「まったく下地処理を行わなければフラッシュカラーは正常に印刷されません」
- ページ合成で先に下地を作った場合のみ「下地処理なし」を使う
- **将来パレットに Flash 系(MDC-FMEG / FMES)を追加する場合、`auto_undercoat` とは別の「CMYK 全色ベタの下地」という依存関係の表現が必要になる**(§14 案件)

#### 13.6.5 アンチエイリアスの罠(auto 方式の運用注意)

**フルカラー + 特色モードでは、アンチエイリアスのぼかしが特色の色成分を壊す**(特色活用ガイド p15)。特色同士が接する縁に「どちらのメタリックでもない色」ができ、色抜け・汚れに見える。公式の指示は「環境設定でアンチエイリアスを切る」。多色モードは中間色がどちらかに分解されるため影響なし。

**Foilwright の `auto` 方式にも同じ罠がそのまま当てはまる。** 利用者向けドキュメント(§7)に必須の注意事項として記載する。tolerance を広げても、縁の中間色は「白でも金でもない値」になり得るため根本解決にならない。

#### 13.6.6 その他の実務情報

- **カセット同時装着数は 7**(MD-5500。上段 4 + 下段 4 の 8 ホルダ中 7 個掛け。特色活用ガイド p13)。8 色以上はページ合成で分割
- **ページ合成は 3 回以上も可能だが版ずれが増える**(p12)。チェックは 1 回目の印刷前のみ。2 回目はチェックしない
- **JPEG / GIF はフラッシュカラー印刷に不適**(p16)。JPEG は色成分が保存で変わり、GIF は色数制限。BMP / TIFF / PICT / EPS を使う
- **疑似ハーフトーン(誤差拡散)は 100ppi 程度まで**(p16)。細かいドットにはフラッシュインクが乗らない
- **紙用基本 4 色を特色として使う技法があり、Windows ではイエローをフラッシュゴールドのスロットで指定する**(p41-42)。ドライバ UI の制約で、多色モードのインク選択にイエロー枠がないため
- フラッシュとメタリックはカセット外観が似ている。B 面の表示で確認(p13)
- 昇華フォトカラーはオプションの昇華スタータキット(MDT-DSKT)が必要(オンラインマニュアル p4。§1.3 の非目標)

### 13.8 最終版ドライバの解析(Ver.2.3.2 / Windows 2000・XP 用)

#### 13.8.1 D-020 の裏付け — 純正最終版も usbprint.sys の上に載っていた

INF の対象 ID が **`USBPRINT\ALPS___MD-5500_T-03_F01C`** である。これは **Microsoft 標準の `usbprint.sys` が列挙した装置に紐づく形式**であり、Win9x 版が持っていた独自 USB ポートドライバ(`mdp_usb.sys` / `MD_USB1:` ポート。§13.7.1)は**この世代には存在しない**。

**つまり純正の最終版も、USB では標準ドライバの上でプロトコルを喋っていた。** D-020(L0 は `usbprint.sys` のデバイスインターフェースを直接開く)は、公式が最後に採った構成と同じ土俵に立っていることになる。WinUSB への差し替えを避けた判断の裏付けとして扱える。

構成は v3 ドライバ + LanguageMonitor(`AL1CLM.dll`)+ PrintProcessor(`AL1CS.DLL`)。**§3.6 で却下した「EMF + 自作プリントプロセッサ」(D-021 の C 案)は、まさに純正がやっていた方式**である。却下理由は技術的な不可能性ではなく、第三者製印刷コンポーネントに対する Microsoft の廃止方針(D-001 / D-021)。

#### 13.8.2 ベースドホワイトは最終版でも健在

`AL1CL.dll` / `AL1CLG.dll` / `AL1C.HLP` に「ベースドホワイト」「紙用特色ホワイト」の文字列が UTF-16LE で存在する。§13.6.1 の公式記述と整合する。

**POP カラー系のモードが追加されている**(`SpotMultiPopDeepBlue` / `PopMossGreen` / `PopVermilion` / `PopMagenta` / `PopYellow` / `PopCyan` / `PopBlack` / `PopWhite`、`SpotSingleInkPop`)。§13.7.5 のカセット表にあった「ポップ用赤 / 緑 / 青」がモードとして拡張された世代とみられる【推測】。

**§11 #11(ベースドホワイトの色選択コード)を `AL1CK.dll`(約 1MB、32bit)の静的解析で確定しようと試みたが、費用対効果が低く打ち切った(2026-08-07)。**

Win9x 版(`aldv63.drv`、16bit)ではプレーン構築コードが `mov byte ptr [bx], imm` の連なりだったため、色コードの列を直接読み取れた(§13.7.4)。**32bit 版では同じ手が効かない。**

- 即値書き込み(`C6 /r ib`)で 0x00〜0x20 を書く箇所は全体で数十件しかなく、16bit 版のような密な列を成していない
- 既知の組み合わせ(`0b 06 05 04 07 00` = 白+メタリック4+黒、`01 02 03 00 11 14` = CMYK+箔、`0a 09 08` = ラベカ)をバイト列として探しても**1 件も一致しない**
- `01 02 03 00`(CMYK)だけは 1 箇所見つかるが、周辺はコードとデータが混在しておりテーブルとして読み解けない

**32bit のコンパイラが色コードを静的配列に置き、間接参照で組み立てているとみられる**【推測】。追跡には本格的な逆アセンブルが要り、得られるのは 1 バイトである。

**したがって §11 #11 は実測で確定させる方針に戻す** — ベースドホワイトのカセットを装着して純正ドライバに刷らせ、USBPcap で採取する(§13.7.6)。候補が 0x1c / 0x1e の2 つに絞れている以上、実測 1 回で決着する。**同じ静的解析を繰り返さないこと。**

**注意:** 展開したドライバのバイナリ・文字列はリポジトリに置かない(著作物)。解析は相互運用目的の読み取りに限る(§12.3)。

### 14.1 全パスの 1 ジョブ化【最優先・機能というより前提】

§11.5 の課題そのもの。**他のすべての将来機能より優先度が高い。** これが成立しないと多色刷りの実用性が用紙長に縛られ続ける。

### 14.2 白版のトラッピング(チョーク / スプレッド)

パス間の紙送り誤差により、色版と白版には必ず版ズレが生じる。印刷業界の定石は、**白版を色版よりわずかに縮める(チョーク)**ことで、多少ずれても白が色の内側に隠れるようにすることである。隠蔽力を優先する場合は逆に太らせる(スプレッド)。

**実装は 1bit プレーンに対する収縮・膨張処理であり、規模は小さい。** `auto_undercoat` に `choke` を指定する形が自然。

**§11.5 が成立した後に価値が上がる。** 1 ジョブ化で版ズレが小さくなって初めて、トラッピング量が現実的な値に収まる。逆に §11.5 が成立しない場合は、**トンボによる手動見当合わせの誤差を吸収する保険**として機能する。

**公式ドライバに同等機能は存在しない。**

### 14.3 失敗パスの部分再送

§4.6 のバイト列ダンプにより、**特定のパスのみを再送できる。** 5 パス中 4 パス目で失敗した場合、公式ドライバでは全パスをやり直すしかない。リボンと用紙が有限であることを考えると効果は小さくない。

**ただし §4.10 との整合に注意。** 排出後の再送は見当が合わないため、実質的には「排出前に失敗を検知して同一ジョブ内でやり直す」形にしかできない可能性がある。

### 14.4 カートリッジ本数制限の実質的な撤廃

公式の Multiple Ink 印刷は最大 4 本装填・最大 6 色(§13.3)。Foilwright は 1 パスずつ手動交換で回すため、**理論上の色数上限がない。** 交換の手間が増えるだけである。§7.2 の交換指示 UI が前提として機能する。

### 14.5 ディザリングの用途別選択

公式ドライバの Halftone は No Halftone / Fine Dither / Standard Dither の 3 択で、写真向けの設計である(§13.3)。線画とベタで構成されるデカール用途には最適ではない。**輪郭を優先するディザや、用途別プリセットを自前で用意できる。**

§4.2 で初版を閾値二値化のみとしたのは着手順序の話であり、恒久的な制約ではない。

### 14.6 予約色の再定義

`magic_rgb` は公式値を初期値としているが(§6.1)、**銀 189,193,197 と白 230,230,230 は近接しており誤判定の risk がある。** 公式ドライバではこの割り当てを変更できないが、Foilwright はパレット定義を書き換えるだけで衝突しない値に振り直せる。

#### USBPcap と VMware の USB パススルーは併用できない(2026-08-08 実測)

**機構エラーの種別を得る経路を探すため USBPcap を再導入したが、採取に失敗し環境を壊した。**

経過:

1. USBPcap を導入して PC を再起動、キャプチャを開始した
2. **仮想 PC から MD-5000 へ接続できなくなった**
3. **ホスト側からもデバイスが消えた**(`Get-PnpDevice` に現れない)
4. 採取を中止し USBPcap をアンインストール

**USBPcap のフィルタドライバは、VMware の USB パススルーと併用できない。** usbipd が同ソフトを「非互換」と警告するのと同じ理由とみられる。**純正ドライバを仮想 PC で動かしながらバスを採取する、という手が使えない。**

**8/4 に採取できたのはなぜか:** あのときは**先にキャプチャを開始し、その後で仮想 PC にデバイスを接続した**。今回は逆で、既に仮想 PC が起動している状態でフィルタを挟んだ。**順序が効く可能性がある**【推測】が、再現を試すには環境を壊す危険を再び負うことになる。

**結論:** 機構エラーの種別解読は、**この手段では進められない**。別の道を探すか、**種別は識別できないものとして扱う**(§13.8.3 の方針どおり、状態表示では「機構の異常(種別は特定できません)」と出す)。

**この失敗の一般化は skill `debugging-external-systems` の項目 4(解析用の足場は必ず撤収する)に含まれる。** 足場が本体の作業を壊した時点で、足場を外すのが先である。

## §15 MD-5500 USB 転送プロトコル(L0 仕様・実測で確定)

**2026-08-04 に純正ドライバの印刷を USBPcap で捕捉して解読した(`dumps/vm_print2.pcap`)。** §11.3 / §11 #8 が想定していた「USB 直結は標準 usbprint.sys が掴む楽なケース」は誤りで、**バルクエンドポイント上に ALPS 独自のパケット層がある。RGL の生ストリームは受け付けない**(書くとリンクごと落ちる。§11.1.1)。

### 15.1 エンドポイント

`044e:2002` / USB 1.1 Full Speed / interface 0 alt 0(クラス 07 = プリンタ、プロトコル 02 = 双方向)。**バルク OUT `0x01` / バルク IN `0x82` の 2 本のみ。** 最大パケット 64 バイト。

### 15.2 パケット形式

すべてバルク上でやり取りする。制御転送は列挙と `GET_DEVICE_ID` にしか使わない。

| 方向 | バイト列 | 意味 |
|---|---|---|
| OUT | `05 ff` | **送信要求**。データを送ってよいか尋ねる |
| IN | `06` | **許可**(1 バイト) |
| OUT | `02 01 {len16} {payload}` | **データパケット**。`len16` はリトルエンディアンで **ペイロード長 − 1**。ペイロードは最大 **32764** バイト(総転送 32768) |
| IN | `06` | **受理**(1 バイト) |
| OUT | `05 01` | **カセット状態の問い合わせ** |
| IN | 38 バイト | 状態応答(§11.4) |
| OUT | `05 02` / `05 03` / `05 04` | 機体情報 / 用途不明 / 数値表。いずれも 256 バイト応答 |
| IN | `04`(1 バイト) | 未サポートのコマンドに対する応答 |

**送信手順:** RGL ストリームを 32764 バイトずつに切り、各断片について `05 ff` → `06` → `02 01 {len-1} {断片}` → `06` を繰り返す。

**注意:** バルク IN を読んでよいのは**応答を返すコマンドの直後だけ**。応答が無い状態で読むと STALL し、繰り返すとインターフェースがウェッジする(回復は `usbipd detach`/`attach`、または物理再接続)。

#### 15.2.1 プリンタとの会話は 1 本しかない(2026-08-04 / 実地で踏んだ)

**このプロトコルは「コマンドを書いて応答を読む」往復を 1 本の会話として持つ。複数のプロセスが同時に話しかけてはならない。**

実際に壊した手順:

1. トレイアプリ相当のプロセスがジョブ送出中だった(`05 ff` → `06` → データ → `06` の繰り返し)
2. そこへ別プロセスが状態問い合わせ `05 01` を割り込ませた
3. **応答が交差した。** 送出側は自分の `06` の代わりに 38 バイトの状態応答を読み、以後すべてがずれた
4. インターフェースがウェッジし、**読み取りが永久にブロックする**状態になった

**回復手順(2026-08-04 に実地で確立):**

1. **USB を物理的に抜き挿しする。** これでブロックしていたプロセスが解放される
2. その直後、Windows はデバイスを **Status=Error** と認識している
3. **`tools/reset-printer.cmd` を管理者で実行する**(デバイスの無効化 → 有効化)。Status が **OK** に戻る
4. 状態問い合わせが通ることを確認する

**順序が重要。** 抜き挿しの前に `Disable-PnpDevice` を試しても、保留中の I/O があるため失敗する。ブロックしたプロセスは `Stop-Process -Force` でも終了しない(中断不能なカーネル I/O で待っているため)。**まず物理的に抜き挿してハンドルを解放し、それからデバイスをリセットする。**

usbipd を使っていた時期は `detach` → `attach` だけで回復できたが、**Windows ネイティブ経路(D-020)にはその手段が無い。**

**リボン残量のカウンタはこの回復を通しても保持される**(49/653/653/63 が抜き挿し前後で一致)。プリンタ本体が保持している値であることの裏付けになる。

**設計上の帰結:**

- **トレイアプリがデバイスを排他的に所有する**(D-024)。他のツールが同時に状態を読みに行ってはならない
- §7.3 のカセット検証(交換後に `05 01` で確認する)は、**パスとパスの間**で行う。送出の最中に挟んではならない
- 開発用の採取ツール(`tools/probe-status.ps1`)は、**トレイアプリが動いていないときにだけ**使う

#### 15.2.2 送出には必ずタイムアウトを設けること(2026-08-04 / 実地で踏んだ)

**プリンタが `06`(受理)を返さない状況が実在する。** 応答を無期限に待つ実装は、そこで永久に停止する。

観測した経過:

1. 1 本目のジョブは全バイトが受理された(`21675/21675`、送出完了)。**その後プリンタは給紙に失敗しエラーになった**
2. 用紙を入れ直すとエラー表示は消え、状態バイトは `0x00`(待機)に戻った
3. **しかし以後のジョブは受理されなくなった。** `05 ff` を書いた後の `06` が返らず、読み取りが戻らない
4. この状態でも Windows から見たデバイスは正常(`Status=OK`)で、**送出プロセスは通常どおり終了できる**(§15.2.1 のウェッジとは別物)

**エラー表示が消えることと、プリンタがジョブを受け付ける状態に戻ることは別である。** 内部に前のジョブが残っているとみられ、解消には**プリンタ本体の電源再投入**が要る(実地で確認)。

**実装への要求:**

- **`WriteFile` / `ReadFile` に必ずタイムアウトを設ける。** ハンドルを `FILE_FLAG_OVERLAPPED` なしで開いている場合、待機中の読み取りは別スレッドからの `CancelIoEx` で打ち切れる
- タイムアウトしたら**利用者に「プリンタが応答しない。電源を入れ直してほしい」と伝える。** 黙って固まらない
- §7.2 のトレイアプリは、この状態を**進捗表示で見える形にする**(何バイト送って、どこで止まったか)

**未確定:** ジョブを取り消す手段があるかは不明である。`05` 族のコマンドで応答を返すのは `01`〜`04` の読み出しクエリのみで、取り消しに相当するものは見つかっていない(§15.2)。純正ドライバのステータスモニタには「中断」ボタンが存在するため、**何らかの手段はあるはず**。USBPcap で純正ドライバの中断操作を採取すれば判明する。

#### 15.2.3 応答を読み切らないと以後の会話がすべてずれる(2026-08-04 / 自分で踏んだ)

**応答を途中で打ち切って読むと、読み残しがデバイス側に滞留し、次の会話の先頭にそれが出てくる。** 以後すべての読み取りが 1 つずつずれ、正常な通信に戻らなくなる。

原因を作ったのは自作の採取ツール(`tools/probe-status.ps1`)だった。`05 02`〜`05 04` は 512 バイトを超える応答を返すが、固定長 512 バイトで 1 回だけ読んでいた。

**滞留した状態で送出したときの実出力:**

```text
状態要求 05 01 : OK(2)
状態応答      : 102 バイト 00 00 00 00 00 00 00 00   ← 本来 38 バイト、02 80 21 で始まる
  送信要求 05 ff : OK(2)
  許可           : 15                                ← 本来 06(ACK)。0x15 は NAK
  データ         : OK(1492)
  受理           : 15
```

**症状が紛らわしい。** 書き込みはすべて成功を返し、読み取りも「成功」するため、**一見すると通信できているように見える**。実際には受け取っている中身が別物で、プリンタは NAK を返している。

**2026-08-04 の午後、実機が「純正ドライバでは刷れるのにこちらでは刷れない」状態に陥った原因はほぼこれである。** 採取ツールを走らせるたびに滞留が増え、その後の送出が失敗していた。プリンタの電源再投入・PC 再起動・USB の抜き挿しで一時的に直るのは、いずれも滞留が消えるためだった。

**対策(実装要件):**

- **デバイスを開いた直後、最初のコマンドを送る前に受信パイプをドレインする**(データが返らなくなるまで読み捨てる)。ドレインには必ずタイムアウトを使う(§15.2.1 のウェッジを避けるため)
- **応答は最後まで読み切る。** 固定長で打ち切らない。バッファがちょうど埋まったときは続きを読む
- ドレインで捨てたバイト数が 0 でなければ、**異常が起きていた証拠として利用者に見せる**

**教訓:** 「書き込みも読み取りも成功している」ことは、正しく通信できている証拠にならない。**受け取った中身が期待どおりかを検査すること**(状態応答ならヘッダが `02 80 21` か、ACK なら `06` か)。

**対策の効果(2026-08-04 に実測):** ドレインを実装した後、状態応答は正しい形式(`02 80 21 00 00`)で返るようになり、**1488 バイトのジョブが NAK ではなく正常に全受理された**。送出後の状態バイトは `0x09`(印刷実行中)へ遷移した。**午後を通じて再現していた「送出が通らない」現象は解消した。**

**副次的に判明:** `GET_DEVICE_ID`(`IOCTL_USBPRINT_GET_1284_ID`)は 1024 / 256 / 64 のいずれのバッファ長でも `win32=87` で失敗する。**しかし失敗したまま送出は成功する。** §11.4 が「前置きが要る」と記録したのは libusb 経由の話であり、**usbprint.sys 経由では不要**とみられる。この IOCTL が通らない理由は未解明のまま残る。

### 15.3 純正ドライバが実際に送る RGL の先頭

参考として、フルカラー印刷 1 枚(7,262,724 バイト)の先頭を再構成した。**ppmtomd が出さないコマンドが含まれる。**

```text
1b 65                 プリンタリセット(ppmtomd はこれを末尾に置く)
1b 25 80 41           RGL モード選択
1b 26 6c 07 00 4d     メディア種別 (07,00)
1b 26 6c 04 00 41     用紙サイズ A4
1b 26 6c ed 18 50     ページ長 6381 ドット
1b 2a 74 03 52        解像度 600dpi
1b 1a 00 00 4c        未知(§13.7.3 の "L" コマンド)
1b 1a 08 00 49        未知("I" = ステータス系)
1b 2a 72 08 55        転送モード 0x08(ppmtomd の enum に無い値)
1b 26 6c 04 00 43     未知("C"。ppmtomd のカール補正とは別形式)
03 02 01 00           ESC で始まらない 4 バイト
1b 1a 21 00 55        未知("U")
1b 2a 72 01 41        ラスタ開始(ppmtomd は 00)
```

末尾は `0c 1b 2a 72 43 1b 25 00 58 03`(排出 → ラスタ終了 → RGL 終了 → `03`)。

**この差分は印刷に不要と判明した(2026-08-04)。** `ref/` が生成した ppmtomd 形式のジョブ(blackRaster・1488 バイト)を §15.2 のフレーミングで送ったところ、**全バイトが ACK 付きで受理され実機に印刷された。** 純正ドライバの追加コマンド群は少なくとも単色ラスタでは必須ではない。**したがって L1(emitter)は現状のままでよく、USB 対応で変更が必要なのは L0 だけである。**

### 15.4 Phase 1 成立(2026-08-04)

**`ref/` の出力が実機で印刷された。** プロジェクト開始以来はじめて、自前のバイト列が自前の転送経路で紙になった。

- ジョブ: `dumps/phase1_blackraster.bin`(5mm 角の黒ベタ / blackRaster / 600dpi / A4)
- 送出: `tools/alps_send.py`(§15.2 の実装)
- 結果: 1488/1488 バイト受理(0.01 秒)、印刷成功

**状態バイト(応答の 5 バイト目)の遷移を観測した。** 送出前 `00` → 直後 `09` → 数秒後 `01` に落ち着く。過去には `10` も観測している。**`09` が印刷実行中を表すとみられる**【推測】。用紙・カバー等との対応は未確定で、状態を変えながら採取すれば特定できる。

### 15.5 多色刷り(colourPlane)の実機検証(2026-08-04)

**L1 の本丸である多色パスが実機で動作した。** `ref/` で CMYK 4 色のテストジョブを生成し(5mm 角のパッチ ×4、各プレーン 13924 ドット、色選択 4 個 + バックフィード 3 回、6515 バイト)、§15.2 のフレーミングで送出した。

**印刷中のステータスを 3 秒間隔で追ったところ、カセットの入れ替えを直接観測できた。**

| 経過 | スロット列(11 レコードの先頭バイト) | 読み取り |
|---|---|---|
| +3s | `ff 03 01 00 ff 02 ff ff ff 00 00` | 開始時の装填状態 |
| +6s | `ff 02 01 00 ff ff ff ff **03** 00 00` | シアン(03)が 9 番目へ移動 |
| +12s | `03 ff 01 00 ff ff ff ff **02** 00 00` | マゼンタ(02)が同位置へ |
| +21s | `03 02 ff 00 ff ff ff ff **01** 00 00` | イエロー(01)が同位置へ |
| +27s | `03 02 01 ff ff ff ff ff **00** 00 00` | ブラック(00)が同位置へ |

**ジョブで指定したインク順(C → M → Y → K)と完全に一致する。** これにより 2 つのことが同時に判明した。

1. **9 番目のレコード(0 起点で index 8)は「現在ヘッドに装着されているカセット」を表す。** 純正ドライバの文字列にあった "Holder Position"(§13.7.3)の実体。残り 8 スロットが上段 4 + 下段 4 のホルダに対応する
2. **`ref/` が生成する色選択コマンドとバックフィードが実機で意図どおり解釈されている。** golden 一致だけでなく、機械の挙動としても正しい

**状態バイトは実行中ずっと `09` を維持し、完了後に `01` へ戻った。** `09` = 印刷実行中の裏付けが取れた。

**印刷結果は利用者が現物で確認済み(4 色すべて出力)。** 版ずれの定量測定は未実施 — §11.5(1 ジョブ多パス化)の判断材料として、いずれ実測する。

**この時点で `ref/` の L1 / L2 は実機で成立したとみなす。** golden 15 種一致 + pytest 76 件 + 実機印刷(単色 blackRaster / 多色 colourPlane)。残る未検証パスは特色ホワイト(カセット未装填)、カール補正、メディア種別。

### 15.6 Windows ネイティブでの実装が成立(2026-08-04 / D-020)

**プロトコルの解読には usbipd-win + WSL2 + libusb を使ったが、これは開発用の足場であり本番構成にはできない。** 本番の L0 は Windows から直接 USB を叩く必要がある。候補は 2 つあった。

1. 標準の `usbprint.sys` を残したままデバイスインターフェースを `CreateFile` で開き、`WriteFile` / `ReadFile` で §15.2 のパケットをやり取りする
2. WinUSB へドライバを差し替える

**1 が成立した。** `tools/alps-send.ps1` で実測した結果、状態問い合わせもジョブ送出も通り、印刷まで完了した。

```text
デバイス: \\?\USB#VID_044E&PID_2002#80D0027H#{28d78fad-5a12-11D1-ae5b-0000f803a8c2}
状態要求 05 01 : OK(2)
状態応答      : 38 バイト 02 80 21 00 00 ...
  送信要求 05 ff : OK(2)   許可: 06
  データ         : OK(1492) 受理: 06
```

送出後の状態バイトは `09`(実行中)→ `01`(完了)と遷移した。

**含意:**

- **ドライバの差し替えが不要。** WinUSB を当てると、そのデバイスは Windows からプリンタとして見えなくなり、導入手順も利用者の負担になる。この代償を払わずに済む
- **usbipd / WSL は本番から完全に消える。** 開発時の解析手段としてのみ残る
- 利用者は USB を挿すだけでよい(標準ドライバのまま動作する)

**実装上の注意(実測で判明):**

- デバイスパスはレジストリの `DeviceClasses\{28d78fad-5a12-11D1-ae5b-0000f803a8c2}` から得る。**キー名の先頭の `##?#` だけが `\\?\` に対応し、以降の `#` はそのまま残す**(すべて置換すると `win32=3` で開けない)
- PowerShell 5.1 でこの種のツールを書く場合、`.ps1` は **UTF-8 BOM + CRLF** で保存する。BOM が無いとインライン C# 中の日本語コメントが文字化けしてコンパイルエラーになる

### 15.7 MD-5000(パラレル + 変換ケーブル)での生送出が成立(2026-08-19)

**D-025 で実装した生送出が、実機で初めて成立した。** MD-5000 に `dumps/phase1_blackraster.bin`(5mm 角の黒ベタ / blackRaster / 1488 バイト)を送出し、**印刷された**。

```text
ジョブ: phase1_blackraster.bin (1488 バイト)
送出前状態バイト: 0x00(待機)
  1488/1488 バイト
送出完了
```

**確定したこと:**

- **パラレル経路にパケット層は不要。** RGL を包まずそのまま書けば印刷される。D-025 で【推測】としていた前提が実測で裏付けられた(根拠にした「ppmtomd がパラレル向けに生の RGL を出力している」という観察は正しかった)
- **7 月の失敗(§11.1.1「データが到達しない」)は再現しなかった。** 当時と違い、現在はドレイン・タイムアウト・応答の中身検査が実装されている。**当時の症状は読み残しの滞留が原因だった可能性が高い**【推測】
- **状態問い合わせも同経路で通る**(§11.4 で既に確認済み)

**MD-5500(USB 直結・パケット層)と MD-5000(パラレル・生送出)の両方で印刷が成立した。** L0 の 2 系統がいずれも実機で裏付けられたことになる。

**送出後の状態は `0x00`(待機)のままで、印刷実行中(`0x09`)を捉えられなかった。** ジョブが小さく、状態を読む前に完了したとみられる【推測】。MD-5500 では `0x09` を観測できていた(§15.4)。
**多色刷りも MD-5000 で成立した(2026-08-19)。** CMYK 4 色のジョブ(`dumps/phase2_cmyk4.bin`、6515 バイト)を生送出し、**4 色のパッチが印刷された。**

送出前に構造を検査した結果は次のとおりで、§4.10(排出は最終パスの後に 1 回だけ)を満たしている。

```text
色選択: 0x01 -> 0x02 -> 0x03 -> 0x00(最後に last フラグ)
バックフィード: 3 回   排出: 1 回
```

**このバイト列は MD-5500 用に生成したものをそのまま使った。** golden が両機種でバイト完全一致する(§11 #3)という前提が、実機の印刷結果としても裏付けられたことになる。

**見当は実用上問題ない範囲だった**(利用者の目視確認)。定量測定は未実施。**白 + カラーの重ね刷り(§1.1 の主用途)が成立する見込みが立った。**

**MD-5500 と異なり、印刷中のカルーセル回転を状態から観測できなかった。** 送出完了後に読んだ時点では既に待機へ戻っており、カセット配置も送出前と同じだった。MD-5500 では `0x09`(実行中)とカセットの移動を捉えられていた(§15.5)。**パラレル経路では状態の更新が印刷完了後にまとめて反映される可能性がある**【推測】。
