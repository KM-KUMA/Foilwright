# PROJECT ARCHITECTURE: Foilwright

現状(2026-07-28): ref/(Python 参照実装)が golden 15 種とバイト一致。L1 emitter、L2 raster(CMYK 分解 / マジックカラー / 自動判別の 3 入口)、ハーフトーン 3 方式、設定ファイル層(profiles / palette / papers / media)が動作。src/(C# 本番実装)と PPD は未着手。実機は Phase 0(デバイス列挙)まで完了、印刷は未実施。

## 目的とスコープ

- 解決する課題: ALPS MD シリーズ(MD-5000 / MD-5500)の公式ドライバが 32bit 版のみで 64bit Windows では動作しない問題を解消する。任意のアプリの印刷ダイアログから通常のプリンタとして選択でき、白・金銀を含む特色印刷が可能な 64bit ネイティブの印刷経路を提供する(DOMAIN §1.1)。
- Phase 構成(DOMAIN §9.4):
  - Phase 0: 環境調査(ポート一覧・変換ケーブルのデバイス ID 取得のみ、実機リスクなし)
  - Phase 1: 5mm 角のベタ 1 色を 1 枚(プロジェクトの成否を決める関門。§11.2 のタイミングリスクがここで判明する)
  - Phase 2: 仮想プリンタ経由でメモ帳から印刷
  - Phase 3: 白版を含むフルパス(外部協力者への配布はこの成立後に限る)
  - Phase 4: MD-5500 USB 直結対応(Phase 3 成立後に着手。DOMAIN §11.3)
- 明示的な非目標(DOMAIN §1.3):
  - 昇華モード(ダイサブ)への対応
  - Windows 以外の OS
  - v4 プリンタドライバ形式
  - 難読化・解析対策
  - なお MD-5500 の USB 直結対応は非目標ではなく保留(Phase 4 として実施予定)

## レイヤ構成

四層構造、依存方向は L3 → L2 → L1 → L0 の一方向のみ(逆流禁止)。特に L0 と L2 は機種を一切知らない。機種差は L1 のプロファイルに閉じる(DOMAIN §3.1)。

### L0 transport
- 責務: 物理経路への書き込み
- 触ってよい/いけない境界: バイト列を受け取って送出する以上に具体化しない。ポート名やプリンタキュー名を L1 以上に漏らさない(DOMAIN §11.3)

### L1 emitter
- 責務: MD コマンド生成 + 機種プロファイル
- 触ってよい/いけない境界: 機種による分岐はここに閉じる。`if model == "MD-5500"` のような条件分岐がプロファイル定義の外に現れることは設計違反(DOMAIN §4.4)

### L2 raster
- 責務: 画像 → インク別 1bit プレーン
- 入口が 3 つある(DOMAIN §6.6。利用者が印刷ダイアログで選ぶ)
  - `auto`(既定): 特色を先に判定し、一致しない画素を CMYK 分解へ回す。特色とフルカラーの混在に対応
  - `per_page`: 1 ページ = 1 インク。原稿の側でレイヤーが分離済みの用途向け(誤爆が起きない)
  - `spot_only`: マジックカラーのみ。一致しない画素は刷らない
- 触ってよい/いけない境界: 機種を一切知らない。インク定義はハードコードせず外部ファイルから受け取る(DOMAIN §4.5)

### L3 interface
- 責務: PPD / ポートモニタ連携 / トレイアプリ

## データフロー

DOMAIN §3.2 の経路図(そのまま引用):

```
アプリケーション(Photoshop / Illustrator / ペイント等)
  ↓ 印刷ダイアログでプリンタを選択
Microsoft PostScript Printer Driver V3 + 自作 PPD
  ↓ PostScript
Windows スプーラ
  ↓
mfilemon(ポートモニタ / 既製品・改造しない)
  ↓ パイプで標準入力へ
Foilwright 変換器(セッション 0 / UI を持たない)
  ↓ ジョブをキューフォルダに積んで即終了
Foilwright トレイアプリ(ユーザーセッション / UI を持つ)
  ↓ WritePrinter (RAW)
Generic / Text Only プリンタ → USB001 → USB-パラレル変換ケーブル
  ↓
MD-5000 / MD-5500
```

内部座標は常にドット単位。mm は L3 の入口(PPD 解釈)でのみ扱う(DOMAIN §4.1)。

## 主要データ構造 / IR

IR は「インク名 → 1bit プレーン」(DOMAIN §4.2 / §6.6)。**どのインク指定方式を入口に使っても、L2 以降のこの内部表現は同一。**

- 保存しないもの: `auto_undercoat`(他インクが乗る画素の和集合として導出される下地プレーン。旧称 auto_backing)は保存せず、必要時に導出する(DOMAIN §6.2)
- ハーフトーンは方式を選択できる。既定は閾値二値化、ほかに Halftone / CoarseHalftone(DOMAIN §4.2.1)

| 依存 | 用途 | 代替を却下した理由 → DECISIONS |
|---|---|---|
| mfilemon(ポートモニタ・改造しない) | スプーラからのジョブをパイプで変換器の標準入力へ渡す | — |

| PyYAML(`ref/` の唯一の実行時依存) | 設定ファイル(profiles / palette / papers / media)の読み込み。src/ 側は YamlDotNet 等を使う | D-013 |

## 既知の制約 / 未解決

**最重要リスクは 2 件で、いずれも Phase 1 の実機試験で同時に判明する。**

- **スプーラ経由でのタイミング成立性**(DOMAIN §11 #7 / §11.2)。成立しなければ仮想プリンタ方式そのものが破綻する
- **全パスを 1 ジョブとして送れるか**(#10 / §11.5)。プロトコル側は成立を確認済み(golden g10)。残るはスプーラがジョブ境界を保つか

**§11.0 の警告:** タイミング(§11.2)・USB 直結(§11.3)・エラー読み出し(§11.4)・ジョブ境界(§11.5)の 4 件は、いずれも「L0 がポートを直接握る方式へ移行するか」という**同一の判断に帰着する**。個別に判断してはならない。この構造への備えが §4.8(L0 を送信専用に固定しない)。

その他の未確定(詳細は DOMAIN §11):

- カラーマネジメントによる RGB 変位(#2。マジックカラー方式の成否に直結)
- `max_width_dots` の実値(#4。参考値は §5.5 にあるが実機未確認)
- サードパーティ特色インクの識別(#5。§6.5 の設計バッファで両ケースを吸収済み)
- MD-5500 USB 直結の難易度(#8。Phase 4)
- ベースドホワイトの色選択コード(#11。実物の入手待ち。§10.9.1)
- 解像度とカートリッジ識別が結びつく理由(#12)

**解決済み:** 変換ケーブルの双方向対応(#1。Phase 0 で確認)、MD-5000/5500 のコマンド差分(#3。golden で差分ゼロ)、2400dpi の実体(#6。可変ドットの俗称と判明)。

## 実装状況と検証

`ref/` は golden 15 種とバイト一致し、pytest 69 件が通る。検証済みの経路:

- 単色ベタ / 2 色 / 白単独 / 解像度違い / 機種違い / 空白領域(空行スキップ)
- メタリック 4 色(`order` 同値の安定ソート検証)/ 位置合わせのシフト
- 白を含む多層 / 実作業手順(白 → コーティング → 色)/ フルカラー混色
- ハーフトーン 2 方式 / メディア種別(厚紙)

**golden で検証できない領域**(ppmtomd に該当機能がないため、ref/ 独自のテストで担保):

- マジックカラー方式と `auto` 方式の振り分け(§6.6)
- `passes` による重ね刷り(§6.2)
- 設定ファイルの読み込みと検証
