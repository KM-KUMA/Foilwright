## D-001: プリンタドライバを自作せず MS PostScript V3 + 自作 PPD を使う

- 状況: 64bit Windows でプリンタとして振る舞う経路をどう実現するか決める必要があった
- 決定: Microsoft PostScript Printer Driver V3 をそのまま使い、自作 PPD を差し替えて独自プリンタとして振る舞わせる
- 理由: 署名不要・Microsoft のサードパーティ製ドライバ廃止方針の影響を受けにくい・PPD 差し替えのみで足りる(DOMAIN §3.3)
- 却下案: ドライバ自作(署名の手間、Microsoft の段階的廃止方針の影響を受ける)
- 日付: 2026-07-27 / 状態: active

## D-002: v3 ドライバ形式を採用する

- 状況: プリンタドライバの世代(v3 / v4)を選ぶ必要があった
- 決定: v3 形式を採用する
- 理由: 本構成はポートモニタに依存するが、v4 は Microsoft 製以外のポートモニタを使用できないため v3 一択(DOMAIN §3.4)
- 却下案: v4(サードパーティ製ポートモニタが使用不可)
- 日付: 2026-07-27 / 状態: active

## D-003: 変換器(セッション0・UIなし)とトレイアプリ(ユーザーセッション・UI)の二段構成にする

- 状況: ポートモニタから起動されるプロセスの UI 表示要否と配置を決める必要があった
- 決定: セッション 0 で動く変換器(UI なし・ジョブをキューに積んで即終了)と、ユーザーセッションで動くトレイアプリ(UI あり・キュー監視)に分離する
- 理由: セッション 0 はユーザーのデスクトップから隔離されておりダイアログを表示しても誰にも見えない。特色印刷はカートリッジ交換の指示 UI が必須(DOMAIN §3.5)
- 却下案: 単一プロセス(セッション0からUI表示不能なため成立しない)
- 日付: 2026-07-27 / 状態: active

## D-004: 内部座標は常にドット単位とし、mm は L3 入口のみで扱う

- 状況: 内部で座標をどの単位で持ち回るか決める必要があった
- 決定: 内部座標は常にドット単位。mm は L3(PPD 解釈)の入口でのみ扱い、以降はドットに変換して持ち回る
- 理由: 解像度が機種・設定で変わるため、mm を持ち回ると変換が散らばり丸め誤差が蓄積する(DOMAIN §4.1)
- 却下案: なし
- 日付: 2026-07-27 / 状態: active

## D-005: プレーンは 1bit とし、初版は閾値二値化のみでディザ非実装

- 状況: 階調表現の方式を決める必要があった。公式マニュアルにより「複数特色の同時使用時は中間階調を表現できない」制約が確定しており(DOMAIN §4.2/§13.3)、本用途(白+色の複数特色)はこれに該当する
- 決定: 各インクプレーンを 1bit ラスタとし、初版は閾値二値化のみを実装する。ディザリングは実装しない
- 理由: 主用途のアイデカールはベタ塗りと線が中心で階調表現をほぼ必要としない。ディザを先に入れるとコマンド生成の正しさを検証する段階で変数が増える(DOMAIN §4.2)
- 却下案: なし
- 日付: 2026-07-27(2026-07-28 状況欄を改訂: 旧「機構が階調を持たない」は DOMAIN 0.2.0 で誤りと判明)/ 状態: active

## D-006: ref/(Python 参照実装・恒久)と src/(C# 本番)の二言語を維持する

- 状況: 参照実装と本番実装を同一言語に統一するか、二言語で維持するか決める必要があった
- 決定: ref/(Python・恒久維持)と src/(C#・本番)を異なる言語のまま維持する
- 理由: MD のコマンド言語には公開仕様書がなく実装は推測に基づく。同一言語では同じ誤解を両方で踏む。異なる言語で二度書くことで仕様理解の曖昧な箇所が挙動の差として顕在化する(DOMAIN §4.7)
- 却下案: 単一言語(同じ仕様誤解を両方で踏むリスク)
- 日付: 2026-07-27 / 状態: active

## D-007: ppmtomd 出力を golden とする三段検証を行う

- 状況: 実装の正しさをどう検証するか決める必要があった
- 決定: ppmtomd(20年の実績を持つ C 実装)の出力を golden とし、golden ⇔ ref ⇔ src の三段で一致検証を行う
- 理由: 一致/不一致の組み合わせで「C# の移植バグ」「仕様理解の誤り」「Python 側のバグ」を切り分けられる(DOMAIN §9)
- 却下案: なし
- 日付: 2026-07-27 / 状態: active

## D-008: 解像度上限は 1200x600 とし、2400dpi は追わない

- 状況: カタログ上 2400x2400 dpi とされる中、実装が対応する解像度の上限をどこに置くか決める必要があった
- 決定: 1200x600 を実装上の上限とする
- 理由: 既知の実装(Ghostscript md5k、コミュニティ製ユーティリティ)もこの値までしか到達していない。2400 が半ドットずらしの複数パスで実現されるとしてもパス数増加は版ズレのリスクを増大させ、特色を重ねる用途では解像度向上より位置ズレの損失が上回る可能性が高い(DOMAIN §11.1)
- 却下案: 2400 追求(版ズレリスク増、用途上不要)
- 日付: 2026-07-27 / 状態: active

## D-009: Phase 3 成立まで USB-パラレル変換ケーブル単一経路とし、MD-5500 USB 直結は Phase 4 保留

- 状況: MD-5500 は USB 直結が可能だが、パラレル経路と並行して対応するか経路を統一するか決める必要があった
- 決定: Phase 3 が成立するまで両機種とも USB-パラレル変換ケーブル経由に統一する。MD-5500 の USB 直結対応は Phase 4 として Phase 3 成立後に実施する
- 理由: 経路を 1 本に固定することで Phase 1(タイミングリスクの関門)における原因の切り分けが容易になる(DOMAIN §5.3 / §11.3)
- 却下案: 並行2経路(Phase 1 失敗時の原因候補が倍になる)
- 日付: 2026-07-27 / 状態: active

## D-010: ライセンスは GPL-3.0。mfilemon/Ghostscript/ppmtomd は非同梱、解析対策なし、公開先行

- 状況: ライセンス形態、他者コードの同梱可否、解析対策の要否、公開と配布の順序を決める必要があった
- 決定: GPL-3.0 を採用する。mfilemon・Ghostscript・ppmtomd は同梱せずインストール手順で案内するのみとする。難読化・解析対策は行わない。GitHub での公開を配布より先に行う
- 理由: 参照する ppmtomd / gdevmd2k が GPL 系であり「参照」と「移植」の境界が曖昧になりうるため最初から GPL とする。mfilemon(GPL-3.0)・Ghostscript(AGPL-3.0)は他者コードの配布責務を負わない。全体を GPL で公開する以上、解析対策には意味がなく、むしろ ref/ による第三者検証可能性が信頼性そのものになる。GitHub 公開により改竄不能なタイムスタンプが残るため公開を先行させる(DOMAIN §12)
- 却下案: なし
- 日付: 2026-07-27 / 状態: active

## D-013: 機種プロファイル・パレット定義のファイル形式は YAML

- 状況: ref/(Python)着手にあたり、`profiles/` と `palette/` の形式を決める必要があった。Python 標準ライブラリは YAML を読めず、外部依存(PyYAML)を要する
- 決定: YAML を採用し、ref/ は PyYAML に依存する。src/(C#)側は YamlDotNet 等を使う
- 理由: 設定ファイルは ref/ と src/ が共有する土台であり(DOMAIN §8 / §4.5)、後からの形式変更は両実装と DOMAIN の書き直しを伴う。DOMAIN §5.1/§6.1 のスキーマがすでに YAML で記述されており、そのままファイル化できる。実測値の由来を注記するためコメントが必須で、JSON は不可。入れ子の配列(magic_rgb 等)は YAML が最も素直に書ける
- 却下案: TOML(標準ライブラリで読め依存ゼロを維持できるが、DOMAIN のスキーマ表記を全面改訂する必要があり、配列テーブル記法が読みにくい)/ JSON(コメントが書けず、実測データを育てるファイルに不向き)
- 日付: 2026-07-28 / 状態: active

## D-014: 用紙寸法表は機種系列ごとの独立ファイルにし、プロファイルから参照する

- 状況: emitter と設定ファイルを結線するにあたり、用紙寸法表(A4 = 幅 4800 ドット等、全 8 種類)の置き場所を決める必要があった。ppmtomd は同じ表を**機種系列ごとに 2 つ**持つ(5000 系 / pre5000 系、ppmtomd.c:51-81)
- 決定: `papers/{系列名}.yaml` として独立させ、`profiles/*.yaml` の `paper_table` フィールドが名前で参照する。初版は `papers/5000-series.yaml`(MD-5000 / MD-5500 / DP-5000 共通)のみ
- 理由: MD-5000 と MD-5500 は同一の表を共有するため、機種プロファイルに直接書くと同じ内容が 2 ファイルに重複し、片方だけ更新する事故が起きうる。DOMAIN §5.5 が既に「5000 系共通」という括りで記述しており、系列という単位が実在する。将来 OEM 系(Citizen Printiva 等、§9.3.1)を追加する際も表を 1 つ足すだけで済む
- 却下案: 機種プロファイルに直接記述(1 ファイルで完結する単純さはあるが、同内容の重複が生じる。将来 MD-5000/5500 で実測値の差が判明した場合はこちらが素直になるため、その時点で再検討する)/ 設定ファイルに置かずジョブ設定として渡す(換算表がコードに埋まり §4.5 の趣旨に反する)
- 日付: 2026-07-28 / 状態: active

## D-015: マジックカラーの色マッチングは各チャンネル独立判定(整数演算のみ)

- 状況: §6.3 は tolerance による近傍マッチングを要求していたが、「近い」の測り方が未定義だった。距離の定義次第で同じ `tolerance` 値の意味が変わる(白と銀のずれは、チャンネル最大値なら 41、ユークリッドなら約 64、合計なら 111)
- 決定: R・G・B のずれが**すべて** `tolerance` 以内ならマッチとする。複数マッチ時は最も近いもの(距離 = ずれの最大値)、同点なら `order` の小さいほう。非マッチ画素はどのプレーンにも乗せない
- 理由: **整数演算のみで完結し、`ref/`(Python)と `src/`(C#)で判定が食い違わない。** ユークリッド距離は平方根で浮動小数点が入り、境界付近の色だけ判定が分かれてバイト列が一致しなくなる恐れがある(§9.2 の三段検証の前提が崩れる。§4.9 の安定ソート問題と同種)。また `tolerance: 8` が「各チャンネル ±8」と読め、DOMAIN の暫定初期値の想定と一致する
- 却下案: ユークリッド距離(人間の感覚に近いが浮動小数点の言語差リスク。二乗のまま比較すれば整数化できるが `tolerance` の意味が変わり初期値の書き直しが必要)/ マンハッタン距離(整数だが同じ値で許容範囲が約 1/3 になり、初期値の見直しが必要)
- 日付: 2026-07-28 / 状態: active

## D-016: インク指定方式は 3 種類を用意し利用者が選ぶ。既定は自動判別

- 状況: 実際の用途は特色とフルカラーの混在を要求する(白目は特色ホワイト、それ以外は赤青黄を含むフルカラー)。しかし L2 の入口は排他的な 2 つ(マジックカラー / CMYK 分解)しかなく、どちらか一方では成立しない。さらに用途によって最適な方式が異なる — デカール制作では原稿の側で既にレイヤーが分離されているが、通常の画像印刷では分離されていない
- 決定: 3 方式(`auto` / `per_page` / `spot_only`)を用意し、印刷ダイアログから選択可能にする。既定は `auto`(1 枚の原稿から特色を先に判定し、残りを CMYK 分解へ回す)
- 理由: 入力の性質が違うだけで優劣ではないため、単一方式への固定は誤り。`auto` を既定とするのは §1.1 が「任意のアプリの印刷ダイアログから通常のプリンタとして」を掲げているためで、何も設定せず刷った利用者が期待どおりの結果を得られる方を既定にすべき。`auto` の誤爆リスクは `tolerance` の抑制と §7.2 のプレビューで実用上抑えられる。既定値の永続化は Windows の標準機能(PPD + 印刷設定)で足り、追加実装が不要
- 却下案: 単一方式への固定(用途の一方を切り捨てる)/ `per_page` を既定にする(主用途には最適だが、通常の画像印刷が期待外れになる)/ 原稿を常に 2 枚要求する(位置合わせの責任を利用者に負わせる)
- 日付: 2026-07-28 / 状態: active

## D-017: 先行機を MD-5500 の USB 直結に変更する(D-012 を差し替え)

- 状況: D-012 で MD-5000 を先行機としたが、その理由「経路を 1 本に固定して切り分けを容易にする」という前提が崩れた。Phase 1 で 5 パターンを 2 経路から送出していずれも到達せず、公式ドライバ(32bit 仮想 PC)でも「通信エラー(デバイスを識別できません)」で失敗した。セルフテストは成功しており機械は正常。**残る変数が USB-パラレル変換ケーブルの経路そのものに絞られた**(§11.1.1)
- 決定: 先行機を MD-5500 に変更し、本体の USB ポートで直結する。Phase 0(デバイス列挙)からやり直す
- 理由: **変換ケーブルという最大の変数を経路から除去できる。** MD-5500 は USB を前提とした世代であり、公式ドライバが素直に動作する可能性も高い。golden で MD-5000 と MD-5500 のバイト列が完全一致することを確認済み(§11 #3)のため、機種プロファイルの差し替えのみでコード変更は不要(§4.4 の設計が効く)。あわせて §11.3 の未確定事項(USB 直結が「楽」か「重」か)も同時に判明する
- 却下案: MD-5000 のまま別の変換ケーブルを探す(入手に時間がかかり、そもそも変換ケーブル経由で公式ドライバが動作した前例を確認できていない)/ パラレルポート搭載 PC に直結(本来の使い方を再現できるが、該当する機材の有無に依存する)
- 日付: 2026-08-01 / 状態: active

**D-012 は superseded by D-017。** ただし「経路を 1 本に固定する」という原則自体は維持する。MD-5500 の USB 直結に固定し、変換ケーブルとの併用はしない。

## D-018: L0 は ALPS USB バルクプロトコルを自前実装する(Windows 印刷スタックに委ねない)

- 状況: §11.3 / §11 #8 は「MD-5500 の USB 直結は標準 `usbprint.sys` が掴む楽なケースで、L0 の追加実装は不要」と判断していた。しかし実測の結果、**バルクエンドポイント上に ALPS 独自のパケット層があり、RGL の生ストリームは受け付けない**ことが判明した(書き込むとリンクごと落ちる)。スプーラ経由で RAW を流す方式では、この層を挟めないため原理的に印刷できない
- 決定: L0 は Windows の印刷スタックに委ねず、バルクエンドポイントを直接開いて DOMAIN §15 のプロトコルを実装する。送信要求 `05 ff` → 許可 `06` → データパケット `02 01 {len-1} {最大32764B}` → 受理 `06` の往復で RGL を運ぶ
- 理由: **実機で成立を確認済み**(§15.4 / Phase 1 成立)。ppmtomd 形式の RGL がそのまま通ったため、L1 / L2 は一切変更せずに済み、レイヤ分離(§3)が結果的に守られた。あわせてカセット状態の読み出し(§11.4 / §11 #9)も同じ経路で実現でき、§7.2 のプリンタ状態表示と §11.0 が挙げた 4 件が一括で解決する

## D-019: パレットにプロセスインク(CMYK)を表現する。判別は `channel` フィールドの有無

- 状況: `palette/default.yaml` には特色(白・メタリック 4 色)と黒しかなく、素の C/M/Y が存在しない。実機での多色刷り検証(§15.5)では printer_code をスクリプトに直書きして回避したが、これは DOMAIN §4.5(インク一覧をコードにハードコードしない)に反するため本番では使えない。一方で CMYK を既存スキーマのまま追加すると `magic_rgb` によるマッチング対象になり、**純粋なシアンの画素が「特色シアン」として拾われて CMYK 分解を通らなくなる** — auto 方式の挙動が変わってしまう
- 決定: 同一ファイル内でインクに種別を持たせる。**判別は専用の `kind` フラグではなく、`channel` フィールド(`C`/`M`/`Y`/`K`)の有無で行う。**
  - `channel` を持つインク = **プロセスインク**。CMYK 分解の受け皿になる
  - `magic_rgb` を持つインク = **特色インク**。マジックカラーのマッチング対象になる
  - **両方を持つことを許す**(黒がこれに該当する)
  - どちらも持たないインクはエラー(選択される経路が存在しないため)
  - `channel` の値はパレット内で一意(2 つのインクが C を主張すると分解先が曖昧になる)
  - `magic_rgb` と `tolerance` は特色インクのみ必須。プロセス専用インクでは省略する
- 理由: **黒が二重の役割を持つことが実装検討で判明したため、排他的な `kind` フラグでは表現できない。** 黒は「純黒画素にマッチする特色」であると同時に「CMYK 分解の K の受け皿」でもあり、物理的には同一のリボン・同一の printer_code である。フィールドの有無で判別する方式なら、この二重性が自然に表現でき、**新しい概念(種別という語彙)を導入せずに済む**。判断タイムで採択した B 案(同一ファイル + インクに種別を持たせる)の趣旨は保っている
- 却下案: `kind: spot | process` の排他フラグ(黒の二重役割を表現できず、黒を 2 エントリに分けると同じ printer_code が重複して多色ジョブで同じリボンを 2 回刷る事故になる)/ プロセスインクを別ファイルに分離(A 案。分離は明快だがインク定義の所在が 2 箇所になり、機種プロファイルからの参照も 2 系統になる)/ CMYK を機種プロファイルに置く(C 案。最小の変更だが §4.5 の「インクは設定で決まる」原則を骨抜きにする)
- 補足(後続課題): auto 方式で、`magic_rgb` と `channel` の両方を持つインク(黒)がマッチと分解の双方から画素を受け取る場合、**プレーンを合成して 1 パスにまとめる必要がある**(2 回選択すると同じリボンで 2 回刷る)。本決定の実装範囲には含めず、auto 方式の改修時に扱う
- 日付: 2026-08-04 / 状態: active

## D-025: 先行機を MD-5000(パラレル + 変換ケーブル)へ戻し、L0 に送出方式を 2 系統もつ(D-017 を差し替え)

- 状況: D-017 で先行機を MD-5500 の USB 直結に変更し、実際に実機印刷まで到達した(§15.4 / §15.5)。しかし 2026-08-04 深夜、**MD-5500 に「ペーパーフィードメカニズム異常」が発生し、電源再投入・PC 再起動・USB 再接続・リボン取り外しのいずれでも解消しなくなった**(§11.4)。純正ドライバでも同じエラーが出るため機構側の状態であり、復旧の見込みが立たない
- 決定:
  1. **先行機を MD-5000 へ戻す。** 接続は USB-パラレル変換ケーブル経由
  2. **L0 に送出方式を 2 系統もつ。** MD-5500 の USB 直結は ALPS 独自のパケット層(§15.2)を使い、**MD-5000 のパラレル経路は RGL を包まずそのまま送る**
  3. デバイス探索の VID を設定可能にする(直結は ALPS 自身の `044E`、変換ケーブル経由はケーブル側の `056E`。§10.1.1)
- 理由:
  - **手を止めないため。** MD-5500 の復旧見込みが立たない以上、動く機械で開発を進める方が合理的。L1 は MD-5000 と MD-5500 で golden がバイト完全一致しており(§11 #3)、**プロファイルの差し替えだけで済む** — 機種差を L1 に閉じ込めた設計(§4.4)がここで効く
  - **パラレル経路にパケット層は存在しないとみられる。** ppmtomd はパラレル向けに生の RGL をそのまま出力しており、パケット層があるならその出力は成立しない。**したがって生送出が正しい**【推測。実機で確認する】
  - **実装コストが小さい。** 生送出はパケット層より単純(包む処理が無いだけ)で、デバイス探索・タイムアウト・ドレイン・応答検査といった共通部分はそのまま再利用できる
  - **7 月の失敗を再検証する価値がある。** D-017 の根拠となった「MD-5000 + 変換ケーブルでデータが到達しない」(§11.1.1)は、**当時「読み残しが滞留して会話がずれる」問題を知らなかった**時期の観測である(§11.4 の訂正)。ドレイン・タイムアウト・応答の中身検査を実装した現在は、同じ構成でも結果が変わりうる
- 却下案: **MD-5500 の復旧を待つ**(実装を分けずに済むが、修理が必要な場合に長期間止まる)/ **MD-5500 のパケット層を流用してパラレルへ送る**(ppmtomd の挙動と矛盾し、成立する根拠がない)
- 補足: MD-5500 は放棄しない。機構が復旧したら**両機種を対象として維持する**(§9.3 の方針どおり、機種差はプロファイルに閉じる)。USB 直結の実装と実測記録(§15)はそのまま資産として残る
- 日付: 2026-08-05 / 状態: active

**D-017 は superseded by D-025。** ただし「経路を 1 本に固定して切り分けを容易にする」という原則は維持する — 当面は MD-5000 + 変換ケーブルに固定し、MD-5500 との併用はしない。

## D-026: パレットのインクに `barcode`(カセットの物理 ID)を持たせる

- 状況: §7.3 のカセット過不足判定を実装するには、「ジョブが必要とするインク」と「プリンタが報告する装填カセット」を突き合わせる必要がある。しかし**この 2 つは別々の番号体系である**(§10.9.2 / §13.7.5)。パレットが持つ `printer_code` はホストがプリンタへ送る色選択バイトであり、状態応答(`05 01`)が返すのはカセットに印刷されたバーコード番号で、値が一致しない(例: 紙用特色ホワイトは `printer_code` `0x0B` / バーコード `0x10`、メタリックゴールドは `0x04` / `0x08`)。**対応表が無いため判定できない**
- 決定: **パレットのインク定義に省略可能な `barcode` フィールドを追加する。** 値は §13.7.5(純正ドライバの文字列リソースから抽出したカセット名の対応表)に基づく実測値
- 理由:
  - **§4.5 の原則(インクの情報は外部ファイルから読む)に従う。** インクごとの属性であり、コードに表を置くと第三者製インク(§10.10)を追加したい利用者が触れなくなる
  - **`channel` を追加した D-019 と同じ形。** スキーマの拡張方法として前例があり、省略可能にすれば既存の定義を壊さない
  - バーコードは**カセットの物理的な識別子**であって推測の余地がない。§13.7.5 は純正ドライバから直接得た一次情報である
- 却下案: **コード内に対応表を持つ**(`MachineRoute` と同様の扱い。機種→VID のような装置固有の知識ならコードでよいが、**インクは利用者が増やしうる**ため不適)/ **`label` の文字列で突き合わせる**(品番を含む表示用の文字列に依存するのは脆く、表記ゆれで壊れる)/ **printer_code から導出する**(対応に規則性が無く不可能)
- 補足: **エラー中は状態応答のカセット情報が更新されない**(§11.4 で実測)。過不足の判定は**エラービットが立っていないときの応答に限って有効**であり、エラー中に「インクが足りない」と表示してはならない。現物と食い違う指示になる

## D-027: 白版モードは 3 択とし、パレットの `auto_undercoat` を設定が上書きする

- 状況: §7.1 は設定項目として「白版モード(なし / 自動生成 / マジックカラー指定)」を挙げていたが、**各選択肢が何をするかは定義されていなかった**。実装するには意味を確定させる必要がある。また白の生成方法はパレットの `auto_undercoat` フラグでも決まるため、設定と二重に効く
- 決定: 次の 3 択とする。

  | 設定 | 動作 |
  |---|---|
  | **なし** | 白のプレーンを作らない(パスが 1 つ減る) |
  | **自動生成** | 他インクが乗る画素の和集合を白にする(`auto_undercoat` 相当) |
  | **マジックカラー指定** | 白の `magic_rgb` に一致した画素だけを白にする |

  **設定がパレットの `auto_undercoat` を上書きする。** パレット側のフラグは既定値として残す
- 理由:
  - **主用途が「白の形を自分で決めたい」場面だから。** §1.2 はウォータースライドデカール制作を主用途としており、アイデカールの白目のように**白の形を原稿側で制御する**使い方が中心になる。「自動生成 / なし」の 2 択にするとこの用途が設定から選べなくなる
  - **普通紙では白の下地が不要**であり、「なし」を選べればパスが 1 つ減ってリボンと時間を節約できる
  - `auto_undercoat` は**「このインクは下地として使える」というインクの性質**であり、「今回のジョブで下地を作るか」という**ジョブごとの選択**とは別の概念である。両方が存在してよく、後者が前者を上書きするのが自然
- 却下案: **2 択(自動生成 / なし)にする**(実装は単純だが、主用途であるマジックカラーでの白版指定が選べなくなる)/ **パレットの `auto_undercoat` だけで決める**(ジョブごとに切り替えられず、同じパレットで普通紙とデカールを刷り分けられない)
- 補足: **`Raster.cs` の既存関数(golden で検証済み)は変更しない。** 白版モードの適用は L2 のジョブ組み立て(`JobAssembly`)で行う

## D-028: プレビューでインクを個別に除外できるようにする(除外 = パレットから外す)

- 状況: 実物のアイデカール原稿(831 色のフルカラー)を `auto` で通したところ、**原稿に一度も使われていないメタリックシルバーのパスが生成された。** 銀の完全一致は 0 画素だが、パレットの `tolerance: 12` の箱に、絵の中のくすんだグレー(`#c6b9bf` 等)が入っていた。**2,951 画素(全体の 0.012%)**のために 1 パスが増え、装填していないカセットを要求する。
  §7.2 はプレビューの目的を「誤爆はリボンと用紙を失うため」と説明しているが、**誤爆を見つけた後にできることが「印刷を中止する」しかなかった。**
- 決定: **プレビューのインク一覧にチェック列を設け、外したインクをそのジョブで使わない。**

  **除外の意味は「そのジョブのパレットからそのインクを外す」と定義する。** プレーンを作ってから捨てるのではない。
  したがって `auto` では、除外したインクに割り当てられていた画素は**そのまま CMYK 分解へ回る**(§6.6 の `auto` の定義どおり)。

  除外はジョブごとの上書きであり、既定値には保存しない(D-024 の二層のうち上層のみ)。
- 理由:
  - **誤爆は原理的に避けられない。** 写真的なフルカラーを `auto` に通す限り、どのマジックカラーでも同種の取りこぼしが起きる。原稿ごとに tolerance を調整するのは非現実的
  - **プレビューの存在意義を完成させる。** 見つけられるのに手が出せないのは中途半端で、除外があって初めて §7.2 の「リボンと用紙を失わない」が成立する
  - **「パレットから外す」と定義すると穴が開かない。** プレーンを捨てる定義にすると、除外した画素が未印字の穴として残る。パレットから外せば `auto` の規則がそのまま働き、その画素は CMYK で刷られる
  - **装填状況に応じてジョブを通せる。** カセットを持っていない特色が誤爆しても、外して刷り進められる
- 却下案:
  - **パレットファイルを選べるようにする**(組み合わせのたびにファイルが増え、誤爆した色を外すという一時的な操作に永続的なファイルを要求する)
  - **`tolerance` を下げる**(対症療法。別の色で再発し、全ジョブに影響する)
  - **面積が閾値未満のスポットプレーンを自動で落とす**(小さい特色の意匠 — 小さなロゴなど — を黙って消す。§0.1 の「推測で埋めない」に反する)
  - **装填されているカセットに自動で絞る**(実機が繋がっていないとプレビューできなくなる)
- 補足:
  - **再ラスタライズはしない。** 除外を切り替えたら、切り出し済みの画像を保持したまま L2 のジョブ組み立てだけをやり直す。Ghostscript の再実行(A4/1200x600 で約 2 分)を挟まないため、切り替えは即座に返る
  - `Raster.cs` の golden 検証済みの関数は変更しない。除外は `JobAssembly` へ渡すインク一覧の段階で行う
- 日付: 2026-08-19 / 状態: active

## D-029: 色補正を選べるようにし、既定を `Photo` にする。テーブルは同梱する

- 状況: 実物のアイデカール原稿(831 色のフルカラー)を刷ったところ、**紫・緑・茶が黒一色になり、赤だけ色が出た**。切り分けの結果、リボン 4 色は正常に刷れ、ハーフトーンも機能しており(インク別ベタ塗り検査図を実機で確認)、**原因は色分解だけ**と確定した。
  `ref/` と `src/` が実装しているのは ppmtomd の `colcorPlain` で、`k = min(c, m, y)` を 3 成分から引く**完全な下色除去**である。**最小の成分が必ず 0 になる**ため、シアンが最小になる色ではシアンが刷られず黒に置き換わる。この原稿ではそれが大半だった。
  ppmtomd の man によれば **`Photo` はディザ指定時の既定**であり、カラーを「ALPS の Windows ドライバから導出したルックアップテーブル」で補正する。**`Plain` を使っていたのは golden をそれで採ったからで、積極的な選択ではなかった。**
- 決定:
  1. **色補正を設定項目にする**(`None` / `Plain` / `Photo`。`DyeSub` は昇華紙用で当面対象外)。
  2. **既定は `Photo`** とする。`Plain` は golden 検証に必要なので残す。
  3. **`photo_colcor` のテーブルをリポジトリに同梱する**(`colour/photo_colcor.bin`、16,384 バイト)。
- 理由:
  - **`Plain` は写真的なフルカラーに向かない。** 完全な下色除去は、印刷用の版下のように色数が限られた原稿を想定した式であり、階調のある絵に掛けると彩度が失われる。実測でも `Photo` の出力は `Plain` の 1.6 倍のデータ量(15,089 対 9,417 バイト)になり、ドット数の差がそのまま色の差になる
  - **`Photo` は純正ドライバ相当の色を与える。** §1.1 の「純正ドライバでできることは実現する」に直結する
  - **同梱を選ぶ理由はライセンスにある。** ppmtomd は GPL-2.0-or-later で配布され、`LICENCE` に「もっと緩いライセンスが必要なら相談してほしい」とまで書かれている。Foilwright は GPL-3.0-or-later であり取り込める。**GPL が想定しているとおりの再利用**である
  - **ALPS の著作物とは扱いが異なる。** §12.3 が禁じているのは権利者が再配布を許していないもの(マニュアル・ドライババイナリ)であり、GPL で明示的に許諾されたものを同じ扱いにするのは線引きを誤っている。**本プロジェクトは既に ppmtomd のアルゴリズムを全面的に再実装している**(プロトコル・ディザ行列・色分解式)。アルゴリズムは可でデータ表は不可、という区別に根拠がない
- 却下案:
  - **テーブルを同梱せず、手元の ppmtomd から実行時に読む**(リポジトリは綺麗なままだが、`Photo` を使う利用者全員に ppmtomd を要求することになる。Ghostscript は代替の効かない大きな機能だから外部依存を許したのであって、16KB の表で同じ判断はしない)
  - **`None` を実装して済ませる**(黒プレーンを作らないため暗部が濁り、リボンも 3 本余計に減る。`Photo` が入れば使う理由がない)
  - **`Plain` のまま `tolerance` や後処理で誤魔化す**(原因が式にあるのに対症療法を重ねることになる)
- 補足:
  - **golden でバイト一致検証ができる。** `-colourcorrection Photo` で採取した g18(CoarseHalftone / 600)・g19(Halftone / 600)・g20(CoarseHalftone / 1200)を基準にする。1200 を含めたのは、**ガンマの既定値が解像度で変わる**ため(600 は 0.8、1200 は -0.9)
  - **ガンマ表は `Photo` の一部である。** `initgamma` を適用してから表を引く。既定値はディザの有無と解像度で決まり、`-gamma` で上書きできる
  - **`opt_keepblack` は既定で無効。** 有効にすると純黒を黒 100% に固定する。今回は実装対象に含めない(未使用の分岐を先に作らない)
  - 未取り込みのテーブルが 2 つある(`vphoto_colcor` = 多値モード用、`dyesub_colcor` = 昇華紙用)。必要になった時点で追加する
- 日付: 2026-08-19 / 状態: active

  - **`tolerance` をメタリックだけ小さくする**(対症療法。別の色で再発する。D-028 で却下済み)

- 補足:
  - **D-028 は撤回ではなく一般化である。** 除外の意味(「そのジョブのパレットからそのインクを外す」)も、再ラスタライズを避ける実装も、そのまま生きる
  - **プロセスインク(CMYK の受け皿)も一覧に出す。** 外せる必要はあまりないが、一覧から消すと「なぜこのインクは操作できないのか」という疑問を生む
  - 既存の `settings.json` に項目が無い場合は、**メタリック無効・それ以外有効**として読む(移行時に黙って挙動が変わらないよう、既存利用者にも同じ初期値を与える)

## D-031: 重ね塗りの回数はプレビューで変えられる。パレットは既定値に徹する

- 状況: `passes`(重ね塗り)を実装した(§6.2)。回数はパレット(`palette/default.yaml`)にしか書けず、**変えるには YAML を編集して再起動する**しかない。しかし §10.5 のとおり**適正な回数は媒体と隠蔽力の要求で変わる**ため、刷り比べながら決める性質のものである。利用者から「回数を自分で決めたい」と要望が出た。
- 決定: **プレビューのインク一覧の「パス数」列を編集可能にする。** D-024 の二層にそのまま乗せる。

  | 層 | 実体 |
  |---|---|
  | 既定値 | パレットの `passes`(インクと媒体の組み合わせに対する妥当な初期値) |
  | ジョブごとの上書き | プレビューの「パス数」列 |

  **上書きは「この設定を既定値として保存」で永続化できる**(D-030 の許可リストと同じ扱い)。保存先は `TraySettings`(`settings.json`)であり、**パレットの YAML は書き換えない**。

  **範囲は 1〜8。** 範囲外は受け付けず、その場で拒否する。
- 理由:
  - **刷り比べて決める値だから。** §10.5 は「実測で決める」と明記しており、パレットの 2 は暫定値。**YAML を編集して再起動する手順は、比較実験の道具として重すぎる**
  - **既に同じ形が 3 つある。** 白版モード(D-027)・インクの許可リスト(D-030)・色補正(D-029)がいずれも「パレットや既定値が下、プレビューが上」の二層になっている。**同じ場所に同じ操作で置くのが一番学習しやすい**
  - **パレットを書き換えない理由:** パレットは**インクの性質**を書く場所であり(§6.1)、**そのジョブでどう刷るか**とは別の概念である。D-027 が `auto_undercoat`(インクの性質)と白版モード(ジョブの選択)を分けたのと同じ切り分け

## D-032: 白版モードに「不透明」を足す。純白でない画素すべてに白を敷く

- 状況: 実物のアイデカールをデカールフィルムへ刷ったところ、**白目に白が乗らなかった**。白版モードは `auto` にしてあり、白のパス自体は出ていた(ドット 142,826)。
  **これは不具合ではなく `auto` の定義どおりの結果である。** D-027 の `auto` は「**他インクが乗る画素の和集合**」であり、**色が刷られる場所の下に白を敷く**ものだからである。白目は原稿でほぼ白 → CMYK 分解でドットがほとんど立たない → **その下に白も敷かれない。**

  |---|---|
  | なし | 白のプレーンを作らない |
  | 自動生成 | 他インクが乗る画素の和集合(D-027) |
  | マジックカラー指定 | 白の `magic_rgb` に一致した画素だけ |
  | **不透明** | **純白(255,255,255)でない画素すべて** |

  - **クリアフィルムのデカールでは、`auto` の定義では白抜きが原理的に作れない。** §1.2 の主用途がこれである以上、定義の穴として塞ぐ必要がある

  - **明るさの閾値で白にする**(例: 全成分 > 200)。**閾値を原稿ごとに調整することになり、外しやすい**。純白かどうかの二値判定のほうが説明しやすく再現性がある。**【追記 2026-08-20】却下の理由がもう 1 つある** — 実物の原稿では**白目も紙の余白もまったく同じ `(255,255,255)`** であり、**明るさでは両者を区別できない**。この案は「白目に白が乗らない」問題を**そもそも解決しない**(D-034 の訂正を参照)
  - **`auto` の定義を変える**。既存の用途(普通紙で色の下だけに白を敷く)を壊す。D-027 は残す
- 補足:
  - **アンチエイリアスの縁が白版に入る。** 純白でない画素はすべて対象になるため、絵の輪郭がわずかに広がる。デカールでは**むしろ都合がよい**(白の縁が色からはみ出す方向)

## D-036: PNG デコーダを `ref/` と `src/` の両方に自作する。既製品を使わない

- 状況: D-035 の訂正により、白版の情報源は **Ghostscript の `pngalpha` 出力**と決まった。
  現行の `ppmraw`(P6 の生バイト)と違い、**PNG を読む必要が出る**。読み方には既製品を使う道と自作する道がある。
- 決定:
  1. **最小の PNG デコーダを `ref/foilwright_ref/` と `src/Foilwright.Core/` の両方に書く。**
  2. **対応するのは Ghostscript の `pngalpha` が出す形だけ** — カラータイプ 6(RGBA)/ ビット深度 8 /
     インタレース無し / 圧縮方式 0 / フィルタ方式 0。**それ以外は明確な例外で止める**(汎用デコーダを書かない)。
  3. **2 実装の出力をバイト比較する**(D-033 の枠を使う)。
  4. **白版の話には入らない。** まずデコーダだけを作って突き合わせ、その後で
     「アルファをどこまで持ち回るか」を別途決める。
- 理由:
  - **依存が増えない。** 展開に要る zlib は **Python にも .NET にも標準で入っている**
    (`zlib` / `System.IO.Compression.ZLibStream`)。`ref/` の依存は **PyYAML 1 つ**のままにできる。
  - **`ref/` を軽く保つのは D-006 の趣旨。** Pillow は参照実装に対して重い。
  - **扱う形が 1 種類に固定されている。** Ghostscript が出すのは PNG 規格の中で最も素直な組み合わせであり、
    **汎用デコーダを書くわけではない**。処理は実質 2 つ — zlib の展開と、行頭 1 バイトのフィルタ種別(5 種)の巻き戻し。
  - **突き合わせが効く。** 2 実装をバイト比較する仕組みが D-033 で既にある。
    **自作の誤りは互いに捕まえられる**(2026-08-20 に 1200dpi の欠陥をこの型で発見した実績がある)。
- 却下案:
  - **両方とも既製品**(C# は `System.Drawing`、Python は Pillow)。**`ref/` に Pillow が増える**。
  - **C# だけ既製品、Python だけ自作**。依存は増えないが、**突き合わせが「自作 対 既製品」になり、
    独立した 2 実装という前提が崩れる**。片方が既製品だと、もう片方の誤りは見つかっても、
    **仕様の読み違えが両方に共通する場合を検出できない**という利点も失う。
  - **`pngalpha` を使わず背景色を変えて 2 回描かせる**。**実測で失敗した**(2026-08-20) —
    下塗りする方法と `Install` 手続きを使う方法の 2 通りを試したが、**どちらも差 0 画素**。
    プリンタドライバの PostScript がページを消去して下塗りを捨てるため。
- 補足:
  - **実測(利用者の原稿、A4 相当 600dpi、5100x6600):**

    | | 現行 `ppmraw` | `pngalpha` |
    |---|---|---|
    | 変換時間 | 0.56 秒 | **2.33 秒** |
    | ファイル | 96.3 MB | **371 KB** |
    | 展開後 | 96 MB | 128 MB |

    **ファイルは 260 分の 1 になるが、変換は約 4 倍かかる。** プレビューが開くまでが 1.8 秒延びる。
  - **IDAT は 47 個に分割されていた。** 連結してから展開する必要がある(1 つだけ読んで済ませない)。
  - **フィルタは 5 種すべて出る**(適応的に選ばれる)。**Paeth の実装漏れは典型的な誤り**なので、
    テストで 5 種すべてを踏むフィクスチャを用意する。

## D-037: 白版モード「アルファ」を追加する。色は `ppmraw` のまま、アルファだけ `pngalpha` を追加実行して取る

- 状況: D-035 の訂正と D-036 のデコーダにより、Ghostscript の `pngalpha` から
  「白を塗った」(`alpha=255`)と「何も描いていない」(`alpha=0`)を取り出せるようになった。
  残るのは**この情報をどう本体へ運ぶか**である。
- **測定(2026-08-20。同じ PostScript を同じ解像度で両デバイスに描かせて比較):**

  `pngalpha` の RGBA を白へ合成した結果は、**現行 `ppmraw` の出力と一致しない。**

  | 区分 | 画素数 | 合成後と `ppmraw` で差あり | 割合 |
  |---|---|---|---|
  | 何も描いていない(`alpha=0`) | 33,478,578 | 302 | **0.0%** |
  | 完全に描かれた(`alpha=255`) | 164,949 | 30,358 | **18.4%** |
  | 縁(中間 `alpha`) | 16,473 | 15,488 | 94.0% |

  **縁のアンチエイリアスだけの差ではない。完全に塗られた画素でも 18.4% 食い違う。**
  PNG に `iCCP`(カラープロファイル)チャンクが入っており、**2 つのデバイスで色の出方そのものが違う**
  とみられる【推測】。**`pngalpha` に一本化すると印刷される色が変わる。**
- 決定:
  1. **色は現行の `ppmraw` のままとする。出力を 1 バイトも変えない。**
  2. **6 つ目の白版モード「アルファ」(`alpha`)を追加する。** 規則は **`alpha > 0` なら白**。
  3. **`alpha` を選んだときだけ、Ghostscript を追加でもう 1 回 `pngalpha` で走らせる。**
     他の白版モード(`none` / `auto` / `magic` / `opaque` / `silhouette`)は**今までどおり 1 回で済む**。
  4. **`pngalpha` の RGB は捨てる。使うのはアルファだけ。**
- 理由:
  - **色の確認をやり直さずに済む。** フルカラーが実機で刷れることを 2026-08-19〜20 に確認したばかりであり、
    **そこを触らない**のが安い。
  - **遅くなるのは白版が要るときだけ。** 変換は 0.56 秒 → 2.9 秒(0.56 + 2.33)になるが、
    **クリアフィルムの用途は元々パスが 5〜6 回あって数分かかる**ため 2.3 秒は誤差である。
    普通紙にフルカラーを刷る経路は**今までどおり 0.56 秒**。
  - **縁の半透明も白にする(`alpha > 0`)。** デカールでは**白が色より少しはみ出すほうが都合がよい**
    (透けるより良い)。§7.1.1 の `opaque` と同じ考え方。
  - **将来 `pngalpha` 一本化へ移る道は残る。** 経路が既にあるので、色も切り替えたくなったら比較実験ができる。
- 却下案:
  - **`pngalpha` 1 回に一本化する。** 変換は 2.33 秒で済むが、**描画画素の 18.4% で色が変わる**。
    良くなる可能性もあるが、**確かめるにはデカールとリボンを使う実機比較が要る**。今やる価値が薄い。
  - **常に 2 回走らせる。** 実装は単純になるが、**アルファを使わない用途まで 5 倍遅くする**理由が無い。
  - **背景色を変えて `ppmraw` で 2 回描かせる。** D-036 で却下済み(実測で失敗)。
- 補足:
  - **両者の判定は完全一致ではない。** `pngalpha` が「何も描いていない」と言う画素のうち **302 個**は、
    `ppmraw` では純白ではなかった(3,300 万画素中)。**実害は無いが、完全一致を前提にしない。**
  - **プレビューでインクの使用可否やパス数を切り替えたとき、Ghostscript を再実行しない**
    という既存の性質(D-028 補足)を壊さないこと。**アルファも画像と同じように保持する。**
  - **切り出しはアルファにも同じように適用する。** 用紙寸法での切り出し(§5.5.1)を色とアルファで
    食い違わせない。
- **実機で確認(2026-08-20 同日)。** 利用者が Inkscape で **`test.svg` の原本**(白目の塗りは `fill:#ffffff` のまま)を開き、**印刷ボタンを押して白版モードを `alpha` にしただけ**でデカールフィルムへ刷れた。**白目に白が乗り、`#fefefe` への塗り替えは不要になった。**
  白版の量は **181,422 ドット**(紙全体の 0.54%)で、事前に採取した PS から計算した予想値と完全に一致した。内訳は完全に不透明 164,949 + 半透明の縁 16,473。**§7.1.2 に記録。**
- 日付: 2026-08-20 / 状態: active

## D-038: 送出後に印刷の完了を見張る。自動復帰は入れない

## D-042: マジックカラーをジョブごとに選べるようにする。純正の単色モードもこれで包含する

- 状況: 利用者から「**特色の色とインクを紐づけて印刷できるモード**が欲しい。**色はインクごとに選べるように**」
  という要望。参照として純正ドライバの機能を紹介する記事が挙げられた
  (http://shingoaiko.blog.fc2.com/blog-entry-74.html)。
- **調査で分かった純正の仕組み(2026-08-21):** 記事が扱っているのは**マジックカラーではない**。
  `特色印刷` → `特色設定` → **`インクカセット選択`(ラジオボタンで 1 つだけ)** + `印刷方法: 単色`。
  **カセットを 1 つ選び、そのパスを丸ごとその色で刷る**方式である。
  **原稿のベタ黒が、選んだインクで出る。** RGB 値の話は記事に一切無い。
  **「白を黒として刷る」という知られた回避策は、これのことだった。**
  多色にするには**原稿を色数ぶん作って刷り重ねる**(ページ合成)。
- 決定:
  1. **`magic_rgb` をジョブごとに上書きできるようにする。** 既定値はパレット(`palette/default.yaml`)。
  2. **上書きできるのは色だけ。** `tolerance`(許容誤差)と `order`(順序)はパレットの値のまま。
  3. **どのインクにも色を割り当てられる。** 今は `magic_rgb` を持たないプロセスインク
     (シアン・マゼンタ・イエロー)にも割り当てられるようにする — **純正の `インクカセット選択` に
     紙用シアン等が並んでいたため。**
  4. **色を外せる**(割り当て無し = マジック判定に参加しない)。
  5. **インク指定方式は `spot_only` と `auto` の両方で効く。**
     `spot_only` は指定した色だけ、`auto` は CMYK のフルカラーに加えて指定した色。
  6. **上書きは設定の層で適用する。** パレットを読んだ直後に差し替えた ink 一覧を作り、
     `JobAssembly` / `raster` には**手を入れない**。
- 理由:
  - **判定の仕組みは既にある。** `spot_only`(D-016)と `to_planes_magic` が
    **まさに「色 → インク」の紐づけ**をしている。**足りないのは色を選べないことだけ**だった。
  - **純正の単色モードを包含する。** 「特色ホワイトの色を `(0,0,0)` にする」と指定すれば、
    **原稿のベタ黒が白インクで刷られる** — **純正の『白を黒として刷る』とまったく同じ動作**になる。
    **専用のモードを作る必要が無い。**
  - **DOMAIN §14.6 が既に想定していた。**「公式ドライバではこの割り当てを変更できないが、
    Foilwright はパレット定義を書き換えるだけで衝突しない値に振り直せる」。**UI が無かっただけ。**
  - **公式値は互いに近い**(銀 189,193,197 と白 230,230,230)が、
    **利用者が離れた値を選べば衝突しない。** 色を選べること自体が誤判定対策になる。
  - **設定の層で適用する理由:** `JobAssembly` と `raster` を触らないため、
    **golden も ref//src の突き合わせも影響を受けない。**
- 却下案:
  - **許容誤差も編集できるようにする。** 要望は「色を選べるように」であり、
    **許容誤差まで出すと「なぜか別のインクで刷られる」という分かりにくい事故が増える。**
    必要になってから足す。
  - **順序も編集できるようにする。** 順序は**刷り重ねの層**に効く(§4.3)。色より影響が大きい。
  - **純正と同じ「カセットを 1 つ選ぶ単色モード」を別に作る。**
    **上書きで包含できるため不要。** モードが増えると選び方の説明も増える。
- 補足:
  - **黒は二役である**(`magic_rgb` と `channel` の両方を持つ。D-019)。
    **黒の色を変えると二役の合成にも影響する。** 変えられるようにはするが、この点は文書に書く。
  - D-030(使うインク)・D-031(パス数)と**同じ形**にする — null と空を区別し、
    null なら既定(パレットの値)を都度導出する。

## D-043: 複数ページの原稿は明確なエラーで止める。ref と src の食い違いを塞ぐ

- 状況: 利用者から「印刷ダイアログで部数やカラーモードを変えたらどうなるか」と問われ、
  調べる過程で **複数ページの PostScript の扱いが ref と src で食い違っている**ことが分かった
  (2026-08-21)。
- **実測で分かったこと:**
  - Ghostscript は `-sOutputFile` に `%d` が無いと、**1 つの PPM ファイルに複数の画像を連結**して書く
    (`ppmraw` は PNM の連結を作る)。2 ページの PS から `P6` ヘッダ 2 個・208,741,856 バイトが出た。
  - **`src/Foilwright.Core/Ppm.cs`** は長さの完全一致を要求するので例外になるが、文言が
    `truncated PPM data: expected 104370858 bytes, got 208741786` で、
    **「足りない」と言いながら実際は 2 倍来ている**。原因がまったく読み取れない。
  - **`ref/foilwright_ref/raster.py` の `read_ppm`** は `data[pos : pos + pixel_bytes]` でスライスしており、
    **余りを黙って捨てて 1 ページ目だけ返す**。短いときだけエラーにする。
- 決定:
  1. **両実装の挙動を「複数ページは明確なエラーで止める」に揃える。**
  2. 残りバイト数で 4 通りに分ける — 不足なら従来どおり truncated / **余りの先頭が次の PPM なら複数ページ** /
     それ以外の余りは別のエラー / 一致なら正常。
  3. **例外に真偽値の目印を持たせる**(C# は `PpmFormatException.IsMultiPage`、Python は
     `PPMError.is_multi_page`)。Tray はこれを見て日本語の補足を出す。**文言の一致で判定しない。**
  4. Core / ref のメッセージは**英語**のまま(既存に揃える)。**日本語の補足は Tray の層で足す。**
- 理由:
  - **黙って 1 ページ目を刷るのが最悪。** 利用者は 2 ページ刷ったつもりで 1 ページしか出ていないことに
    気づけず、しかも**生産終了品のリボンを消費している**。
  - **文言が原因を示さないと直しようがない。** 「truncated なのに 2 倍来ている」は読み手を確実に迷わせる。
  - **目印を真偽値にするのは、文言を変えたときに壊れないようにするため。**
- **この食い違いが golden で検出できなかった理由(重要):**
  **golden も突き合わせテストも単一ページの入力しか通していない。** 両実装がバイト単位で一致することは
  「同じ入力に対して」しか保証しておらず、**片方だけが受け付ける入力があっても分からない**。
  D-033 で「ジョブ組み立て層を ref/ にも置いて突き合わせる」ことにしたが、
  **突き合わせは入力の範囲でしか効かない** — **異常系の入力を両実装に通す検査が要る**。
- 却下案:
  - **ref に合わせて src も余りを捨てる。** 静かに間違うほうへ揃えることになる。
  - **複数ページを全部処理する。** L2 は 1 ページ前提で組まれており(`per_page` インク指定方式も
    「複数ページ入力は呼び出し元が弾く」前提。§6.6)、対応するなら設計から見直しが要る。
    **今回の要件ではない。**
- **部数の挙動は確定した(2026-08-21 実測)。** Inkscape の印刷ダイアログで**部数 2** にすると、
  **PScript5 が 2 ページの PostScript を吐く** — スプーラがデータを 2 回送るのではない。
  したがって**このエラー経路にそのまま来る**。実機で確認したところ、
  `multi-page PPM: ... (found 2 pages)` と**ページ数まで正しく**出て、日本語の補足も表示された。
  **つまり Foilwright では部数 2 以上は使えない。** 複数枚欲しいときは**部数 1 のまま、
  同じジョブを必要な回数だけ印刷する**(プレビューもその都度出るので、毎回確認できる)。
- 日付- **実装で分かったこと(2026-08-21):**
  - **ページ数は正確に数えられる。** 画素データを走査して `P6` を探すと**偶然一致するバイト列を数えてしまう**が、
    **各画像のヘッダを読んで「次の画像の開始位置」を計算しながら進めば**、手間はページ数に比例するだけで
    (1 ページあたり数十バイトの読み取り)、**100MB 級の画素データには一切触れない**。
    末尾のページが途中で切れている等でヘッダを読み切れなくなった場合は、**嘘の数を出さず
    `found at least N pages` と下限で言う**。
  - **突き合わせテストだけでは「揃って間違う」を検出できない。** 破壊試験で両実装の判定を同時に無効化したところ、
    **分類の一致だけを見るテストは緑のまま通った**。そのため「実際に `multi-page PPM:` で始まること」を
    両側へ要求するテストを別に置いてある。**ref//src の突き合わせは「両者が違う」ことしか見つけられない** —
    **正しさは、突き合わせとは別に固定する必要がある。**
  - **`src/Foilwright.Cli` のエラー表示には日本語の補足を足していない。** Cli は検証用の入口であり
    利用者の経路ではないこと、`DescribeUserError` は Tray にあり Cli から参照できないこと
    (共有するには Core へ移すことになり、層の切り方が崩れる)による。
    **英語の文言そのものが原因を説明している**ので実害は無い。
- 日付: 2026-08-21 / 状態: active

## D-044: 部数はプレビュー側で持ち、1 部ごとに人が紙を入れてから続ける

- 状況: ドライバの印刷ダイアログで部数を 2 以上にすると **PScript5 が複数ページの PostScript を吐き、
  D-043 のエラーで止まる**(2026-08-21 実測)。利用者から「Foilwright 側で部数を設定して
  複数部刷れないか」という要望。
- 決定:
  1. **プレビュー画面に「部数」欄を置く**(1〜20)。ドライバ側の部数は使えないままとする。
  2. **1 部刷り終わるごとに止まり、「次の紙を入れてください」を出して人の確認を待つ。**
     押されるまで次を送らない。**そこで中止も選べる。**
  3. **部数は保存しない**(毎回 1 に戻る)。
  4. **途中でエラーが出たら残りを中止する。**
  5. **プレビューの窓は全部終わるまで閉じない。**
- 理由:
  - **この機械は手差しで運用している。** DOMAIN の実測記録は給紙レバー M(手差し)で、
    **自動給紙は過去に失敗している**(§11.1.1: レバー A では給紙されず M で給紙できた)。
    **紙が無い状態で連続送出すると給紙エラーになり、機構が動いて詰まる危険がある。**

## D-045: 設定のプリセット(用途ごとに名前を付けて保存する)

- 状況: プレビューの設定つまみが 10 個になり(用紙・メディア・ハーフトーン・白版モード・色補正・
  機種・解像度・インク指定方式・使うインク・パス数・色の割り当て・カール補正)、

  「目デカール(フィルム)」と「はがきテスト」のように用途を行き来すると毎回上書きになる。
- 決定:
  1. **設定一式に名前を付けて保存・呼び出しできるようにする。** 保存先は
     `%APPDATA%\Foilwright\presets.json`(`settings.json` とは**別ファイル**)。
  2. **既定値(D-024)とは併存させる。** 既定値は「何も選ばなかったときの初期値」のまま。
  3. **部数と「1 部ずつ確認する」は入れない。** 前者は D-044 決定 3 で
     「そのジョブ限りの量。保存しない」と決めてある。後者は**紙の入れ方(物理的な段取り)**であって
     原稿の設定ではない。
  4. **`UsedInks` / `PassesOverride` / `MagicRgbOverride` の null と空の区別を保ったまま往復する**
     (D-030 / D-031 / D-042 でこの区別に意味があると決めてある)。
  5. **名前の比較は大文字小文字を区別しない。** 利用者から見て同じ名前は同じもの。
- 理由:
  - **別ファイルにする理由:** 既定値とプリセットは**寿命も意味も違う**。
    既定値は「最後に使った設定」に近く、プリセットは「意図して作り置きした設定」である。
    同じファイルに混ぜると、片方を消したいときにもう片方を巻き込む。
  - **既定値を残す理由:** プリセットを一度も使わない人の体験を変えないため。
    プリセットは**上位互換ではなく追加の道具**である。
  - **null と空の区別を保つ理由:** ここを潰すと、D-030 の
    「利用者が明示的に全インクを無効にした」状態が「触っていない」に化け、
    **パレットの既定へ勝手に戻る**。テストで固定した。
- 却下案:
  - **既定値をプリセットの一種として作り直す。** 移行が要るうえ、
    「何も選ばなかったときどうなるか」の説明が複雑になる。
  - **部数もプリセットに含める。** D-044 と矛盾する。
    「3 部のプリセット」を選んだ翌日に気づかず 3 部刷る事故になる。
- **実装で分かったこと:**
  - **プリセットを当てるときは、コンボを 1 個ずつ書き換えるたびに再構成してはいけない。**
    抑えないと**コンボごとに Ghostscript が走り**、しかも `_busy` に弾かれて古い値のまま走る。
    フラグで抑えて**全部書き終えてから一度だけ**組み直す。
  - **再構成の経路は 2 通りに分かれる。** 機種・用紙・解像度・**メディア種別**が変わるときは
    Ghostscript から やり直す(`RefreshPreviewAsync`)。それ以外(ハーフトーン・白版モード・色補正・
    インク指定方式・使うインク・パス数・色)は切り出し済みの画像を使い回す(`RebuildFromImage`)。
    **メディア種別がこちら側に必要な理由:** `RebuildFromImage` は `previous.Config`
    (用紙とメディアを含む)を使い回すため、**メディアだけ変えても反映されない**。

## D-046: リボン消費は自分で数えて書き溜める

- 状況: **このプリンタのリボンは生産終了品で、残量が最大の制約**である。
  プリンタに残量を尋ねる経路(`05 01` の応答の `low` / `high`)は**意味が未解明**で、
  実測でも**新品の白 92 に対し使い込んだ黒 112** と、**残量ではないことが分かっている**(§11.4.3)。
  一方 **Foilwright は刷ったドット数をインクごとに知っている**(プレビューの「ドット数」列)。
- 決定:
  1. **プリンタに聞くのをやめ、刷るたびに自分で数えて書き溜める。** 保存先は `%APPDATA%\Foilwright\usage.jsonl`。
  2. **1 行 1 レコードの JSON Lines** にする。
  3. **累計は「ドット数 × パス数」で数える**(重ね塗りした回数ぶん消費するため)。
  4. **失敗した回も記録する。** 途中で止まってもリボンは減っている。
     **送出そのものが例外で落ちた回も記録する**(そこまでに送ったぶんは刷られている可能性がある。§15.2.2)。
  5. 記録するインク名は**パレットの `name`(識別子)**。表示のときに現在のパレットから
     `label` を引く。**引けなければ識別子をそのまま出す**(古い記録を落とさない)。
  6. **書き込みに失敗しても例外を投げない。** 記録が取れないことより、印刷が止まるほうが困る。
- 理由:
  - **JSON Lines にする理由:** 印刷のたびに追記するファイルであり、**途中で壊れても
    その行を飛ばせば残りが読める**。1 つの JSON 配列にすると、壊れた瞬間に全履歴を失う。
  - **`label` ではなく `name` を記録する理由:** `label` は利用者が編集しうる。
    編集された瞬間に**集計が別インク扱いに割れる**。
  - **失敗した回も数える理由:** 帳簿の目的は「あと何回刷れるか」であり、
    **成功したぶんだけ数えると必ず過小評価になる**。
- 却下案:
  - **プリンタの `low` / `high` を使う。** 意味が未解明で、**新品より使用中のほうが大きい**という
    観測と矛盾する(§11.4.3)。**数字の意味が確実なほうを採る。**
  - **「カセットを新品に替えた」を今回作る。** 履歴が貯まってからどういう形が使いやすいか決めたい。
    **まず数え始めることを優先する**(数え始めなければ、いつまでも判断材料が無い)。
- 補足: **これは推定であって実測ではない。** ドット数と実際のリボン消費が比例するとは限らず
  (ヘッドの温度・メディア種別・重ね方で変わりうる)、**「同じ条件どうしの比較」には使えるが
  絶対量の保証にはならない**。カセット交換の記録が貯まれば、1 本あたりの実力が測れる。
- 日付: 2026-08-21 / 状態: active

## D-048: 「塗る範囲で決まるインク」を第三の種類として足す(光沢仕上げ2 / MF インク)

- 状況: 利用者から光沢仕上げ・光沢仕上げ2・ベースドホワイトへの対応要望。
  §14.7 の調査で **光沢仕上げ2(MDC-FRVG。`printer_code` 0x0E / `barcode` 19)と
  MF インク(MDC-PREP。0x10 / 18)は値が確定**し、**両方とも利用者の手元にある**ことが分かった
  (2026-08-22)。残る 2 つ(光沢仕上げ MDC-FLCG / ベースドホワイト MDC-OPWH)は
  **`printer_code` が不明で、カセットも手元に無い**。
- **足せなかった理由(パレットの壁):** 現行のスキーマは
  `must have 'magic_rgb' (spot ink), 'channel' (process ink), or both` を要求する(D-019)。
  **光沢仕上げも MF インクもどちらでもない** — **「どこに塗るか」を別の方法で決めるインク**である。
  ppmtomd man:564-565「ハーフトーンも色補正も掛からない。オンかオフだけ」、
  man:555-559「全面ベタ、または純白でない画素で使う」。
- 決定:
  1. **第三の種類「塗る範囲で決まるインク」を足す。** パレットに真偽値の印を持たせ、
     検証を「`magic_rgb` / `channel` / その印のいずれかを持つこと」に緩める。
  2. **塗る範囲はジョブごとにインク単位で選ぶ**(D-031 のパス数と同じ形の辞書)。
     値は **`none`(既定)/ `artwork`(純白でない画素)/ `full`(全面)**。
  3. **既定は `none`。** 何もしなければ今までと同じ。
  4. **ハーフトーンを掛けない。** 塗るか塗らないかだけ(man:564-565)。
  5. **位置はパレットの `order` で決める。** MF インク(下地)は白より前、
     光沢仕上げ2 は黒より後。
  6. **MF インクは未検証として記録する。** 値は検算済みの表から取っているが、実機で刷ってはいない。
- 理由:
  - **既定を `none` にする理由:** 動いているもの(白版 `alpha` で目デカールが刷れる経路)を
    一切変えないため。**新しい種類のインクを足しても、使わない人の出力は 1 バイトも変わらない。**
  - **`artwork` を「純白でない画素」と定義する理由:** 透明背景の原稿(Inkscape 等)は
    ppmraw では白に落ちるので、**これで絵の形に一致する**。
    `alpha` 判定にしないのは、**pngalpha の描画は白版モードが `alpha` のときしか走らない**ため、
    別のモードに依存する隠れた結びつきを作らないため。
  - **白版モードに寄せない理由:** 白は `auto_undercoat` という専用フラグで特別扱いされており、
    **光沢仕上げは下地ではなく上掛け**なのでそのままは乗らない。
    **白版モードは実機で成立している唯一の経路であり、触る危険が見合わない。**
- 却下案:
  - **「塗る範囲」の仕組みを一般化し、白版モードもそこへ寄せる。** 設計としては筋が良いが、
    **動いている白の経路を壊す危険**が大きい。分けたまま運用し、必要になったら統合を検討する。
  - **プリンタ内蔵の光沢仕上げ機能(`1b 1a 00 00 4f`)を使う。** 実装は軽いが、
    **印字領域の外接矩形にしか掛からない**(ppmtomd man:186)。
    **デカールでは絵の形に沿わせたい**ので、自前のプレーンを作る側を採る。
  - **光沢仕上げ(MDC-FLCG)とベースドホワイトも同時に足す。**
    **`printer_code` が不明**で、推測で埋めることになる(鉄則 4 / §4.5)。
    カセットが手に入り実測できたときに足す。

## D-049: 「印刷しても何も起きない」を起こさない / 起きても自分で直せるようにする

- 状況: 利用者が **PC を再起動したら印刷ダイアログが「接続中」のまま固まった**(2026-08-22)。
  原因は単純で、**トレイが動いていないと名前付きパイプ `\\.\pipe\foilwright` が存在せず、
  スプーラが開けるまで待ち続ける**こと。**画面には「接続中」以外に何の手がかりも出ない。**
- 調査で分かったこと:
  - **インストーラは既に自動起動を登録している**(`install.ps1` 手順 6、`HKCU\...\Run`)。
    アンインストーラも自分が作った登録だけを消す。**導入済みの環境では、この障害は起きない。**
  - **利用者の環境はインストーラ未使用**(開発ビルドを手で起動)だった。
  - **ただし配布経路にも穴が 2 つ**あった。
- 決定:
  1. **トレイの二重起動を防ぐ**(`Global\` 名前付きミューテックス)。
     2 個目は**静かに終了**する(終了コード 0)。
  2. **`troubleshoot.ps1` を配布物に入れる。** 状態を読むだけで、直せるものだけ提案する。
- 理由:
  - **二重起動を防ぐ理由:** パイプは**同時インスタンス数 1** で作られるため、
    2 個目はパイプを作れず例外 → バルーン → 再試行を**延々と繰り返す**。
    インストーラは手順 7 でトレイを起こすので、**次のログオンで Run キーが二重に起こす筋道がある。**
  - **`Global\` を使う理由:** パイプは**計算機全体で 1 本**しかない。
    `Local\`(セッションごと)では別セッションのトレイを取りこぼす。
  - **`AbandonedMutexException` を「取れた」として扱う理由:** 前のトレイが解放せずに落ちた場合、
    ここで諦めると**二度と起動できなくなる**。
  - **「既に起動しています」を MessageBox にしない理由:** **押されるまで 2 個目が居座る。**
    バルーンを数秒出して自分で終わる形にした(伝わることと、居座らないことの両立)。
- **実装中に見つけた 2 つの誤り(どちらも「助言が状況と食い違う」形):**
  1. **「トレイは動いているのにパイプが無い」を異常と決めつけていた。**
     **いちばん多い原因は「プレビュー窓が開いている」で、これは正常**(確認待ちのあいだ
     次のジョブを受け取らない設計)。**「トレイを終了しろ」と案内すると、開いているプレビューを失わせる。**
     窓の有無で案内を分けた。
  2. **「次にやること」を点検の並び順で決めていた**(先に出たものを採る)。
     **並び順は読みやすさで決めており、深刻さの順ではない。**
     実際、**自動起動の未登録(次回ログオンの話)が「今まさに印刷を止めている問題」より先に採られた。**
     優先度を明示する形にした(1 = 今止まっている / 2 = 次回困る)。
- 却下案:
  - **サービスとして常駐させる。** プレビュー窓は利用者のデスクトップに出す必要があり、
    サービスからは出せない。**トレイは利用者セッションで動く必要がある。**

### 【訂正 2026-08-22】原因の説明は誤っていた

**上の「特色は Standard モードで刷られるから 600dpi に落ちる」という推論は、一次資料に支持されない。**
ppmtomd のソースと実走の両方で確かめた結果:

- **印刷モードは「ビット深度」を決めるものであって、走査解像度とは無関係。**
  `print_mode_bpps[]`(`ppmtomd.c:244-251`)が各モードの bits per pixel を持ち、
  man:488 も「Standard = 1 bit per pixel / VPhoto = 4 bits per pixel」と書いている。
  **`print_mode[]` を設定するコード(`ppmtomd.c:1792-1860`)は `output_resolution` を一度も参照しない。**
- **1200dpi 指定で印刷モードは変わらない**(実測)。`-resolution 600` と `1200` の出力差は
  **3 バイトだけ** — `ESC * t` の解像度コード 1 バイトと、ページ幅 2 バイト。
- **我々の 4 構成すべてで、ppmtomd もこのコマンドを送らない**(普通紙・既定モードでは
  CMYK も特色も下地も全部 `byMediaMode`。`lastprintmode` の初期値も同じなので条件が成立しない)。
  **golden がバイト一致していることと整合する。**

**したがって「我々が送っていないコマンド」は、白が横 2 倍になった説明にならない。**
決定 3(実装しない)は**結論としては正しかったが、理由が違う** —
「バイトが未確定だから」ではなく「**そもそも送るべきバイトが無いから**」。

## D-052: 1200dpi のとき、特色プレーンだけ横 1/2 に縮める(ppmtomd から意図的に離れる)

- 状況: **プリンタはカセットのバーコードで走査解像度を決めており、特色は 600dpi で走る**(§14.7.1)。
  1200dpi のジョブでは、こちらが 1200 幅のプレーンを渡すため**特色だけ横 2 倍で刷られる**。
  **実測(2026-08-22)で、開始位置は正しく、幅だけが 2 倍**と分かった
  (黒を同じ紙に基準として一緒に刷って確認)。
- 決定:
  1. **解像度が 1200 のとき、プロセスインク以外(特色・塗る範囲で決まるインク)のプレーンだけ
     横方向を 1/2 に縮める。** 位置の変換は不要。
  2. **縮め方は OR。** 横に並ぶ 2 ドットのどちらかが立っていれば、縮めた側も立てる。
  3. **プロセスインク(CMYK)は一切触らない。** 1200 のまま。
  4. **1200 以外の解像度では 1 バイトも変えない。**
- 理由:
  - **プリンタがどうせ 600 で打つことに、データの側を合わせるだけ**である。
    **特色の刷り上がりは 600dpi 指定にしたときと同じ**になる。
    **得られるのは「CMYK だけ 1200 のまま使えること」の一点。**
  - **OR にする理由:** 特色は下地・上掛け・ベタが主用途で、**塗り残しのほうが害が大きい**。
    間引き(偶数列だけ採る)は**細い線が消えることがある**。
    OR は細い線が最大 1 ドット(600dpi で約 42µm)太るが、こちらのほうが安全。
- **ppmtomd から意図的に離れる(重要):**
  **ppmtomd はこれをやらない。** 1200dpi でも特色プレーンを 2 倍幅のまま出すことを実測で確認済み。
  **したがってこの挙動は golden で守れない。** D-006(ppmtomd がバイト単位の正)から外れる、
  **本プロジェクトで初めての意図的な逸脱**である。
  **代わりに不変条件で守る:**
  - **縮めたプレーンのドット数が、元の横幅の半分に収まること**
  - **1200 以外では出力が 1 バイトも変わらないこと**(実バイトで確認)
  - **プロセスインクのプレーンが変わらないこと**
  - **OR であること**(片方だけ立っている列の組が、縮めた側で立つ)
- 却下案:
  - **ジョブ全体を 600 に落とす。** 特色の結果は同じだが、**CMYK の横解像度も失う。**
    それでよいなら解像度を 600 にすればよく、この機能自体が要らない。
  - **間引き(偶数列)。** 実装は同じくらいだが**細い線が消える**。
  - **バーコードを貼り替えて全部 1200 にする**(供給元の推奨)。
    利用者が「特殊すぎてやりたくない」と判断した(2026-08-22)。
- 補足: **この挙動は「プリンタが特色を 600 で走らせる」という観測に依存している。**
  ALPS の一次資料に明文の裏付けは無い(§14.7.1)。**機種や個体で違えば破れる。**
  **警告は残す** — 縮めても、利用者が何が起きているか分かる状態にしておく。

### 【追記 2026-08-23】「1 個半」は本物の欠落だった
